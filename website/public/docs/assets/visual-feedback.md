# Visual-feedback mechanisms for game-creation harnesses

The creator of [GothicVania Codex Demo](https://github.com/acatovic/gothicvania-codex-demo#implement---evaluate-cycle-is-the-key) describes a browser-testing loop that exposed a floating enemy and led to a gravity fix. That is a useful starting question for a visual-feedback system: which observations let a reviewer distinguish the defect from a jump, spawn animation or moving camera?

For your own regression, record the same encounter before and after the change. Keep the input trace and inspect the approach, expected landing and subsequent movement. A selector that returns only a polished end frame has missed the evidence needed for this verdict. Mark the case insufficient when the relevant interval is absent, and retain the full recording for review.

Compare uniform sampling with the proposed selector on the same recordings and inspection budget, counting exploratory crops and frames too. Have an independent reviewer check whether the selected evidence supports the stated diagnosis. Use the methods below to choose the intervention: retrieving a missed moment, enlarging a small object and retaining a past observation solve different problems. Add a new memory or critique loop only when it addresses the observed failure.

## Choose the intervention before choosing the score

| Question | Relevant mechanism | Evidence that must remain separate |
| --- | --- | --- |
| Which moments support an interaction judgment? | Rubric-directed replay positions; bug-frame retrieval | Frame-selection support versus correct verdict; selected frame versus full event interval |
| Where should the agent look? | High-resolution crop search and coordinate memory | Predicted region versus authoritative object identity; crop-local versus source coordinates |
| What can fit in context? | Hierarchical selection, learned token compression, compact investigation memory | Omitted evidence versus absence of a defect; black-box context policy versus changed model internals |
| Is a strange motion actually a defect? | Game-aware context, alternative-explanation debate, temporal grouping | Inferred rules versus project specifications; model confidence versus calibrated accuracy |
| Which generated asset should be kept? | Retrieval ranking, first-acceptable validation, iterative scene criticism | Appearance versus geometry/material/runtime validity; more candidates versus a better selector |

## 1. A2Z GameSpec-Bench: trace-guided frame retrieval

**Paper-described interface.** A selector receives a visual rubric, executed input trace with render timestamps, and observation budget. It requests replay positions/intervals; a deterministic resolver returns recorded frames. The final judge receives frames and rubric, producing item scores, rationales and cited frame IDs. In its matched-budget experiment, requests resolve to the first captured frame at or after the requested timestamp, subsequent requests can use observed frames, and every inspected frame counts toward the budget.

**Reported finding and qualification.** Across 244 replays from 50 generated Small games, adaptive selection won 60.5% of the 1,159 preference-bearing item comparisons. Among all 4,102 comparisons, 17.1% favored adaptive, 11.2% uniform, 69.4% were equivalent and 2.3% insufficient. This is model-audited rationale support, not correctness against reference labels. Method names were masked but paths retained source-directory names. [Paper v1, §§D.2 and G.3](https://arxiv.org/html/2609.39564v1)

**Availability and terms.** The [official repository](https://github.com/krafton-ai/a2z-gamespec-bench) explicitly says code is forthcoming; its inspected tree has documentation/assets rather than a released evaluator. Do not repeat the abstract’s broader availability claim as proof of an executable selector. Original repository code/GDDs/contracts are MIT, third-party materials retain their own terms. The [dataset card](https://huggingface.co/datasets/KRAFTON/A2Z-GameSpec-Bench) releases 100 GDD/contract/scenario tasks, all in `test`; Small/Big are size categories, not train/test partitions. It specifies Phaser 4.1, TypeScript and Vite.

**Proposed GameMap adaptation, unimplemented.** Use this first for brief UI feedback and action-triggered transitions. Baseline: uniformly spaced original-resolution frames from the *same recording*. Candidate: trace-guided frames, matched by total inspected pixels/frames, including exploratory retrievals. Measure annotated transition coverage and unsupported verdicts. Input events are not proof of rendered outcomes. Keep evaluator-only requirements out of agent context.

## 2. V* / SEAL: guided crops plus visual working memory

**Mechanism.** The VQA model names missing target objects, searches, and reasons over the question, global image, crops and locations. Working memory is per-question context. On 191 V*Bench examples, the [v2 paper, Table 2 and §5.2](https://arxiv.org/html/2312.14135v2) reports 75.39% for SEAL versus 45.02% for a no-memory/search LLaVA-style model trained on the same data. This is not merely switching search off in a frozen checkpoint. Keeping working memory but substituting GroundingDINO or OWL-ViT gives 62.30% or 62.82%, a closer comparison of search against direct detection. These are specialized high-resolution image-QA results, not game-editor or repair gains.

**Source-inspected interface.** [`visual_search.py`](https://github.com/penghao-wu/vstar/blob/4ede6647959cfb59eeabd09286adf6a5f9478da0/visual_search.py) accepts a PIL image, target-object text, search model, minimum patch size, confidence thresholds and optional visualization target box. It returns `(final_step, path_length, search_successful, all_valid_boxes)`. The search recursively divides patches, prioritizes target/context heatmaps, and can fall back to a lower-confidence candidate. A final-step detection is crop-local pixel `(x,y,w,h)`; the enclosing patch has its own original-image offset. The success flag is therefore mandatory evidence, not redundant metadata. In the no-candidate path, `final_step` can remain `None` before being dereferenced: this is a source-visible edge case, not a reproduced crash.

[`app.py`](https://github.com/penghao-wu/vstar/blob/4ede6647959cfb59eeabd09286adf6a5f9478da0/app.py) adds crop offsets, extracts slightly expanded object crops (`patch_scale=1.2`), then maps boxes through square-image padding and normalization before the final VQA call. The demo warns that its search focuses on common objects and single-instance cases.

**Availability and terms.** Public code, benchmark and checkpoint links appear in the [README](https://github.com/penghao-wu/vstar). Repository [LICENSE](https://github.com/penghao-wu/vstar/blob/main/LICENSE) is MIT. The linked [VQA](https://huggingface.co/craigwu/seal_vqa_7b) and [search-model](https://huggingface.co/craigwu/seal_vsm_7b) pages had no substantive model card or license declaration in the inspected page; code MIT is not a clearance for weights, base model or images.

**Proposed GameMap adaptation, unimplemented.** Compare global screenshot only, fixed grid crops, and query-directed crops at matched image/token budgets. Keep the global screenshot so local crops do not erase spatial context. Each crop needs source frame hash, pixel box, transform and explicit search-success status. Add absent-target and repeated-instance cases; do not translate failed search into proof an object is absent.

## 3. VideoTree: relevance-dependent breadth and depth

**Source-inspected interface.** [`adaptive_breath_expansion.py`](https://github.com/Ziyang412/VideoTree/blob/605ec8e917f9a0f95d37a73a0b50bf0e8cfe076e/adaptive_breath_expansion.py) consumes per-video `.pt` frame features and question/caption records. It clusters feature vectors, chooses representative frame offsets, obtains relevance scores, and writes per-video predictions plus `width_res.json` containing `name`, `tree_node`, and `cluster_ids_x`. It doubles breadth until enough scores equal 3 or the maximum is reached; [`defaults`](https://github.com/Ziyang412/VideoTree/blob/main/util.py) are breadth 8→32 and four highly relevant frames.

[`depth_expansion.py`](https://github.com/Ziyang412/VideoTree/blob/605ec8e917f9a0f95d37a73a0b50bf0e8cfe076e/depth_expansion.py) consumes those cluster assignments, features and relevance scores. Score 1 retains a representative; score 2 expands one level; score 3 expands two. It exports `name`, time-sorted `sorted_values` and `relevance`. Paths are hard-coded placeholders.

**Important representation boundary.** [`prompts.py`](https://github.com/Ziyang412/VideoTree/blob/605ec8e917f9a0f95d37a73a0b50bf0e8cfe076e/prompts.py) selects captions for the final prompt, not original frame pixels. Audit index conventions before reuse: representative tensor offsets are zero-based, while the caption-selection code keeps positive offsets and uses `captions[i-1]`. This source-level mapping concern requires a fixture, not a runtime-defect claim.

**Reported finding.** The [paper v2, Table 5(b)](https://arxiv.org/html/2405.19209v2) reports EgoSchema-subset accuracy of 66.2, 64.4 and 61.2 for the full method, removal of depth expansion, and the further removal of adaptive breadth. This is video QA, dependent on caption fidelity, not game debugging.

**Availability and terms.** [Public repository](https://github.com/Ziyang412/VideoTree), MIT [license](https://github.com/Ziyang412/VideoTree/blob/main/LICENSE); Python 3.8+, GPU-oriented clustering/features and an LLM are documented. Dataset/model/provider terms remain separate. Training-free still uses pretrained models.

**Proposed GameMap adaptation, unimplemented.** Treat the output as an index over retained raw evidence. Compare uniform sampling, fixed-width clustering, adaptive breadth only and breadth-plus-depth at equal total caption/model budgets. Include repeated states and brief transitions. Replacing final captions with pixels creates a new adapter.

## 4. LongVU: temporal filtering and selective spatial-token retention

**Mechanism and reported result.** LongVU fuses DINOv2/SigLIP features, removes temporally redundant frames, gives query-relevant frames greater spatial-token resolution, then drops spatial tokens redundant across neighboring frames. In the [ICML 2025 paper, Table 3](https://proceedings.mlr.press/v267/shen25j.html), the 8K-context VideoMME scores progress from 57.56 for uniform 64-token frames to 59.90 with DINO temporal reduction, 60.08 with query selection and 60.56 with spatial compression. Temporal reduction alone slightly lowers EgoSchema versus the 64-token uniform baseline, so the components are not universally beneficial.

**Source-inspected contract.** [`longvu/cambrian_arch.py`](https://github.com/Vision-CAIR/LongVU/blob/1b0be5cc28614b03a423bbaf129ae364750b5012/longvu/cambrian_arch.py) exposes `select_frame(feature_list, split_sizes, input_ids, new_image_aux_list, image_sizes, window_size=16, threshold=0.83)`. It returns selected features, updated frame counts, two selected image tensors and original selection indices. Its long-video branch retains window-center anchors and caps selected frames at 400. Query-ranked resolution allocation and spatial-token dropping occur inside multimodal-input preparation, with additional truncation under pressure. These internal embeddings cannot shorten an unrelated hosted model’s visual context.

The [README inference path](https://github.com/Vision-CAIR/LongVU/blob/main/README.md) decodes roughly one frame per second, preprocesses them, and calls `model.generate(input_ids, images=video, image_sizes=...)`. It emits answer text, not an evidence manifest; the documented local demo asks for a 40G GPU.

**Availability and terms.** Public code with Apache-2.0 [LICENSE](https://github.com/Vision-CAIR/LongVU/blob/main/LICENSE), Qwen2-7B and Llama3.2-3B checkpoints linked. Both inspected upstream checkpoint pages display Apache-2.0 metadata ([Qwen2](https://huggingface.co/Vision-CAIR/LongVU_Qwen2_7B), [Llama3.2](https://huggingface.co/Vision-CAIR/LongVU_Llama3_2_3B)); this does not replace review of the base-model and training-data terms.

**Proposed GameMap adaptation, unimplemented.** Keep this as a model-internal research track, separate from pi harness-only optimization. Hold backbone/weights/evaluator fixed and ablate temporal reduction, resolution allocation and spatial dropping. Export provenance; measure rare-event recall, text loss and temporal-order errors. One FPS decoding cannot recover an event it never sampled.

## 5. Automated Bug Frame Retrieval: useful retrieval pipeline, unsafe headline metric

**Paper-described interface.** Re-encode gameplay video to H.264 medium, extract encoding keyframes, summarize the bug report with a visual/nonvisual flag, and ask GPT-4o for JSON `Explanation` and `Ranking` (frame filenames), or no result. Consecutive batches are re-ranked in a second pass. Candidate coverage and final retrieval success must remain distinct.

**Metric caution.** `Accuracy@N=TP@N/(TP@N+FN)` excludes false positives, so 0.89 is not whole-video accuracy. The reported pass@3≈0.98 also fails its own arithmetic: `1-(1-.68)^3≈.967`, and independent identical trials are not established. The 94 never-correct videos would imply `256/350≈73.1%` with any correct outcome, including correct abstentions, but the repeat-run tallies are inconsistent: the 183/48/25 videos correct in 3/2/1 runs imply 670 correct outcomes, whereas Table 3 reports `528 TP@1+184 TN=712`. Treat 73.1% as an implication of one reported tally, not a verified empirical pass@3; do not cite 98% as a measured result. Industrial data came from one first-person-shooter game; no public executable/data release was identified in the paper. [Paper v1, Table 3 and §5.3](https://arxiv.org/html/2508.04895v1)

**Proposed GameMap adaptation, unimplemented.** Keep separate denominators for candidate-frame coverage, correct retrieval among all bug-bearing videos, false-positive retrieval on clean videos, and correct abstention. Compare encoding keyframes, uniform and event-aware sampling on owned fixtures. Preserve original timestamp mappings. Return temporal neighborhoods for animation/stutter faults; single stills cannot establish them.

## 6. OmniParser: frame-scoped GUI regions and coordinate contracts

Checked 2026-10-19. A released screenshot-to-region interface for editor UI and game HUD observation, with concrete label/coordinate hazards. It complements query-directed V*/SEAL search and temporal trackers; it does not establish game-creation, repair or gameplay gains. No model, engine, installation, weight download, API inference or fixture execution.

### Source boundary

Microsoft OmniParser source inspected at **354021201345a96178360b28733573e27269f2de**, the default-branch commit returned on the check date. This July 2026 revision changes the default detector to YOLOv9-E, so old YOLOv8-only descriptions do not describe this interface. The model repository's observed head was **f55d0750e5b94db2125ef0b45b0fa4a85ddc59b4**; its [merge diff](https://huggingface.co/microsoft/OmniParser-v2.0/commit/f55d0750e5b94db2125ef0b45b0fa4a85ddc59b4) establishes that the new weight and MIT license were released. No weight bytes were downloaded or independently hashed. Direct pinned model-file pages failed to load; folder-license observations below use separately scoped rolling pages.

### Released input/output surface

The local [FastAPI server](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/omnitool/omniparserserver/omniparserserver.py#L16-L48) exposes POST `/parse/` with `base64_image: str`; it returns `som_image_base64`, `parsed_content_list` and `latency`. GET `/probe/` is a readiness response. This is published self-hostable server source, not evidence of a maintained public inference endpoint or successful local execution. The [model page](https://huggingface.co/microsoft/OmniParser-v2.0) reported no Inference Provider deployment when checked.

The [parser wrapper](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/omniparser.py#L16-L32) decodes the image, runs EasyOCR and icon detection/captioning, and returns a numbered overlay plus element records. Records contain `type` (`text`/`icon`), normalized `bbox: [x1,y1,x2,y2]`, `interactivity`, `content`, and `source`. The client later adds `idx`. OCR, detector and caption outputs are fused; those records are not DOM/accessibility elements, engine object IDs, or validated action targets.

**Two incompatible box shapes coexist.** [The helper](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L349-L372) additionally returns `label_coordinates` as a string-ID dictionary of `(x,y,width,height)`, pixels by default and ratios when requested. In contrast, `parsed_content_list[].bbox` remains normalized corner coordinates. The public parser wrapper discards the helper's coordinate dictionary. A consumer must name both coordinate space and box format; `output_coord_in_ratio` is not a general switch for every returned structure. [Conversion and return path](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L416-L496)

### Resize, crop and original-image mapping

The current [YOLOv9 adapter](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/yolov9.py#L52-L87) rounds requested canvas dimensions up to multiples of 32, aspect-fits the screenshot, truncates resized dimensions to integers, and centers it on a `(114,114,114)` canvas. It restores detector boxes by subtracting left/top padding, dividing by the nominal scale and clamping to original image dimensions before returning pixel `xyxy`. [Inverse mapping](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/yolov9.py#L115-L136)

The server wrapper sets `scale_img=False`; consequently `predict_yolo` does not forward `imgsz`, and this adapter uses its default 640 canvas. The model card's separate example uses 1280, top-left padding, different resizing and suppression settings. Those are distinct configurations, not interchangeable recipes; neither establishes accuracy for tiny editor controls. [Caller and detector dispatch](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L390-L445)

The default Florence/non-Phi caption path crops selected icon regions from the original screenshot using integer pixel boundaries, then stretches them to 64×64 before processing. OCR-only regions are not all captioned, and the separate Phi path does not use this resize. This can remove surrounding UI context and alter aspect ratio. [Caption crop path](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L88-L131)

Any caller-supplied viewport crop or resize is outside those inverse transforms. Proposed GameMap mapping: normalized box → input screenshot pixels → inverse caller resize/padding → source-frame crop offset → desktop/window coordinates only if actions need them. Record original/crop dimensions, offsets, rounding, display scale and window position; a ratio does not encode these transforms. Keep image and action coordinate spaces separate.

### IDs, interpretation and failure boundaries

- The [client](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/omnitool/gradio/agent/llm_utils/omniparserclient.py#L14-L44) enumerates records afresh, attaches screenshot width/height, original screenshot bytes and a filename UUID. There is no temporal matching in this path. IDs are valid for this parse/overlay only; sorting and overlap filtering can renumber them on a later frame. The server alone supplies neither frame ID nor image hash. [Screenshot UUID creation](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/omnitool/gradio/tools/screen_capture.py#L10-L27)
- The [action consumer](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/omnitool/gradio/agent/vlm_agent.py#L149-L168) indexes the current record list by predicted Box ID and takes the normalized-box midpoint times screenshot dimensions. That is a coordinate proposal, not proof the target is enabled, unobscured or still present when clicked. A screenshot UUID is useful association metadata but does not establish freshness or pixel identity.
- `interactivity` is assigned false to OCR text and true to detector icons in the [fusion path](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L251-L328), not checked against application state. Overlapping OCR may become icon content; an icon inside OCR may be removed. Its overlap criterion includes intersection/individual-area ratios as well as IoU. Returned source labels distinguish OCR/fused/caption paths, but detector confidence is not preserved in these element records. Icon descriptions are generated interpretations, not verified semantics.
- **Source-visible edge case, unexecuted:** when no OCR boxes are found, `get_som_labeled_img` sets `ocr_bbox=None` then immediately evaluates `zip(ocr_bbox, ocr_text)`. This is an unguarded failure path in the inspected code, especially relevant to text-free viewports; do not report it as a reproduced crash or convert a parser failure into “no objects.” [Exact branch](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/util/utils.py#L437-L446)

### Code/model license and availability split

The pinned repository's [LICENSE](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/LICENSE) is **CC-BY-4.0**, despite the [README](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/README.md) MIT badge. Preserve that discrepancy. The model folders separately declare [YOLOv9-E `icon_detect_v3`: MIT](https://huggingface.co/microsoft/OmniParser-v2.0/blob/main/icon_detect_v3/LICENSE), [Florence `icon_caption`: MIT](https://huggingface.co/microsoft/OmniParser-v2.0/blob/main/icon_caption/LICENSE), and [legacy `icon_detect`: AGPL-3.0](https://huggingface.co/microsoft/OmniParser-v2.0/blob/main/icon_detect/LICENSE). The model card's permissive-pipeline language does not resolve the repository license mismatch or dependency terms. The source [requirements](https://github.com/microsoft/OmniParser/blob/354021201345a96178360b28733573e27269f2de/requirements.txt) still include Ultralytics. The detector loader can fetch rolling `main`; pin source, actual weight/config and OCR/caption dependencies independently before any future use.

### Proposed bounded GameMap comparison, not implemented

Compare global screenshot; screenshot plus OCR regions; screenshot plus full OmniParser records/overlay. Hold screenshots, model, task set, permissions and total observation budget fixed; include preprocessing/caption latency and failures. Use owned editor/HUD fixtures with repeated icons, tiny controls, nested text/buttons, disabled controls, a viewport crop and a moved window; include blank/text-free inputs and a stale parse after a layout change.

Score region recall, text/semantic correctness, coordinate round-trip error and target selection separately; then measure an authorized action's actual result if needed. Reject stale `(frame hash, parse ID, region index)` references, retain original evidence and authoritative UI/engine assertions, and treat missing/failed parses as explicit outcomes. This tests a GUI observation adapter, not general game understanding or engine-state truth.


## 7. FiftyOne: persistent retrieval over capture evidence

Checked **2026-10-19**. This fills a distinct gap beside V*/SEAL, VideoTree, LongVU, VideoAgent and OmniParser: a released dataset/view/index interface for revisiting stored frames and failed regions across edit iterations. It is not a visual reasoning model or evidence of improved game creation. Source inspection only; no installation, server, model, embedding, media download or execution.

**Source boundary.** FiftyOne inspected at `aacfc8182fc5353296b5edd7475e63335fedb5cb`; its separate Brain repository at `ba978a12293fda9953b478f601ac8950d2a35aa4`. These independently resolved revisions identify the inspected contracts, not a tested compatible installation.

### Identity, coordinates and mutation boundaries

- **Persistence is not an artifact snapshot.** Datasets are non-persistent by default; `persistent=True` retains database records, while raw media remains in external files. Saved views retain selection rules and can change when the underlying records change. Keep original files/hashes and a materialized result manifest separately from a named view. [Dataset persistence](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/using_datasets.rst#L139-L157), [saved-view semantics](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/using_views.rst#L187-L196)
- **Video → frame.** `to_frames()` retains parent-video `sample_id` and **1-based** `frame_number`; the implementation reuses source frame IDs. Without sampling, frames lacking `filepath` are omitted. `sample_frames=True` writes images and source frame paths, and normally reuses existing sampled images unless `force_sample=True`. FPS selection operates on frame numbers; these inspected interfaces do not establish original presentation timestamps or engine ticks. Preserve the recording hash, explicit frame-to-PTS/tick mapping, sampling/resize parameters and derivative hash; a reused path is not proof of fresh pixels. [Frame construction and sampling](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/fiftyone/core/video.py#L528-L648), [source frame identity](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/fiftyone/core/video.py#L944-L978), [1-based convention](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/using_datasets.rst#L5139-L5147)
- **Frame → patch.** Chaining `to_frames().to_patches(field)` yields parent-video `sample_id`, `frame_id` and `frame_number`. The patch ID is the source **label ID**, while `filepath` remains the full-frame path: this view does not itself establish a separately saved crop. `Detection.bounding_box` is normalized `[x,y,width,height]`, unlike OmniParser's normalized corner coordinates. Actual crop extraction can expand/square boxes; preserve those parameters and the crop-to-original transform. IDs identify records, not immutable pixel content; retain additional provenance via `other_fields` or explicit parent joins. [Patch projection/IDs](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/fiftyone/core/patches.py#L936-L988), [box contract](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/fiftyone/core/labels.py#L450-L459), [crop operations](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/fiftyone/utils/patches.py#L160-L189)
- **Views can write back.** Editing patch labels and certain frame fields, or calling view `save`/`keep`/`keep_fields`, can modify/delete underlying annotations. Patch sample tags and unrelated sample fields have different propagation rules; frame tags/metadata do not propagate. Treat evidence browsing and annotation edits as different operations. [Patch propagation](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/using_views.rst#L1162-L1197), [frame propagation](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/using_views.rst#L1888-L1919)

### Similarity freshness and result provenance

Search within a view only returns indexed members; unindexed captures cannot appear. Index membership and current annotations/media therefore need independent checks. Explicit `add_to_index`/`remove_from_index` operations manage vectors, and the pinned guide instructs sklearn users to call `save()` after those edits. This guidance should not be read as saying every backend path defers all writes: sklearn with `embeddings_field` configured writes added embeddings directly. Brain's base `reload()` refreshes view IDs; sklearn can reload stored embeddings, but neither inspected reload path recomputes embeddings from changed pixels/boxes. `missing_size=None` can mean unsupported/unknown, not confirmed completeness. [Membership](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/similarity.rst#L154-L164), [missing-size caveat](https://github.com/voxel51/fiftyone-brain/blob/ba978a12293fda9953b478f601ac8950d2a35aa4/fiftyone/brain/similarity.py#L515-L525), [manual save](https://github.com/voxel51/fiftyone/blob/aacfc8182fc5353296b5edd7475e63335fedb5cb/docs/source/user_guide/similarity.rst#L760-L767), [view/reload contract](https://github.com/voxel51/fiftyone-brain/blob/ba978a12293fda9953b478f601ac8950d2a35aa4/fiftyone/brain/similarity.py#L613-L719), [sklearn reload](https://github.com/voxel51/fiftyone-brain/blob/ba978a12293fda9953b478f601ac8950d2a35aa4/fiftyone/brain/internal/core/sklearn.py#L327-L340)

## Temporal verification: GliDe / VideoGlitchBench

**Source scope:** [paper v2](https://arxiv.org/html/2604.07818v2), plus six inspected files at upstream commit `0626688f2b2eab5414d8f8e28e682cfaf607c0ab` (2026-10-18). This is offline gameplay-video diagnosis, not a game-creation agent or authoritative physics assertion.

- **Interface and mechanism:** The [README](https://github.com/SandyyyZheng/GliDe/blob/0626688f2b2eab5414d8f8e28e682cfaf607c0ab/README.md) documents video/game-name inputs, frame-window screening, targeted VQA/crops and optional SAM3 tracking, then event grouping and interval refinement. Output JSON contains bug descriptions and one or more second-based intervals per bug. Optional tracking can be disabled when unavailable, so tool availability must accompany a result. Intermediate artifacts can be saved.
- **Actual information policy:** In [graph.py](https://github.com/SandyyyZheng/GliDe/blob/0626688f2b2eab5414d8f8e28e682cfaf607c0ab/graph.py), game context is the longest of the first three distinct nonempty scanner descriptions. It is inferred context, not a retrieved authoritative rulebook. No positive scanner window routes directly to summarization, skipping detailed analysis and grounding. [Memory code](https://github.com/SandyyyZheng/GliDe/blob/0626688f2b2eab5414d8f8e28e682cfaf607c0ab/analyzer/memory.py) compresses older debate rounds in planner context to judge conclusions; the latest two get more detail. Serialized tool evidence supplied to debate prompts is truncated to a 1,500-character prefix, followed by an omission notice. Full stored evidence and model-visible evidence therefore differ.
- **Reported evidence:** The paper's Qwen2.5-VL-7B ablation reports description F1 of 39.12 with the full system, 33.03 without game context and 32.17 without debate; grounding removal changes its mIoU from 0.53 to 0.32. Those are the authors' dataset/backbone-specific findings, not a matched-cost claim or proof of reliable project QA. A single unusual pose can be valid game behavior; disconnected temporal intervals can describe one recurring event.
- **Evaluator discrepancy and denominators:** The paper assigns pairs using semantic score multiplied by temporal IoU; the pinned [evaluator.py](https://github.com/SandyyyZheng/GliDe/blob/0626688f2b2eab5414d8f8e28e682cfaf607c0ab/evaluation/evaluator.py) assigns using semantic score alone, then computes overlap. Its description precision/recall sum matched 0–5 judge scores and divide by `5 × predicted/ground-truth bug count`; this is soft description credit, not thresholded true-positive counting. The paper's printed equations omit that factor of five. Mean IoU averages matched pairs only; unmatched events do not enter that mean, and correct no-bug videos do not increase the description numerator. The dataset loop uses only shared ground-truth/prediction names, so missing predictions are excluded. Description-scoring errors can become zero scores. Matching, normalization, missing-output policy and judge failures must be reconciled before calling a run a paper reproduction.
- **Release and terms:** Pipeline and evaluator files are public; [code license](https://github.com/SandyyyZheng/GliDe/blob/0626688f2b2eab5414d8f8e28e682cfaf607c0ab/LICENSE) is MIT. The [dataset card](https://huggingface.co/datasets/SandyZheng33/VideoGlitchBench) declares Apache-2.0, 4,717 glitch clips and 521 negative clips, with annotations and game-organized video files. Its viewer's split label is `train`; that does not establish a held-out optimization protocol. Underlying game/video rights and model dependencies still need separate review. No data archive, model or service was run.

**Comparison template:** compare uniform-window screening, game-context only, debate only and temporal grouping under both equal call/token budgets and reported wall time. Measure candidate-window recall before downstream analysis; include rare brief failures and legitimate stylized movement. Freeze a complete expected-episode manifest, count absent/error outputs separately, preserve report-to-frame references and state whether matching follows paper or code. Compare compressed judge summaries against raw evidence under the same context budget; keep authoritative project rules separate from model-inferred memory. None of these ablations is implemented here.

## Proposed controlled harness search

Treat evidence acquisition as an explicit candidate component alongside the action/tool policy. Keep the game project, model, permissions and task set fixed unless the experiment is expressly about changing them.

1. **Observation packet.** Retain original video/images and build ID; record source timestamps or simulation ticks, camera/viewport, crop-to-original mapping, selection query, model-derived masks/labels, selected and rejected candidate IDs, and omitted-frame ranges. A compact packet should point back to original evidence rather than replacing it.
2. **Matched baselines.** Compare uniform time samples, event-triggered samples and query-adaptive samples at equal frame/pixel budgets; compare full frames versus crop-plus-global-context at equal visual-token budgets. Report selector calls, preprocessing, generation attempts, latency and failures as well as final-model tokens. For learned compression, report the changed checkpoint/architecture separately from prompt/tool-only harness changes.
3. **Useful counterexamples.** Include brief contact failures, valid exaggerated animation, occluded objects, repeated events separated by normal intervals, small HUD changes and empty/missing captures. For assets, test back views, scale/axis/pivot, alpha/material behavior and target-engine import in a future authorized fixture; an aesthetically preferred thumbnail cannot certify these properties.
4. **Separate outcomes.** Score evidence coverage, temporal/spatial localization, diagnosis, proposed repair, executed functional result and subjective quality independently. Keep a no-feedback baseline and a same-budget extra-generation baseline; otherwise a feedback benefit may simply reflect additional attempts.
5. **Prevent selection leakage.** Use project/game-disjoint development and final sets where feasible. Freeze judge prompts and expected episode IDs before comparison. Do not expose held-out answer keys, final scores or inferred final-test lessons to persistent candidate memory. Account for failures, unavailable tools and abstentions rather than dropping them.
6. **Pin and audit.** Preserve source and model revisions, service names, raw tool results, compressed context and exact score implementation. Paper/code discrepancies need an explicit protocol choice before execution. Purpose-specific code, weight, data and service permissions remain a separate gate.

**Remaining boundary:** the collection supports a bounded experiment design, but cannot select a universally best visual harness. That requires a chosen target game/project family, an authorized runtime, owned or cleared assets, calibrated acceptance assertions and a compute/latency budget. No such experiment is claimed here.

### ZoomEye: inference-only crop search

ZoomEye searches image regions using the same frozen model's Yes/No logits for existence, potential visibility and answerability. This requires logit access and model-specific preprocessing, rather than an arbitrary hosted chat endpoint. Its [model wrapper](https://github.com/om-ai-lab/ZoomEye/blob/6762d79f3153552d03b49a2d5c07caaa44fac375/ZoomEye/zoom_model.py) expands selected patches, adds padding/overlays and supplies local or global-plus-local imagery. Saved boxes alone do not reproduce those pixels.

The [tree](https://github.com/om-ai-lab/ZoomEye/blob/6762d79f3153552d03b49a2d5c07caaa44fac375/ZoomEye/tree.py) stores original-image pixel `(x,y,width,height)`, despite the paper's normalized-corner notation. Child offsets remain source-relative. The [search loop](https://github.com/om-ai-lab/ZoomEye/blob/6762d79f3153552d03b49a2d5c07caaa44fac375/ZoomEye/zoom_eye.py) relaxes confidence after its initial pop threshold and extends search; this is not a hard inference-call budget. Queue ranking adds model calls, while exported counters omit failed searches and all-instance work.

[Paper v4, Tables 4–5](https://arxiv.org/html/2411.16044v4) reports 93.45/54.55 accuracy conditional on successful/failed localization, not a randomized crop ablation. Changing partition count changes both accuracy and search effort. MME-RealWorld spatial-position performance regresses, warning against equating localization with spatial understanding.

Code is public at the linked pin, but the [complete tree](https://api.github.com/repos/om-ai-lab/ZoomEye/git/trees/6762d79f3153552d03b49a2d5c07caaa44fac375?recursive=1) has no license text; an Apache classifier in LLaVA-labelled packaging leaves ZoomEye-specific reuse permission unclear. Linked base checkpoints and images require separate rights review.

### DeepEyes: RL-trained crop-tool policy

[DeepEyes v3, Table 9](https://arxiv.org/html/2505.14362v3) compares differently trained policies: same-data text-only RL scores 88.5/75.4/60.8 on V*/HR-4K/HR-8K, versus 90.1/75.1/72.6 for interleaved visual reasoning. It changes weights and does not win every benchmark.

The [training helper](https://github.com/Visual-Agent/DeepEyes/blob/11d20c6be32b2cf62c914e0c73a06db2f9a7e3a1/verl/workers/agent/envs/mm_process_engine/visual_toolbox_v2.py) reads pixel-corner boxes, clamps them and rejects sides ≤30 pixels. Cropping and rotation use the original first image, not the previous observation. The [released evaluator](https://github.com/Visual-Agent/DeepEyes/blob/11d20c6be32b2cf62c914e0c73a06db2f9a7e3a1/eval/eval_vstar.py#L175-L277) instead directly crops/resizes, parses model text with Python `eval`, and permits eleven generation calls of up to 10,240 tokens each. Exhaustion can retain runner status `success` without a complete answer; this is separate from answer-correctness scoring. Its parser and termination labels need replacement before reuse.

Code has [Apache-2.0 terms](https://github.com/Visual-Agent/DeepEyes/blob/11d20c6be32b2cf62c914e0c73a06db2f9a7e3a1/LICENSE); the [weight card](https://huggingface.co/ChenShawn/DeepEyes-7B) also declares Apache-2.0. Base-model/data terms remain separate.

## Visual-history reuse, external memory and controlled exposure

### HistPrune-GUI: reuse encoded history before lossy compression

The current [paper v4, *Where and How to Prune*](https://arxiv.org/html/2603.26041v4) evaluates GUI next-action prediction on AITW, Mind2Web, AndroidControl and GUI-Odyssey with task-finetuned Qwen2.5-VL-3B/Qwen3-VL-2B. Its pruning intervention needs no additional training. Historical-image tokens are pruned inside the decoder; the current screenshot, instructions and action text stay intact. In Table 1, on AITW/Qwen3-VL-2B, ViT caching changes step success from 0.7035 to 0.7030 while reducing reported FLOPs 31.5% and wall time 11.8%; peak memory increases 1.52%. This is feature reuse, not a smaller observation packet. In a separate composition experiment (Table 12), adding 10%-retention random history pruning lowers wall time further but yields 0.6853 step success. Cache and pruning benefits must therefore remain separate. The paper also finds that background coverage and spatially distributed retained tokens matter; foreground-only selection is not a safe general rule.

At code commit `bc3118c85f9a1b1b6e496af857144e8f901c8132`, the [AndroidControl evaluator](https://github.com/Daiqiang-Li/HistPrune-GUI/blob/bc3118c85f9a1b1b6e496af857144e8f901c8132/AndroidControl_eval.py#L1250-L1324) supplies image paths and reference-action history, clears the cache per episode and evicts images outside its history window. [Qwen2.5 caching](https://github.com/Daiqiang-Li/HistPrune-GUI/blob/bc3118c85f9a1b1b6e496af857144e8f901c8132/src/Qwen2_5/model_file/LLM_compression_v2_5_action/modeling_qwen2_5_vl.py#L2610-L2677) reuses features by supplied string key plus grid shape, without checking image content. Immutable capture identity is consequently an adapter requirement. This cannot optimize an unrelated hosted model through prompt changes.

Code and [checkpoint folders](https://huggingface.co/lidaiqiang/HistPrune-GUI/tree/main) are public; the checkpoint page lacks a model card/license, and the inspected code tree lacks a repository-wide license. Inherited model-file Apache-2.0 headers do not settle every file’s or weight’s terms.

### MementoGUI: event-gated ROI memory outside the action model

The [paper](https://arxiv.org/html/2605.18652v1) describes a separately trained controller receiving goal, current screenshot, previous action and working memory. It emits write salience, summary, ROI box and a retrieval trigger. Retained entries pair summaries with crops; older entries compress into summaries plus visual references. Completed episodes become retrievable experience. Coarse embedding retrieval is followed by learned selection. The frozen action model consumes ordinary text and images, making this an external-context design rather than token surgery.

Evaluation is offline GUI action prediction, including 80 MementoGUI-Bench test trajectories and 120 memory-building trajectories. The ROI ablation is mixed: restoring images improves UI-Venus GUI-Odyssey action matching 64.22→67.69, but MementoGUI-Bench VLM action-match score falls 1.53→1.41. Do not repeat the prose’s universal-improvement claim; memory-consistency scores are also judge assessments, not authoritative state.

The [verified repository revision](https://github.com/zzzmyyzeng/MementoGUI/tree/9b32877e42ab8708aba90c6db3bca4ce984ca6be) contains a project page and images, with placeholder resource links and no verified controller, evaluator, checkpoint or license release. Treat this as a design hypothesis. For game creation, preserve full-frame/build references behind every remembered crop and evaluate delayed visual constraints separately from successful edits.

### EMemBench: hold the experienced history fixed when comparing memory

[EMemBench v2](https://arxiv.org/html/2601.16690v2) generates memory questions from logged game trajectories and underlying state. It distinguishes questions about an agent's own experience from controlled exposure to the same recorded history and QA set. The latter helps separate memory reconstruction from differences in exploration. Its reported controlled-exposure experiment uses Jericho text games; visual Crafter results should not be described as the same controlled comparison. The paper describes query-horizon controls that scope question evidence and answers to a prefix; these are not an image-token budget. These are memory-question results, not game-creation quality or proof that a compressed history preserves every relevant observation.

**Inspected visual interface.** The author-linked [March source snapshot](https://github.com/InternLM/EMemBench/tree/8d38a655245934ff8c77bbad0bef4718224017e3) predates that paper revision. Its [answering script](https://github.com/InternLM/EMemBench/blob/8d38a655245934ff8c77bbad0bef4718224017e3/visual_game/answer_crafter_qa.py#L271-L407) offers step-labelled mosaics, an `all` mode capped at the first 50 ordered frames, and first/middle/last sampling. [Default mosaic settings](https://github.com/InternLM/EMemBench/blob/8d38a655245934ff8c77bbad0bef4718224017e3/visual_game/answer_crafter_qa.py#L747-L752) use ten columns, a 160-pixel maximum tile side, 200 frames per image and at most ten mosaics per question batch. Resizing and retained-frame counts therefore need separate accounting. The same [batch construction](https://github.com/InternLM/EMemBench/blob/8d38a655245934ff8c77bbad0bef4718224017e3/visual_game/answer_crafter_qa.py#L472-L512) includes an action/reason/resource-stat timeline; a score from this path cannot isolate image-only recall. The older [generator](https://github.com/InternLM/EMemBench/blob/8d38a655245934ff8c77bbad0bef4718224017e3/visual_game/generate_crafter_qa.py#L1446-L1474) also has whole-episode templates outside its range-based prefix helper, and its answer context remains untruncated; do not treat the paper’s horizon guarantee as universally implemented by these bytes. These are source-inspected controls, not a measured packing ablation.
