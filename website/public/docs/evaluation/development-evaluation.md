# Evaluating agents that create games

Choose an evaluation around what the agent needs to produce: a playable project, a correct modification, a delivered build, or a diagnosed defect. The studies below use different tasks and success criteria; use the [reproduction reference](./benchmarks.md) to locate the artifacts needed for each.

## 1. OpenGameEval: stateful development and exploration

Primary sources: [Roblox repository](https://github.com/Roblox/open-game-eval), [paper](https://arxiv.org/abs/2610.02563).

- **Tasks and evaluation:** The [paper v1](https://arxiv.org/html/2610.02563v1) scores 113 tasks: 84 core and 29 debugging, analyzed separately after four exclusions. Thirteen models receive 16 attempts per task. Public reference solutions cover 67 of the 113. Every check phase must pass; the 84-task core denominator retains ten tasks with no between-model discrimination.
- **Available artifacts:** Task Lua files, places, plugin and submission client are public under MIT. Hosted runs require a Roblox account/OpenCloud key and caller-provided LLM credentials. The [reproduction review](./benchmarks.md#evidence-and-revision-boundary) records the paper's explicit private-runtime and unreleased-system-prompt blockers; the local plugin does not invoke an assistant.
- **Concrete annotation caveat:** Empty expected-instance fields mean unannotated dependencies, not zero dependencies. They should not become zeroes in an exploration score.
- **Lifecycle boundary:** The README lists queued/pending/completed/failed service states and a ten-minute default timeout. A subsequent [client-code inspection](./benchmarks.md) found a 900-second polling budget that excludes request durations, so the README figure is not a verified wall-clock limit. Neither timeout nor job completion alone establishes cancellation or a passing task verdict. Custom model endpoint URLs are described as unsupported.

**Editorial use:** This is a stronger source for “inspect before editing” measurement than anecdotal development transcripts. Retain task/check revision, attempts, observation trace, final check results and service errors separately. A correlation between inspection and success is not a causal guarantee. Before execution, review credential transmission and service permissions rather than assuming repository access grants them.

## 2. SWE-Game: restoration and preservation across construction, repair and porting

Primary source: [paper v3, October 7, 2026](https://arxiv.org/html/2609.33678v3).

- **Tasks:** 247 tasks derive from 41 reference Godot games across 13 categories. Modes include briefs, game-design documents, skeleton completion, 83 injected-fault repair cases and Godot-to-Unity porting.
- **Evaluation:** Semantic instrumentation connects independently structured implementations to evaluator-owned actions and engine-state observations. Certified reference-input replay and agent-authored demonstrations complement local checks. Matched no-input controls test action dependence. Repair checks compare reference, faulty and repaired projects for both restoration and preservation; construction also has separate visual rubrics.
- **Limits:** Instrumentation and demonstrations are part of the evaluation contract, not a universal correctness oracle. Reported human-alignment studies validate specified samples, not every possible behavior or future engine version.

**Version review:** The task counts, instrumentation, replay/no-input controls, and restoration/preservation distinctions above are based on v3.

**Artifact availability and identity:** The previously linked Touchstone-AI-Lab catalogue does not establish this paper's release. Its [pinned task JSON](https://github.com/Touchstone-AI-Lab/swe-game-tasks/blob/8459c64cb1839dbaffa9e2c23800363f13078425/tasks.json) contains 156 mod-repair/construction entries across 12 games, including Don't Starve Together, Garry's Mod and The Binding of Isaac; its [site description](https://github.com/Touchstone-AI-Lab/swe-game-tasks/blob/8459c64cb1839dbaffa9e2c23800363f13078425/index.html) explicitly says game-mod tasks. That inventory does not match the paper's 247 tasks, 41 Godot games and five modes. No author-provided linkage was verified. Treat the catalogue as a same-name identity collision until established otherwise; the paper's executable release and software/data rights remain unverified.

**Editorial use:** Porting should be scored on preserved behavior under an engine-specific execution contract, not source resemblance. Keep repaired-target checks and previously correct behavior as separate results. Proposed local fixtures would include a fake victory screen with no input, a repair that breaks an unrelated mechanic, and a port with visually correct but ineffective collisions.

## 3. Play2Code / PlaytestArena: separate refinement feedback from final judging

Primary sources: [GUI Agents for Continual Game Generation, v2](https://arxiv.org/html/2605.28258v2), [author project page](https://continual-game-generation.vercel.app/).

- **Tasks and dimensions:** PlaytestArena contains 200 browser-game prompts across eight genres with criterion-level expected behavior. The paper separates a coding/refinement loop from benchmark judgment.
- **Evaluation boundary:** The Play2Code GUI playtester sees the game and returns traces/actionable feedback without the final rubric. A separate GUI judge receives the rubric and determines criterion pass/fail. It neither shares the loop's memory nor provides refinement feedback. This distinction matters more than treating every GUI agent as an interchangeable “tester.”
- **Limits:** Human comparison and cross-judge studies are reported, but timing-sensitive failures may reflect evaluator action latency rather than a broken game. The paper retains this ambiguity.
- **Available artifacts:** An author-associated [demo repository at `8c5e167`](https://github.com/RunRiotComeOn/gui-agents-for-continual-game-generation/tree/8c5e1675fc25da0876e48dcbe1da5f5f4e57bed7) provides eight browser-demo directories and a root [Apache-2.0 LICENSE](https://github.com/RunRiotComeOn/gui-agents-for-continual-game-generation/blob/8c5e1675fc25da0876e48dcbe1da5f5f4e57bed7/LICENSE). The [README](https://github.com/RunRiotComeOn/gui-agents-for-continual-game-generation/blob/8c5e1675fc25da0876e48dcbe1da5f5f4e57bed7/README.md) describes a static gallery; some directories contain bundled builds rather than uniform development sources. The [owner profile](https://github.com/RunRiotComeOn) matches the paper author’s name, affiliation and public correspondence, and the repository links the paper-designated project domain. This corroborates author association; the paper does not directly link this code revision. The full 200-task/rubric corpus and executable refinement/final-judge implementation remain unverified. The root license does not independently clear bundled third-party assets. No demo was executed or benchmark result reproduced.

**Editorial use:** A future fixture should save revision-specific builds, play traces and repair requests, then evaluate the final build with a separate rubric holder. Reusing the same evaluator feedback for optimization and final scoring would change this experimental design. Cross-task memory must also be recorded so an apparent improvement is not attributed only to one local revision.

## 4. WebGameBench: delivery quality rather than build success

Primary source: [paper v1](https://arxiv.org/html/2605.17637v1), [abstract](https://arxiv.org/abs/2605.17637).

- **Tasks:** 111 browser-game tasks use frozen structured specifications, a unified build/serve protocol and runtime interaction; the study reports 12 agents across 14 configurations.
- **Dimensions and denominator:** The evaluator checks input, spatial mapping, rules, state transitions, terminal conditions and restart. Excellent/Usable rates use only valid scored attempts; Usable includes Excellent. Coverage is the fraction of attempts receiving a valid label. Artifact-caused build/serve/access failures count as Unusable; evaluator/infrastructure failures, corrupted evidence and unresolved evaluator timeouts may be unscored. Report coverage alongside quality rates. This policy is also explicit in [v2, §4.1](https://arxiv.org/html/2605.17637v2).
- **Limits:** The paper explicitly says human alignment is stronger for usable-rate estimation than exact three-way quality labeling. Template-generated specifications and runtime preconditions do not exhaust randomized, long-horizon or multi-session behavior. It is evidence about browser-accessible artifact delivery, not arbitrary software competence.
- **Availability:** The examined primary paper provides a protocol; no working official evaluator/data repository or reusable code/data license was verified. Do not advertise a ready-to-run package solely from the paper.

**Editorial use:** Preserve build health, load health, playable delivery and requirement satisfaction as distinct fields. An acceptable failure report should show the interaction and observation that failed, rather than translating “page loaded” into “game works.” This is complementary to the existing engine-native benchmark notes.

## 5. JAMER / JamSet / JamBench: project structure and runtime behavior

Primary source: [paper v1, June 18, 2026](https://arxiv.org/html/2606.19830v1).

- **Tasks and data:** The paper describes 8,133 verified 2D Godot projects, with 300 manually verified benchmark projects and the remainder forming JamSet. Tasks cover theme-driven generation and completion at different code granularities.
- **Evaluation:** Headless checks separate file integrity, compilation, runtime stability, Structural Completeness Score and Behavioral Alignment Score. No online LLM verdict is used, but offline LLM-generated eval_config selects player nodes, tracked signals and expected behaviors used to derive input strategies. Thus verification depends on model-produced configuration; it is not annotation-independent. This distinction persists in [v2, §§3.3/4.4 and Appendix D.1](https://arxiv.org/html/2606.19830v2).
- **Scope limits:** It evaluates code frameworks, not complete art/audio quality, and does not cover Unity/Unreal. Cross-file dependencies can fail behaviorally despite a structurally complete result.
- **Availability and rights:** The abstract claims all data/code are public, but the Ethics/Open-Source Commitment section says they will be released. It says only open-source-licensed source projects were included. A working official release URL and consolidated downstream license inventory were not verified from the examined source. Preserve “paper claims public availability” separately from “artifact retrieved and verified”; source-project licenses cannot be replaced by a blanket dataset assumption.

**Editorial use:** This fills a project-scale engineering gap without relabeling code completeness as polished game quality. A future experiment should record project scale, removed code granularity, imported asset treatment, headless settings and behavioral coverage alongside compilation.

## Adjacent dataset worth retaining, not an agent leaderboard

[OSSGameBench's author-hosted MSR paper](https://nimmiw.com/papers/MSR_2026_data_and_tool_track.pdf) explicitly links [Zenodo record 18359123, version v3](https://zenodo.org/records/18359123). Its publication date is **January 23, 2026**; January 24 is the record's technical created/modified date. The paper reports 950 game/tool repositories after deduplicating 970 candidates. These are development-history records, not 950 executable repair tasks.

The inspected [Scripts.zip](https://zenodo.org/records/18359123/files/Scripts.zip?download=1) matches the record's MD5 `b416d06113d02a7abdccb636508c0c9d`; [analysis.zip](https://zenodo.org/records/18359123/files/analysis.zip?download=1) matches `8c6155a7603b391ded1991caf69ed6b6`. Separate repository families and time periods; withhold target fixes and post-resolution discussion from agent context. Add a reproducible failing fixture, repair acceptance checks and regression tests. None of those proposed gates was implemented or evaluated here.

## 6. GameASG-Bench: declare behavioral testability before generation

Primary sources: [paper v1, September 18, 2026](https://arxiv.org/abs/2609.21293v1), which directly links the [official repository](https://github.com/areal-project/GameASG-Bench); this review inspects [release commit `6427cb6`](https://github.com/areal-project/GameASG-Bench/tree/6427cb6517ce11ff350ec45fcae17b67c5aec245). Source inspection only; no installation, model call or benchmark execution.

- **Tasks and delivery:** 47 browser-game generation tasks span 12 primary genres, including 32 2D and 15 3D games. Each task provides a prompt, gameplay specification and public testing contract; the submission is a single `index.html`. The inspected release contains all 47 task prompts and matching executable L2 suites. [Pinned README](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/README.md)
- **Contract and runtime evidence:** `window.__gameTest` exposes reset, legal scenario setup, player-level input and stable snapshots. Scenario setup must not pre-apply the outcome being tested. The Armor Alley suite combines semantic observations with real keyboard/mouse input, checking resource changes, sustained fire/release, pause invariants and terminal locks. This is concrete behavioral coverage, not a general correctness oracle. [Contract](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/task/armor-alley/tdd.md), [checks](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/tests/armor-alley/checks.js), [Chromium CDP runner](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/scripts/l2/run.js)
- **Isolation and entrypoints:** Generation receives task documents without benchmark tests. Separate evaluation mounts the submission and checker inputs read-only and writes reports separately. `docker_run.sh` supports Claude Code/Codex generation; `docker_test.sh` evaluates an existing HTML without a model key. Isolation reduces experiment-time exposure but does not establish training-data decontamination. [Evaluation orchestration](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/docker_test.sh), [entrypoint](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/docker_test_entrypoint.sh)
- **Metric boundary:** The report's strict success requires recorded successful generation, usable evaluation results, every L1 check passing, and applicable checks in **both P0 and P1**, all passing; P2 is excluded. Its denominator is `len(results)`: the stock collector includes every task directory, even those with missing summaries. Test-only submissions contribute check pass rates but not strict successes; generation metadata is not independent authentication. The paper's 26/47 best strict result belongs to its reported experiment, not this audit. [Report implementation](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/scripts/gen_report.py)
- **Availability and limits:** The repository is [Apache-2.0](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/LICENSE); third-party materials retain their own terms. The paper describes verified reference implementations, but the [complete pinned release tree](https://api.github.com/repos/areal-project/GameASG-Bench/git/trees/6c9c4e334bd166e924ed430f567ec78cb77feb9a?recursive=1) contains no HTML files, so do not describe reference games or generated HTML as released by this tree. The [Dockerfile](https://github.com/areal-project/GameASG-Bench/blob/6427cb6517ce11ff350ec45fcae17b67c5aec245/Dockerfile) pins agent CLI versions but not the base-image digest, apt/Chromium packages or `ws`; record those before reproduction. The sampled TDD also mentions `design-doc.md`, absent from that task's three-file release, a documentation inconsistency rather than an established runtime blocker.

**Editorial use:** Separate an explicit game-state observation contract from the implementation, and test action-to-outcome behavior rather than trusting self-reported state alone. Preserve per-check outcomes, applicable checks, missing tasks, generation records and evaluator errors. Public source availability and successful runner completion do not establish a playable game or reproduced paper result.

## 7. GBQA: keep defect discovery separate from generation and repair

Primary sources: [paper v1, April 3, 2026](https://arxiv.org/html/2604.02648v1), [paper-era repository snapshot `ca7e3fb`](https://github.com/camel-ai/GBQA/tree/ca7e3fb652a2e4826d0f14392a9a390522a1f1a7), and [later revision `500e5ea`](https://github.com/camel-ai/GBQA/tree/500e5ea252ee7afccc275b0e28fbd6de8c8f5dfc). The historical README uses the paper's exact title and matching research description; the author-associated [paper page](https://huggingface.co/papers/2604.02648) links this repository. These establish project linkage, not equivalence between the paper experiment and either inspected revision. Read-only source review; no game, model, container or evaluator was run.

- **Task boundary:** The paper evaluates autonomous bug discovery in 30 game environments containing 124 human-verified defects, not production of a new game or successful repair. Agents interact through backend APIs; exploration-only and specification/source-informed conditions are separate. A critic matches reported defects to annotations to compute recall. This does not establish visual QA, false-positive control or generated-game quality. [Paper §§3–5](https://arxiv.org/html/2604.02648v1)
- **Historical artifact boundary:** The March 29 snapshot includes the agent, prompts, evaluator and one Dark Castle environment with [three annotated bugs](https://github.com/camel-ai/GBQA/blob/ca7e3fb652a2e4826d0f14392a9a390522a1f1a7/hub/dark-castle/bugs/dark-castle.json). Its [complete tree](https://api.github.com/repos/camel-ai/GBQA/git/trees/ca7e3fb652a2e4826d0f14392a9a390522a1f1a7?recursive=1) does not contain the reported 30-game corpus or a LICENSE file. This is an inspectable paper-era example, not a verified paper release or a claim about every historical revision.
- **Later protocol boundary:** At June 25 revision `500e5ea`, the [README](https://github.com/camel-ai/GBQA/blob/500e5ea252ee7afccc275b0e28fbd6de8c8f5dfc/README.md) describes a broader software-QA framework with a selected bug hint and a binary reward for a complete report whose source pinpoint aligns with a golden patch. Its [tree](https://api.github.com/repos/camel-ai/GBQA/git/trees/500e5ea252ee7afccc275b0e28fbd6de8c8f5dfc?recursive=1) has three named Dark Castle target-task packages plus a template, not three distinct games. The [key-fragment manifest](https://github.com/camel-ai/GBQA/blob/500e5ea252ee7afccc275b0e28fbd6de8c8f5dfc/gbqa/tasks/dark-castle-key-fragment-combine/gbqa.yaml) specifies medium hinting, a separate upstream release and Daytona/Modal execution. These are not the paper's recall protocol; patch-shaped localization evidence is not proof of a repaired game. Runtime and verifier behavior were not independently tested.
- **Reuse boundary:** The later revision has an [Apache-2.0 LICENSE](https://github.com/camel-ai/GBQA/blob/500e5ea252ee7afccc275b0e28fbd6de8c8f5dfc/LICENSE). That observation does not establish rights for missing corpus content or separately fetched software/assets. Full paper-corpus reproduction remains unverified: obtain the designated revision, environment/annotation inventory and matching evaluation configuration before comparing results.

**Editorial use:** Record whether a QA task is open-ended discovery or hinted diagnosis, whether source code is visible, and whether the score measures defect recall, localization or actual repair. Keep these outcomes separate from game-generation acceptance. Neither an author-linked repository nor a historical commit alone establishes release completeness.

## Recommended integration and next acceptance gap

Integrate these as a focused evaluation-methods note before adding broad catalog entries. OpenGameEval and GameASG-Bench have inspected code/task surfaces with distinct hosted-service, reference-artifact and dependency limitations; the remaining studies warrant explicit paper/protocol or partial-artifact labels until their executable releases are established. Neither inspected release is a fully reproduced benchmark. GBQA adds inspectable historical/current QA examples without establishing its complete paper corpus. Five useful distinctions emerge:

1. Engine-state checks and visual judgment answer different questions.
2. Repair requires both fixing the intended defect and preserving existing behavior.
3. Agent play traces can guide development while a separate evaluator owns final scoring.
4. Build/load success is a prerequisite, not evidence of complete requirements.
5. Public paper, public task catalogue, public code and reproducible full benchmark are different availability states.

These are editorial synthesis, not new benchmark findings. No cross-study numerical ranking is justified: task families, engine versions, action spaces, attempt budgets, memory, model/judge choices, human calibration and release completeness differ. A proposed comparison manifest should include all of those fields plus failures/timeouts, artifacts and rights scope. No such manifest-driven experiment or fixture is implemented here.
