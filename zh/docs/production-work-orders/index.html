生产任务模板：交付物、恢复与验收

英文原文

Use these work-order templates to connect asset creation, import, build, testing, and delivery. Each template defines the inputs, expected artifacts, completion checks, failure handling, and evidence to collect when implementing it.

Common execution contract

Design acceptance: Tears of the Kingdom construction affordances links recognizable pieces, visible interaction exceptions and multiple viable solutions. F.E.A.R. behavior authoring, Left 4 Dead pacing controls and Valve playtesting evidence distinguish valid plans and policy traces from realized gameplay and human experience. Use them to define separate checks for behavior, pacing, and player understanding.

Each work order needs an isolated workspace, intended target platform, immutable input manifest, source and consuming-tool versions, selected operation/options, native diagnostics, output hashes and an explicit acceptance policy. Record documentation versions separately from installed versions.

Keep these states distinct: request accepted; native operation terminal; expected artifacts present; artifacts validated; project saved; fresh process reopened; target-runtime acceptance complete. Record accepted, quality failure, unsupported, infrastructure failure, timeout, cancelled or inconclusive separately. A timeout is not cancellation, a retry is not necessarily idempotent, and an existing file may belong to an earlier run. Cancellation and power-loss durability remain unknown unless a specific source establishes them.

The acceptance and recovery policies below are editorial proposals. Do not repair source assets, replace baselines, normalize audio, alter system network settings, upload packages or publish a build merely to make a check pass. Keep source inputs and failed artifacts. Tool licensing, fonts, media rights, SDK access and deployment authority need their own checks; this document grants none.

1. Export an authored asset, import it and audit dependencies

Related contracts: Portable-asset validation and composition validation; native import/save boundaries; Infinigen procedural export and resume.

Outcome: a named asset survives transfer and fresh reopen with the intended scale, orientation, references and target identity.

Documented surfaces. Maya 2026 file operations expose scene open/save, references and import/export. Standalone initialization is session-sensitive; the 2022 guide is not an installed-version assertion. Unity GetDependencies, checked as Unity 6000.6, returns asset references; recursive results include the roots, and referenced assets are not necessarily required in a build. Unreal AssetRegistry 5.6 dependency queries cover on-disk references. Waiting before full engine initialization can leave unloaded-plugin assets ungathered; is_loading_assets describes initial searching, not every gathering operation.

Proposed chain. Freeze the authoring scene, references, plugins and export options → write a candidate export to a new destination → import into a disposable target project → wait for the selected importer and dependency scan → inspect the asset and reference graph → save → reopen in a fresh consuming process. Use Unreal's coordinate system and unit defaults only for that target: left-handed, Z-up, X-forward and default centimeters do not define the source asset's units.

Completion and evidence. Require an asymmetric, known-size object and expected reference sentinels. Preserve source/export/import hashes, object mapping, direct versus transitive edges, disk versus dirty-editor scope and reopen observations. Dependency enumeration does not authorize deleting allegedly unused assets or prove packaged reachability.

Failure and recovery. Missing plugin, unknown root, incomplete scan, changed unit basis or stale output blocks promotion. After an authorized save, Unreal can rescan specified modified filenames; rerun against the new disk snapshot. Reimport is not assumed idempotent: reconcile newly created objects before retrying. Exporter atomicity and arbitrary import rollback are unverified.

Unimplemented fixture: move one referenced texture, leave one scene edit unsaved, interrupt import, and compare the original and fresh-process manifests. The project-specific importer completion observer and save/reopen driver still need implementation.

For USD packages, dependency-discovery and package-membership boundaries add a selected-version check before declaring portable closure; a discovery or package Boolean alone is insufficient.

Versioned asset publication and consuming-scene ownership

For a Blender → AYON → Unreal Editor handoff, track the published representation, its files, and the actors that consume it.

Evidence and prerequisites

Independently pinned development snapshots: AYON Blender addon 1.1.11+dev at 1bae7f10b014761039e1412a89c03fc7a7cc0c2d; AYON Unreal addon 0.4.0+dev at 43b4a800a52289dd0bae19b1345889a835766bb7; AYON Core addon 1.10.1+dev at 136b43c6ba4b6e01cb0b97e0b31fb4df92e46409. These are not an installed or demonstrated compatible bundle. The Blender addon declares Core ≥1.9.9; the Unreal addon ≥1.8.0; this Core snapshot requires AYON Server ≥1.14.0,<2.0.0 and Launcher ≥1.5.4. Those declarations do not establish compatible Blender/Unreal executable versions.

The Unreal setup guide requires the Unreal integration plugin and Qt bindings; it describes source/compiled plugin paths and automatic building when no usable plugin exists. The artist guide launches Unreal through AYON. Runtime prerequisites include configured server/project access, a selected addon bundle, storage roots and readable published files. AYON permissions do not confer filesystem permissions.

The inspected Blender, Unreal and Core repositories carry Apache-2.0 licenses. The current licensing guide separately identifies the server as Functional Source License and some features/addons as licensed. This does not license source assets, grant engine access or establish service entitlement.

Authored scene → validation → candidate FBX

CreateModel creates a model publish group and can parent selected objects into it. ValidateObjectIsInObjectMode rejects included objects outside Object Mode; optional ValidateMeshHasUvs checks for UV-layer existence, not UV quality. The documented recovery selects invalid objects, changes the scene, resets Publisher and reruns validation.

Settings enable the optional UV check but disable ExtractFBX by default. A model publish therefore does not automatically include FBX. SaveCurrentSceneBlender saves the current workfile before extraction and rejects a filename change since collection.

When enabled, ExtractFBX exports selected instance objects to a staging file and registers an fbx representation with filename, extension and staging directory. It temporarily creates missing materials, then removes them after export; this cleanup is not protected by a surrounding finally. An export exception therefore warrants checking source-scene state before retry. Texture packing documented for ExtractBlend does not establish equivalent FBX dependency packaging.

Candidate → versioned publication

Core integration prepares product/version entities, commits them before transferring files, then finalizes representation records after transfers. Consequently, a database version alone does not establish available, complete artifacts.

Its error handling attempts file rollback and explicitly leaves database rollback unresolved. FileTransaction backs up existing destinations, copies files and later removes backups; it warns that ordinary filesystems are not transactional and created directories remain. Rollback itself can fail. No distributed atomicity, crash durability or cancellation guarantee follows.

ValidateVersion rejects versions no higher than the collected latest version when active, but disables itself without a matching host profile. Preserve effective settings; do not call versioned publication universally immutable or retry-idempotent. Project Anatomy separates version directories and warns against representation-specific subdirectories that break shared resource paths.

Publication → Unreal assets → scene update

StaticMeshFBXLoader accepts model/staticMesh FBX representations. Its active import path uses Interchange, then creates an AYON container. The separate get_task helper is not called there: its mesh-combination/Nanite settings are not evidence of effective Interchange options.

Load/update resolve a representation path, choose a unique destination or reuse a layout asset directory, imprint representation/version IDs and save enumerated assets. The import return value is not checked in this helper. Container existence and requested saves are intermediate evidence, not proof of successful geometry import or fresh reopen.

The static-mesh update method contains no retargeting of already placed actors. The separate LayoutLoader update calls destroy_actor for every enumerated actor after requesting the layout level load, then rebuilds and requests saves; the load/delete/save results are not checked. That ownership boundary matters for hand-authored additions.

Composition remains unestablished: this Blender layout extractor writes reference/reference_fbx/reference_abc; this Unreal layout reader selects representation and version, otherwise skipping elements. The inherited preprocessing also requires representation, so it does not establish a conversion from those Blender fields. This is a mismatch between independently inspected snapshots, not evidence that an officially supported bundle is broken. The Blender artist guide calls Layout legacy and recommends blendScene; that does not establish an Unreal blendScene replacement path.

Proposed acceptance and recovery

Suggested check: freeze the effective bundle, host builds, publish settings, source workfile and dependencies. Publish one asymmetric prop; reconcile product/version/representation IDs with actual files and independent hashes. Load into a disposable Unreal project; verify geometry, material dependencies and container identity. Publish a changed version, update, then independently inspect placed-actor references and fresh-process reopen.

After failure, retain staging files and diagnostics; reconcile server records, destinations/backups and authoring-scene changes before retry. An empty import, new container or green publisher report cannot substitute for this evidence. Layout replacement needs separate ownership and schema checks; preserve the previous consuming workfile. End-to-end rollback, actor preservation and compatible bundle behavior remain unverified.

2. Transfer a rig and test animation behavior

Related contracts: Animation sampling and compression, including joint identity, partial output and final decoded motion. For engine-side culling, evaluation phase, events and movement ownership, see runtime animation observation gates.

For the selected Godot 4.4 source path, normalized-key and target-scale acceptance separates imported keys, receiving-skeleton samples, extracted deltas and controller travel; reuse the runtime observation gates for general playback and movement ownership.

Outcome: a skinned character preserves its rest pose and intended motion, including root transforms and contacts.

Documented surfaces. Unity 6000.0 bind poses correspond by index to bones and use inverse base-pose transforms in the illustrated mesh/root setup. Unreal Motion Matching searches a Pose Search database using configured features. Ubisoft's Learned Motion Matching explanation, July 30, 2020 explains that supplied motion limits behavior coverage: separate walking and drinking examples do not automatically supply walking while drinking. Foot locking, IK and blending remain integration concerns. This historical account is not a public SDK contract.

Proposed chain. Record hierarchy, bind matrices, bone indices, weights, coordinate basis and clip sample rate → transfer a candidate mesh and clips → inspect rest pose under both identity and nonidentity root transforms → sample designated clips and transitions → record contacts, root trajectory and behavior coverage → save and reopen → repeat the same samples.

Completion and evidence. File import and a populated animation database are intermediate results. Acceptance requires project-declared tolerances for joint positions, root displacement, contact sliding and transition discontinuity. Preserve source clip timing, engine sampling time, retarget settings and camera-independent geometry observations alongside video. A visually similar frame does not establish matching weights or temporal behavior.

Failure and recovery. Bone permutation, missing clip, transform mismatch or unsupported behavior blocks promotion. Correct the mapping or source export, then create a new candidate and rerun; do not automatically relabel unmatched bones or treat a failed retarget as a partial success. Preserve the accepted source rig. Native rollback, deterministic cross-platform sampling and cancellation behavior are unverified.

Unimplemented fixture: a small asymmetric skeleton with one weighted joint, a translated root, a planted-foot interval and a deliberately absent behavior combination. Requires a rig-inspection adapter and authoritative contact/trajectory evaluator; no automatic artistic-quality judgment is supplied.

3. Export textures without losing channels or color meaning

Related contracts: Material, color and texture contracts; KTX policy, packing and target checks; lighting bake persistence and scene association.

Outcome: downstream textures preserve required channels/subimages and explicitly declared color interpretation.

Documented surfaces. Substance Painter remote control drives a running authoring application; it does not establish a headless bake/export acceptance contract. The OpenImageIO oiiotool manual, displayed as 3.3.0 when checked, documents --info, --colorconvert, --diff and --absdiff. Most commands normally operate on the first subimage and discard others; -a and subimage selection modifiers control broader processing. Named color transforms depend on the selected configuration. This is a rolling manual, not a pinned binary.

Proposed chain. Freeze Painter project, export preset and destination manifest → export candidate maps → inventory dimensions, channels, subimages, data types and alpha convention → classify color versus data maps → apply only declared transforms → compare candidate values and rendered material response → import, save and reopen. Preserve an untouched original and a separately identified derivative.

Completion and evidence. Require every expected map and subimage, plus the exact color configuration/hash and source/destination space names. A numerical diff is diagnostic, not proof of equivalent material appearance. Color conversion cannot be inferred from a filename. Normals, roughness, masks and other data channels require an explicit policy rather than blanket RGB conversion.

Failure and recovery. Missing secondary subimages, unknown color space, clipped data or wrong channel packing fails acceptance. Regenerate into a fresh directory with corrected selection/preset; do not overwrite the source or silently adopt a new baseline. A successful remote script return does not establish completed export, durable save or target-renderer compatibility. Export cancellation and interrupted-file atomicity remain unverified.

Unimplemented fixture: a multipart image containing color and normal data, a known ramp, an alpha edge and a deliberately omitted subimage. Require independent file inventory and target-material observation, not just the authoring preview.

4. Measure loudness, peaks, silence and loop boundaries

Production experience: Prototype 2 contextual mix acceptance and Overwatch listener-dependent priority explain why artifact measurements need gameplay-context and perceptual review; neither case supplies a tested external adapter.

Related contracts: Audio middleware readiness and ownership; runtime audio observation and capture integrity establishes tap/coverage provenance before artifact measurement. Event completion remains separate.

Outcome: a complete audio artifact has reproducible measurements and a separately reviewed loop seam.

Documented surfaces. The rolling FFmpeg filter manual documents ebur128 M/S/I/LRA measurements; true-peak mode oversamples and requires libswresample. astats supplies channel/overall statistics; Peak_count counts extrema occasions, not clipped samples. silencedetect announces silence after a duration threshold; end/duration metadata appears after silence. mono=1 separates channels. For mono input intended for stereo playback, the manual calls for dualmono compensation; its panlaw setting also affects the measurement. No installed FFmpeg configuration was checked.

Proposed chain. Hash the original → identify selected stream, decoded sample format/rate and channels → run separate measurement passes using ebur128=peak=true, astats=metadata=1:reset=0 and explicitly configured silencedetect → reconcile complete decoded coverage → compare to project thresholds → render at least two intended loop repetitions through the target import/codec path → inspect and audition the wrap.

Completion and evidence. Retain full command, binary/build configuration, stderr/metadata, sample count and actual analyzed range. Success requires the expected metrics and complete span, not merely exit code zero. Define clipping criteria for the sample representation and intended signal; never substitute Peak_count for a clipped-sample count. Trailing silence without a later frame needs explicit EOF reconciliation. Keep the noise threshold and minimum silence duration visible. Record the intended mono/stereo playback interpretation and dualmono/panlaw choices with the loudness result.

Failure and recovery. Decoder errors, truncated scans and unsupported true-peak processing are incomplete outcomes. Retry unchanged input/settings into isolated report files. Normalization, limiting, silence removal and crossfading are separate edits; if authorized, preserve derivative lineage and remeasure. Equal boundary samples alone do not establish musical continuity or codec-safe looping.

Unimplemented fixture: known silence on one channel, an intentional transient, terminal silence and a loop with a known discontinuity. Listening and project-specific loudness/peak limits remain necessary; no platform certification or universal game-mix target is claimed.

5. Verify audio/video timing and spatial playback

Related contracts: Native audio scheduling and ownership.

Outcome: observed sound onset and visual events align within declared tolerances, with the intended listener and routing.

Documented surfaces. ffprobe exposes stream, packet and frame sections. Interval seeking is inexact; relative duration is measured from the actual seek point. FFmpeg ashowinfo reports audio PTS in input-timebase units, seconds, sample rate and sample count, while asetrate changes speed/pitch without changing PCM. Unity 6000.0 PlayScheduled uses the absolute DSP timeline; past times start as soon as possible, with different late-time behavior for AudioRandomContainer. dspTime is sample-based; its example discusses pause/suspension. AudioListener specifies one listener per scene; spatialBlend ranges from 2D to 3D and applies 3D processing after stereo panning.

Proposed chain. Record clip/source/listener identities and device/mixer setup → schedule a marked sound with preparation lead time → capture audio plus a visible marker → associate decoded samples and visual-frame timestamps with a common observation clock → repeat markers near start, middle and end → exercise pause/resume and a scene/listener change → inspect spatial fixtures left/right/front/back and at selected distances.

Completion and evidence. Preserve rational time bases, origins, edit offsets, sample counts and capture uncertainty. Scheduling receipt is not audible onset. Equal durations do not prove synchronization; distinguish offset from drift. Persist the capture and runtime event log, not just a requested timestamp. Listener transforms alone do not establish HRTF quality, occlusion, routing or accessibility. Preserve event refusal, API results, pause and Core-versus-Studio virtualization separately; native PLAYING/STOPPED observations are not audible-success verdicts.

Failure and recovery. Missing PTS stays unknown rather than zero. Missing/duplicate listener, unexpected routing or dropped markers leaves acceptance incomplete. Reconcile episode/source state before retrying a timed-out schedule to avoid duplicate sounds. A fresh session needs a fresh DSP schedule; saved numeric timestamps are not a replay contract. Device latency, cancellation and rollback are unverified.

Unimplemented fixture: late schedule, pause/resume, long-run drift, channel swap and additive-scene listener replacement. Requires a clock-alignment collector and manual perceptual review. Do not silently retime audio to hide a failing observation.

6. Compile localization, shape text and inspect accessible UI

Production experience: Mass Effect 2 revision/context gates, Forza co-development and learnable cues, and Far Cry New Dawn dependency/testing limits complement the technical chain below; these historical accounts do not establish a tested adapter or universal player outcome.

Related contracts: Font artifact validation and native GUI evidence limits.

Outcome: reviewed translations compile and display with the intended glyphs, layout and accessible interaction. For native Godot UI, first check semantic activation, deferred actions and platform boundaries; an inspector-only Auto-mode run can lack active semantic updates.

Documented surfaces. GNU gettext documents msgfmt --check, including format/header/domain checks. Marked format mismatches block MO generation; --use-fuzzy can include unreviewed entries. HarfBuzz selects and positions glyphs; it is not a complete layout system. FreeType provides font access and glyph images rather than higher-level layout. MSDF Atlas Generator defaults to ASCII unless overridden and requires linear sampling of atlas channels. These upstream pages do not license the chosen fonts.

Proposed chain. Freeze message extraction and format flags → review translations/fuzzy status → compile a fresh candidate MO → build an explicit locale/glyph set → shape representative text using the intended font/fallback stack → render real screens → test keyboard/assistive paths and localized overflow → package and reopen under each target locale.

Completion and evidence. Compilation is separate from translation coverage, shaping, line breaking and accessibility. Retain locale/domain, catalog hash, font versions/licenses, glyph-set definition and rendering configuration. For browser UI, Playwright screenshots wait for stable captures but masks/styles/animation controls can change evidence. axe-core 4.10.3 API at checked commit distinguishes violations, passes, incomplete and inapplicable; restricted result types may omit node detail. DOM scans do not certify game canvases. For live locale switching, distinguish string delivery, rendered layout and native accessibility; a successful refresh request is not completion of all three.

Failure and recovery. Fix extraction format classification at source; do not remove PO flags or auto-clear fuzzy status to pass. Preserve incomplete/manual findings. Retry changed locale/UI state as a new observation, retaining exclusions and options. Never update screenshot baselines automatically. Catalog write atomicity and complete fallback coverage remain unverified.

Unimplemented fixture: plural forms, mixed-direction text, combining marks, missing glyphs, long labels, captions and a hidden focus target. Xbox Accessibility Guidelines inform manual review; they are not legal certification. Requires project-specific locale switching and disabled-player testing.

7. Exercise multiplayer transport under impairment

Load scope: VALORANT platform workload illustrates why concurrency, duration, scenario mix, mocked components and acceptance bounds must travel together; transport impairment and real-gameplay soak remain separate experiments.

Failure evidence: Bungie distributed crash collection and Valve dump/build provenance distinguish incident linkage, capture completeness and diagnostic eligibility. These historical methods do not establish a tested soak workload or authorize disruptive collection.

Related contracts: Protocol-scoped input/impairment and server state/transaction boundaries.

Outcome: a bounded multiplayer scenario retains authoritative gameplay invariants under declared latency, loss and reconnect conditions.

Documented surfaces. GameNetworkingSockets supplies reliable/unreliable messages, latency/loss simulation and statistics; it does not supply entity serialization or delta encoding. Own signaling and service-specific access may be required. The rolling native interface header documents send failures including invalid state, closed connection and queue limits. RunCallbacks dispatches queued callbacks when not using Steam's dispatch mechanism. Callback user data reflects when the callback was queued. Closing with linger attempts to flush remaining data; without linger, reliable data is not flushed. Closing a listen socket closes accepted connections ungracefully. These are source contracts, not a tested library revision or durable-delivery guarantee.

Proposed chain. Launch isolated server/client roles → record build/protocol/session identities → establish a clean baseline scenario → apply declared transport-local impairment → record send outcomes, callbacks and authoritative state transitions → remove impairment → reconnect/reconcile under a new connection identity → verify final application state → archive logs and terminate owned processes.

Completion and evidence. A connection or successful enqueue is not game-state commitment. Require application-level operation IDs and acknowledgements where the game needs them, server-authoritative invariants and bounded queue/timeout policy. Persist causal event logs and observed timing, including rejected actions. Durable gameplay persistence requires a separate project storage contract; transport close alone establishes none.

Failure and recovery. Queue saturation, stale callback identity, timeout and protocol mismatch are distinct. Reconcile unknown actions before application retries; transport reliability does not make purchases, rewards or repeated commands idempotent. Do not change host firewall/network policy or assume Steam relay entitlement. Roll back only fixture-owned impairment settings and verify cleanup. Network-seed reproducibility is not established here.

Unimplemented fixture: duplicate application request, delayed callback after reconnect, lost final acknowledgement and forced close during queued traffic. Requires a game-specific state driver, impairment configuration adapter and observability collector. Transport measurements alone cannot certify cheating resistance or production scalability.

8. Build a release-bound content update and reconstruct its patch

Related contracts: Shipped-build inspection and comparison; allocation lifetime and retained-resource evidence separates runtime ownership from built size and reference-count summaries.

Outcome: a candidate update corresponds to the intended released baseline and reconstructs independently verified artifacts.

Documented surfaces. Addressables 1.21 BuildContentUpdate uses the specified content-state cache version and returns a build result. Its update settings can fall back from unavailable remote state to an existing local cached file; change group Update Restriction during full builds. Modified-entry gathering targets static Addressable dependencies. butler offline patching requires staging, resumes an interrupted identical apply command, and otherwise applies in place unless another output directory is selected. Signature checking is optional; in-place unchanged files are not all checked. Independent verify detects hash mismatches; healing requires a pristine source.

Proposed chain. Match release/platform to a hashed content-state file → snapshot group/profile settings → gather changes → build to candidate output → inspect native error/result and artifact manifest → produce a patch from an immutable baseline → apply into separate scratch output using a dedicated checkpoint → verify the reconstructed build against the expected signature → install into an isolated target and exercise content loading → archive release lineage.

Completion and evidence. Result-object existence, patch completion and content activation are different gates. Preserve baseline, state-cache identity, patch/signature hashes, changed dependencies and complete reconstruction verification. A cache path is not evidence that the cache belongs to this release. No upload or release promotion is included.

Failure and recovery. Wrong fallback state or changed update policy stops incremental retry; select a full-build workflow explicitly. Resume butler only for identical inputs/command/checkpoint identity. Preserve failed reconstruction. Healing is a separate authorized mutation; do not repair a production installation automatically. Atomic promotion, concurrent patch writers and power-loss durability remain unverified.

Unimplemented fixture: unavailable remote state with stale local cache; interrupted patch; corrupted unchanged baseline file; wrong-platform content. Requires isolated installer and runtime content-load checks. A complete build still needs platform certification and distribution approval.

Godot 4.4 content patches: mounting is not dependency activation

Check both pack contents and the resources visible to the consuming process: a correct pack can still leave cached resources in use. References below target Godot's 4.4 documentation branch and 4.4-stable source at 4c311cbee68c0b66ff8ebb8b0defdd9979dd2a41; verify cache behavior for other releases separately.

Documented boundaries. ProjectSettings.load_resource_pack mounts PCK/ZIP content into res:// and returns a boolean. Same-path entries replace existing entries by default; replace_files=false disables that replacement. The 4.4 reference cautions that DirAccess does not show changes to res:// made by this operation. A directory listing is therefore not the acceptance oracle for newly mounted content.

ResourceLoader cache modes establish a separate boundary: default CACHE_MODE_REUSE reuses cached resources and external dependencies. CACHE_MODE_IGNORE bypasses the main resource/subresource cache but still loads external dependencies with reuse; CACHE_MODE_IGNORE_DEEP propagates the bypass through dependencies. Replacement modes may refresh existing instances when types match, or recreate them otherwise. exists() can also report true for an unsaved resource whose path was taken over in cache. Inference: mount success, resource existence and reloading only the top-level object cannot alone prove that an entire patch dependency graph is active.

Fixed-source corroboration. At that commit, the text-resource loader selects external-dependency reuse for ordinary IGNORE/REUSE/REPLACE and propagates the deep modes; the resource loader returns an existing cached resource for REUSE. This corroborates the cache distinction, not every resource-format plugin or the directory-listing warning.

The 4.4 pack guide also includes scripts among pack contents and documents an additional C# assembly-loading step before mounting a C# mod. Treat a pack as potentially executable content, not merely an inert texture archive; an approved data-pack mount does not establish that its separate assembly was delivered or loaded. This is not a claim that the engine authenticates or sandboxes a mod.

Proposed acceptance. Preserve engine/template identity, baseline and ordered pack hashes, expected path collisions, replacement policy and resource-loading/cache policy. Use a project-owned manifest of expected resource paths, types, dependency identities and observable version markers. Record mount results separately from the resources actually returned and the gameplay/rendered result. Validate a fresh process that mounts the intended pack set before loading fixture resources; if hot updates are promised, validate the warm process independently. Do not silently switch to deep replacement in a live game: existing object identity and side effects require their own contract.

Unimplemented fixtures: (1) cache a scene and its external material, mount a patch changing both, then compare default, top-level-ignore and deep-ignore loads against a fresh-process reference; (2) mount two packs with a deliberate path collision in both orders and with replacement disabled; (3) add a new known resource and compare manifest-directed loading with directory-list observations; (4) omit a required dependency or C# assembly and require a distinct activation failure rather than a mount-only pass. Preserve native errors and returned object/dependency markers, not merely screenshots or booleans.

Failure/recovery limits. Quarantine a mismatching candidate and restart the isolated fixture from its immutable baseline. The inspected contracts do not establish safe unmount/rollback, concurrent hot replacement, crash durability, signature trust, cross-version pack compatibility or bit-identical exports. None is claimed by this proposal.

9. Compile shader permutations and qualify first-use behavior

Related contracts: Capture and shader diagnostic completion.

Outcome: required shader artifacts compile for declared targets and first-use behavior is measured independently of compiler success.

Documented surfaces. The DXC API guide, checked as a wiki revision dated May 5, 2023, distinguishes API-call success from IDxcResult::GetStatus. Diagnostics can include warnings as well as errors; expected object output must be retrieved separately. Debug PDBs are external by default and -Vd disables validation. Exact installed flag compatibility is unknown. Epic's February 4, 2025 PSO precaching account explains content/permutation coverage and driver-cache effects; its UE5.5 gaps must not be presented as current universal engine behavior.

Proposed chain. Freeze source/include graph, defines, entry points, HLSL version and target profiles → compile each required permutation with validation enabled → inspect API and compile status separately → retain object/debug/hash outputs → integrate into the intended engine build → exercise first-use scenarios in isolated cold-cache and warm-cache conditions → compare timing and rendered results → save the artifact/measurement manifest.

Completion and evidence. Every required permutation needs its own terminal outcome and fresh output. Preserve include resolution, compiler identity, target device/driver/RHI, quality preset and cache condition. Compiler success is not PSO creation, rendering correctness or hitch-free traversal. Driver-cache state is an experimental condition, not a property of the source hash.

Failure and recovery. Missing include, compile error, absent output and target incompatibility block promotion. Correct inputs and write new candidate outputs; never reuse an earlier success blob. Collect native errors before resetting. Do not erase a user's shared caches to create a cold run; provision an isolated fixture. No cross-driver cache portability or transactional compiler-output guarantee is established.

Unimplemented fixture: malformed include, valid but wrong target profile, material/skin swap and newly streamed object during traversal. Requires shader/PSO telemetry correlated with frame artifacts and a declared timing budget; a warm rerun cannot replace a failed cold-run result.

Complete sample integration examples

These source-backed examples connect assets, scenes, interactions, builds and playtest surfaces inside one project. They are complementary to the nine proposed chains above. Upstream code and tests are available at the cited revisions, but their presence is not a GameMap execution result.

Unity Boss Room: a source-backed multiplayer production chain

Scope. The official sample at commit 1299ba4fc97d83b634e7d32a86c438ba668d7f9c (2025-10-23), inspected 2026-10-18, provides a concrete project joining authored assets, scene flow, interactions, builds and tests. Its README describes an eight-player, server-authoritative cooperative RPG with latency-masking animation. Those are upstream design statements, not a GameMap playtest or a measured latency guarantee.

Godot 3D Platformer: an inspectable scene-to-build route

Scope. Reviewed 2026-10-18, source-only, at official demo commit 52e30044658448149b04e8f69b475eebbfbd8f6e, from the 4.3 branch. Project configuration selects game.tscn and declares 4.3; the sample README identifies GDScript and Forward+. This is a historical interactive-scene baseline, not a current compatibility or completed-game claim: the 4.3 documentation labels that engine version unsupported. No engine or game was installed or run; binary assets were not downloaded, and import/export was not attempted.

Assets → scene. The player GLB import sidecar records source/derived paths, named skins, generated mesh LODs and 30-fps animation import; the enemy sidecar records corresponding settings. The tile material binds separate albedo and roughness textures. The main scene combines stage, player, coins and enemies. Stage resources include GridMap, sky, lighting and reflection probes; the tile library connects meshes and collision shapes. The player scene connects a CharacterBody3D capsule, imported character, camera, AnimationTree, labels, touch controls and sounds. Import settings and resource references establish intended assembly; they do not prove dependency closure, successful import or visual correctness.

Scene → interaction. Player code implements camera-relative movement, shorter jumps on early release, press-edge shooting and animation blending. The input/physics configuration sets movement, jump, shoot and reset actions with 120 physics ticks per second. Coin code sets taken and increments the player count once; its take animation hides the coin and triggers particles/audio without deleting its node. Node disappearance would therefore be an incorrect collection assertion. Enemy contact handling marks dying, disables repeat hits from that bullet and queues animations; a later animation method track calls _die, which queues deletion. Contact, visible feedback and terminal removal are separate observations.

Control and reset boundaries. The Backward touch button emits move_backwards, but the input map and controller use move_back: a verified source mismatch, not a reproduced mobile failure. Keyboard, gamepad and touch need independent checks. Respawn logic sets position to initial_position and velocity to zero after reset input or falling, before continuing that physics update; subsequent gravity/input processing can change velocity, while coin/world state is retained. Respawn is not a clean episode reset. No campaign-completion controller was found in the inspected sample scripts/scenes; a bounded route needs an explicitly authored success condition.

Interaction → export. Committed presets target Linux/X11 and Android, but their presence is not a successful build. Linux/X11 spelling alone is not a demonstrated defect: Godot 4.3-stable source maps it to Linux unless DISABLE_DEPRECATED is defined; remaining option compatibility was not exhaustively checked. The 4.3 CLI reference requires an editor build, selected preset, matching template and existing output directory. Import completion is distinct from gameplay; a data-only PCK is distinct from executable-plus-data delivery. No add-on, C# or GDExtension dependency was declared in the inspected subtree; engine/templates, graphics support and target tooling remain prerequisites. Android signing and SDK setup were not verified.

Export → testing. No gameplay harness was found under the sample. This revision’s only repository workflow, Static Checks, runs text-formatting checks, not Godot or gameplay assertions. The root README’s hosted-demo link is mutable and was not played. Its availability cannot validate the pinned source. Godot 4.3 Web documentation requires Compatibility/WebGL 2.0 rather than Forward+ and identifies web audio/threading restrictions. A browser port therefore needs its own visual, input and audio acceptance.

Proposed route, unimplemented and unexecuted. Remaining implementation work

The chains need project drivers, native terminal observers, bounded process ownership, artifact collectors and independent acceptance evaluators. Authoring-format equivalence, console SDK/certification, codec/device latency, translation quality, accessible gameplay and application-level multiplayer durability remain project-specific. Historical industrial lessons help select failure cases; they do not expose private studio tooling or reproduce studio performance.

Retain source review dates, document versions and exact links in future implementations. Recheck rolling manuals and provider licenses before deployment. The proposed fixtures above have no run IDs, measured tolerances, passed checks or runtime compatibility claims because none has been executed.
