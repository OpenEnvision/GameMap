2D / 3D 游戏开发 AI 研究

英文原文

Explore systems for generating game rules, constructing playable projects, editing scenes, and evaluating the results. The sections below distinguish their outputs and the engine feedback each workflow uses.

For additional project sources, see the repository research.

Categories and evidence

  • Development agents / frameworks take requirements or a project and produce code, scenes, rules, or assets. Playable prototypes, local project changes, and complete games are different outcomes.
  • Skills provide workflows, references, and scripts for general agents. They are not trained models and do not guarantee independent execution.
  • MCP / CLI connects editors, runtimes, and asset tools to agents, providing execution and feedback interfaces. The existence of a tool does not establish the correctness of its outputs.
  • Development benchmarks include GameDevBench and GameEngineBench for project modifications. GameXpert-Bench adds creation, repair, and iterative improvement. GameGen-Verifier studies functional verification of generated games.
  • Related evaluations include CADBench for 3D modeling. Card game self-play can validate rules, but win rate measures gameplay ability and cannot substitute for development quality.
  • World models that predict action-conditioned video produce a different artifact from explicit engine projects. Kling's GameFactory is separate from OpenDCAI's GameFactory-3A. Video2Game produces explicitly reconstructed environments and belongs to the 3D reconstruction route.
  • Procedural backends such as Infinigen do not use an LLM to generate geometry. Infinigen is included because it can supply controllable scenes and synthetic data to AI game development workflows.

  • MarioGPT: language conditions become character-grid levels. play() and run_astar() launch simulation; the inspected wrapper returns no structured playability verdict.   • Agent Sprite Forge: a skill and deterministic asset-processing chain, with code marked MIT. Generation depends on external image or video capabilities. Record the provider route, version, reference image, frame order, anchors, and export checks.

Author results: separate metric populations

Paper v3 trains on 37 path-annotated levels. Playability uses 250 generated levels, each tested five times with Baumgarten's A* controller because performance depends on compute. It reports 88.4% completed levels; only one successful level needed a retry. This is not a per-attempt success rate or human difficulty assessment.

Path MAE averages five runs, comparing vertical coordinates only at horizontal positions visited by both trajectories: 1.15 tiles for playable levels, 4.56 for failures, 1.56 overall. Predicted paths can imply excessive airtime or leave the level while the controller is trapped near spawn. A low overlap-conditioned error does not certify the unvisited remainder.

Prompt adherence is a separate 1,000-sample test: pipes 81%, enemies 68%, blocks 92%, elevation 76%. These are per-feature scores, not joint constraint-and-playability success. Novelty search uses smoothed predicted paths, not observed controller traces; 78% coordinate coverage after 300 archive additions is a diversity measurement. Neither that visualization nor archive coverage proves controller solvability, visual originality or broad human preference. Paper §§3–4

Source-inspected contracts

  1. Returned prompt is a measurement-derived description. SampleOutput.create assigns prompter(level_tensor)[0]; it does not retain the original request. The sampler separately consumes the requested prompts to produce conditioning. Save the input request independently before comparing intent with output. Calling the returned description evidence that the request was followed would lose the disagreement being tested. returned description, 35–80, conditioning, 181–223

  2. Count labels are implementation-specific bins, not literal guarantees. The helper counts E and B characters as enemies, literal <> occurrences as pipes, and X/S/?/Q as blocks in row-concatenated text without separators. Elevation inspects only X, <, > in its first six rows. Its default configuration uses np.digitize(..., right=True) with enemy thresholds [1,3,7] and pipe thresholds [0,2,5]. Consequently, by source deduction, one counted enemy receives the “no” label, and exactly five pipes receive “some”; “many” starts above five. Custom statistics and use_raw_counts can change this behavior. Paper §4.4 instead calls five pipes “many”; the inspected default is not established as the paper configuration. This was not executed. Preserve raw counts, grid width and explicit boundary semantics instead of treating the generated label as a literal zero/count assertion. prompter.py, 15–19, 46–109, NumPy interval semantics

  3. run_astar() is a launcher, not a structured acceptance API. It calls Simulator.astar, which writes a temporary level, launches java -jar PlayAstar.jar, and discards the CompletedProcess stored in _. It captures stdout but never parses or returns it, does not check the process status, set a timeout or return win/loss/trace information, and exposes only a rendering toggle. play() is similarly an interactive launch. Normal Python return therefore supplies no verified completion verdict. A process-launch exception can propagate; the method does not implement the paper's five-run protocol. sampler.py, 107–121, simulator.py, 36–63

  4. Level artifact and preview have distinct failure surfaces. Sampling trims a partial trailing 14-token column before decoding. The renderer prints a diagnostic and substitutes background for an unknown character, so the preview alone can conceal a token/representation problem. Saving writes the grid as newline-separated text; it does not persist request, model revision or a playability result. Preserve decoded text and token identities alongside any preview. sampler.py, 81–112, utils.py, 13–37, 50–64, 116–128

GAVEL: rule-design search and verdict boundaries

Checked 2026-10-18. Read-only inspection of author source at 1a849c3ba00c3ecb1194c202451a617ef0556b60 (2024-10-30), paper v2 (2024-12-03) and artifact listings. v1 is dated 2024-07-12 and is a distinct publication snapshot. No installation, model inference, game/JAR/class execution, archive deserialization or reproduction. The source snapshot is not established as the exact implementation that generated the paper's results. Python invokes bundled bin classes; correspondence between inspected Java source and those class files remains unverified.

Author study, kept separate from inspected implementation

Paper v2 describes CodeLlama-13B fill-in-the-middle mutation of Ludii rules: 574 fine-tuning games, 14 held-out search seeds and 49,968 training tuples. PCA maps 510 concepts to a 40×40 archive, fitted on the complete, pre-filtering Ludii corpus. Three runs each use 500 steps and nine proposals per step. Its six-metric harmonic mean includes coverage; completion means reaching an end state. Novel-cell improvements over baselines are not statistically significant with three runs. Expert screening is preliminary; broad human validation remains future work. Sections 3–8

The 14 seeds are excluded from task-specific fine-tuning, then directly optimized during search. They are not an untouched final evaluation set. This does not establish foundation-model decontamination or human preference validity. Paper §§4,7–8

Source-inspected candidate and search contract

  • Representation and mutation. ArchiveGame retains the complete rule string, scalar fitness, metric dictionary, ancestor lineage, original game name, generation and epoch. The mutator selects a balanced parenthetical region, excluding the outermost whole-game expression, conditions on its prefix/suffix, and inserts generated text. It requests up to 512 new tokens and strips newlines. Grammar-enforced mutation is an advertised enum/CLI option whose implementation raises NotImplementedError. “Recombination” here should not imply a verified two-parent crossover operator. config.py, mutators.py, 80–154
  • Sampling differs from the paper's terse description. Each selected elite has one mutation location chosen; num_return_sequences generates the configured number of alternatives at that location. The saved main configuration selects three elites and three alternatives each. mutators.py, evolution.py, 262–289, 440–449, run_args.json
  • Admission is not a quality pass. Archive insertion excludes fitness −3 and NaN, but can retain −2 unplayable or −1 uninteresting entries in empty cells. Positive-quality occupancy must therefore be reported separately from total occupancy. The PCA archive loads a cached model and bins compiled concepts; novelty is representation- and reference-population-relative. archives.py, 96–124, 170–219
  • Novelty population. The inspected baseline comparison constructs occupied reference cells from the published model dataset's train ∪ val splits, then scores final archive entries against that set. It does not load every original Ludii game for this comparison. Its QD calculation adds fitness + 2 across retained entries, so −1 entries contribute to QD although they fail the quality gate. Do not translate QD or novel-cell counts into a proportion of enjoyable or globally novel games. compare_against_pure_generation.py, 41–75, 112–152

Compile, playable and sampled-quality gates

The Python two-step evaluator first requests 100 Random-agent trials with a 500-turn setting. It rejects random-play balance below 0.5 or decision-move fraction below 0.5, then requests the selected AI evaluation. Main saved arguments specify UCT, ten trials, 0.25 seconds thinking time and max_turns=50. These populations should remain distinct from the separate UCT-versus-Random skill sample. java_api.py, 169–241, run_args.json

The Java standard endpoint returns −1 if compilation produces no game. Evaluation exceptions, an error report, or mean duration below two return −2. Thus “unplayable” is broader than absence of legal moves. The Python fitness layer further rejects completion below 0.2, mean turns below three, decision moves below 0.1 or board coverage below 0.1. StandardEvaluationEndpoint.java, 64–104, fitness_helpers.py, 148–186

For remaining candidates, the inspected default harmonic mean uses five scores: balance, completion, decisiveness (drawishness), decision moves and trace score. Coverage and duration are excluded from aggregation, although both affect rejection. The CLI permits average/harmonic/min aggregation but does not change this fixed exclusion list. This is a paper/source protocol mismatch to resolve before reuse, not evidence that published results are incorrect. fitness_helpers.py, 9–38, 148–186, evolution.py, 383–391, 485–493

The inspected Completion source counts trials whose winner index is nonzero, excluding draws; it is not a general terminal-state count. Python recomputes balance as one minus the maximum player-win-rate difference, and decisiveness as one minus winner-zero frequency, from returned winner counts. A metric's label alone is insufficient to reconstruct its semantics. Completion.java, 47–57, StandardEvaluationEndpoint.java, 93–99, fitness_helpers.py, 119–146

Skill population: the Python wrapper requests five trials per player slot. Java puts UCT in each slot in turn against Random opponents and divides UCT wins by trialsPerGroup × playerCount; this is ten trials for a two-player candidate, but not universally ten for mutated player counts. It measures this policy/budget matchup, not general strategic depth or human skill. fitness_helpers.py, 77–84, FastTraceEndpoint.java, 143–196

Failure, timeout and budget accounting

  1. The 300-second setting is not an end-to-end deadline. It decorates only two_step_evaluate; Java evaluator construction occurs before that wrapper, and FastTrace runs afterward with its own 120-second subprocess timeout. Java startup waits for a Ready line without an explicit deadline in the inspected Python method. fitness_helpers.py, 57–90, java_api.py, 61–86
  2. Exception and numeric failure routes differ. Python-caught exceptions, including wrapper timeout, set both compilable and playable false and attach an error string. FastTrace's Java timeout instead returns numeric −3; other caught trace exceptions return −2. The Python aggregate clamps included metric values to at least 0.01 before its negative-value check, so a numeric trace failure can become a small positive contribution when other gates pass. This is a source-observed path, not an executed failure measurement. fitness_helpers.py, 77–90, 172–182, FastTraceEndpoint.java, 49–60, 117–139
  3. Early random rejection does not prevent every expensive test. The random-filter failure object remains compilable/playable, so the surrounding helper still calls FastTrace, although final quality will be −1. java_api.py, 230–236, fitness_helpers.py, 77–84
  4. Aggregation loses diagnostics. _get_fitnesses takes flags from the first grouped evaluation, averages metrics and omits individual errors. With repeated evaluations it concatenates winner-count vectors rather than summing corresponding player bins; do not increase repetitions and assume correct pooled balance/decisiveness. The inspected main saved configuration uses one evaluation. The class initializes and writes error_logs, but no append appears in this file; an empty errors file cannot establish an error-free run. evolution.py, 88–94, 179–228, run_args.json
  5. Proposal count is not evaluation cost. Each step filters unchanged parents and exact same-step duplicates; it does not use the initialized global evaluation cache. Failed, repeated-across-steps and extra trace evaluations consume resources. Saved main arguments request 1,000 epochs, whereas the published directory contains checkpoints through 500 and the comparator selects generation 500. The README command also inherits the 1,000-epoch default. Preserve actual checkpoint and observed steps, rather than infer finished budget from requested arguments. evolution.py, 262–339, 367–391, run directory, comparison, README

Proposed GameMap / harness-RSI adaptation, not an author result

Use GAVEL as a design-search pattern: mutate a bounded rule/program representation, retain lineage, reject invalid candidates, and explore diverse feasible alternatives. For a game-production fixture:

  • Freeze candidate grammar, mutation locations, project assertions, rights scope and evaluator outside the mutable policy
  • Store separate compile errors, invalid play, sampled-quality rejection, infrastructure failures, process timeout, move-cap termination and human rejection; never collapse them into one bad-game score
  • Preserve each playout's seat, opponent, seed, budget, terminal reason and raw counts; declare the actual novelty reference pool and archive projection
  • Count all proposals, deduplications, attempted evaluations, trace trials, retries and wall-clock/model costs; retain the exact selected checkpoint
  • Hold out game families and a final evaluator, then conduct human playtests separately from the proxy score; require rule activation/coverage evidence before describing a newly inserted mechanic as used

This is an unimplemented adaptation specification. It does not establish a general game-design validator, an engine adapter, improved human enjoyment or harness-RSI performance.

MiniDungeons: persona utility can expose design tradeoffs without measuring fun

Reviewed 2026-10-18. This is a source-only addition to GameMap's design/playtest evidence, complementing controller solvability and development-correctness benchmarks. No simulator, JAR, model, game, engine or evaluation service was executed; no participant data was downloaded or collected. The contribution is a concrete connection between a designer's intended playstyle, instrumented behavior and level selection, with a deliberately narrow release claim.

Published mechanism and metric population

Liapis, Holmgård, Yannakakis and Togelius (2015) separate three acceptance conditions: fixed feature counts, passable connectivity to every feature, and baseline-persona completion with every monster dealing maximum damage (14 HP). Completion must explore at least 12 tiles. Only then do monster-killer or treasure-collector personas assess level utility, averaged across ten stochastic playthroughs. Thus connectivity is not completion, and completion is not the persona's targeted behavior profile.

A critical negative result is useful for design: maximizing treasure utility produces levels where the critic always collects all seven treasures without dying; maximizing monster-utility variability produces a 0.92 death ratio. These are different optimization targets, neither an enjoyment score. Table 1 summarizes best final levels from 20 evolutionary runs, each replayed ten times; parenthesized deviations are within-level simulation deviations averaged over runs, not uncertainty across independent levels.

The personas were evolved on all ten authored levels; those same levels appear as the comparison baseline. Prior human alignment uses next-action agreement for 38 players on those levels, not enjoyment of the newly generated levels. This is not an untouched final-test study. Paper §§2.2–4, Table 1

What is actually released

The author's MiniDungeons project page directly links sentientdesigns/minidungeons as a minimal agent simulation. The reviewed source is commit 298b86cac5624e4b121b4d2e5a2fd3cd93c622f7, dated 2017-06-07. This establishes author association and exact inspected code, not equivalence to the 2015 experiments.

The README explicitly describes a bare-bones MiniDungeons 1 framework, with ten research maps plus tutorial map 0, ASCII presentation and a custom-controller interface. The complete tree contains those eleven maps and simple Idle, Random, Roomba, Zombie and Pathfinding controllers. It does not contain the paper's evolved-persona weights or feasible/infeasible evolutionary level-generation implementation. Do not attach the paper's results to this release as a reproduced benchmark, or describe it as the later MiniDungeons 2 MCTS system.

Three source-inspected surfaces make the release useful as a design-instrumentation example:

  1. A behavior vector accompanies the outcome. SimulationMode retains per-run HP, monsters killed, treasures collected, potions consumed, attempted actions and distinct visited tiles, then prints both aggregate and full per-run values. The stock configuration uses ten runs with a 300-action ceiling. Measurements include every run, including deaths and capped runs, rather than filtering to wins. Its counters classify completed as HP > 0 and actions < 300, and uncompleted as actions == 300: completion on action 300 would be counted uncompleted, while death on that action can enter both died and uncompleted. These are implementation counters, not mutually exclusive terminal verdicts. This lets a future comparison preserve the cost of obtaining treasure or combat coverage instead of presenting only a single completion percentage. SimulationMode, lines 20–142

  2. The displayed heatmap has a precise information limit. renderHeatmapDungeon consumes getAnyVisited() and marks visited locations with %. It is a binary occupancy map, not a visit-frequency map or an ordered action trace. PlayMap separately stores visit counts and collision/exit event strings. A designer can inspect where behavior went, but the exported occupancy alone cannot establish when a potion was used, how often a corridor was retraced or which decision preceded death. PlayVisualizer, PlayMap

  3. Controller identity and randomness remain experimental variables. The stock runner instantiates PathfindingController, whose action choice minimizes path distance to the exit; it does not implement the learned treasure/monster personas. RandomNumberManager creates a default Java Random with no exposed seed-setting method. Choosing a controller, adding seed control and recording exact initial damage draws would therefore be adaptation work, not existing reproduction support. PathfindingController, RandomNumberManager

The README says the codebase and bundled lib/ai_path.jar use the GNU Lesser General Public License, but gives no explicit numbered version; the inspected tree has no standalone license text. Record that wording without converting it into MIT or a specific LGPL SPDX identifier. The binary was not fetched or inspected. The minimal ASCII release also does not establish rights for separately linked graphics. README licensing notice, MD-tree

Proposed GameMap / piRSI adaptation, unimplemented

For an original project-owned dungeon, have the designer state the intended tradeoff before optimizing: for example, optional treasure should require a survivable detour while a safer completion route remains available. Keep mandatory reachability/completion gates separate from persona-specific behavior targets. Do not silently change the design target because a candidate improves an easily optimized statistic.

Use a small development fixture family: an unreachable reward, a connected but lethal route, a safe direct route with trivial rewards, and a meaningful optional detour. Pair each run's native outcome with the behavior vector, ordered event trace and viewable route. Preserve deaths and budget exhaustion beside successful runs. A persona's failure should trigger diagnosis of both controller competence and level design; it does not prove that no player could succeed.

For a recursive harness comparison, freeze persona definitions, observation access, game rules and budgets before evaluating candidate changes. Hold out whole layout families and reserve a final evaluation set that cannot influence controller or harness selection. Report completion and behavior-target attainment separately for each persona, with the full denominator. A faster or more varied synthetic route is useful feedback about these defined agents. Representative human playtesting and designer review remain separate evidence needed to assess clarity, pacing, frustration and enjoyment; neither has been performed here.

Sonic trajectory visualization: comparing training populations

Checked 2026-10-19. This research prototype complements MiniDungeons binary occupancy with aggregate route comparison across agent populations. Richer diagnostic evidence is not itself validated design advice.

Published mechanism and limits.

The prototype trains 30 NEAT agents per generation in Gym Retro for Sonic 2. Reward uses final-position-to-goal Euclidean distance. Controller observation encoding, exact reward formula, episode cap, seeds, total training cost and independent repetitions are unspecified. Logged inputs are per-frame positions, level reward and generation identity; outputs are minimum/mean/maximum reward curves plus two independently selected generation maps. Circles summarize characteristic route points; line width aggregates travel frequency in either direction.

Illustrations compare Emerald Hill generations 29/56 and Hill Top generations 11/53. They suggest route discovery, repeated obstacle trouble and skipped backward power-ups under the progress reward. These are qualitative interpretations, not measured diagnosis accuracy, controlled designer benefit or validated human-expertise predictions. Difficulty versus inadequate agent training remains ambiguous.

Aggregation ignores walls and omits gameplay-event context. Integrated training controls, changed start positions and focused trajectory segments are future work. The paper does not establish individual-episode drill-down, temporal event replay, exact characteristic-point parameters, industrial deployment, coverage gains or enjoyment improvement. It reports observations from three levels of one game, not a representative held-out game study. Primary paper, §§III–V and Figs. 1–3

Proposed GameMap adaptation, unimplemented. Retain native episode outcomes, directed trajectories and mechanic/event traces behind each aggregate. Define whether edge width counts traversals, unique episodes or dwell time; keep graph construction and normalization fixed across candidates. Separate obstacle arrivals, crossings, deaths, timeouts and invalid logs. Use project-owned fixtures with one-way gates, nearby disconnected corridors and backward rewards to test whether aggregation hides failures. Freeze policy checkpoints while comparing displays, or cross controller and display changes separately. These controls are proposals, not features or measured benefits of this prototype.

SuSketch: interactive surrogate feedback, with a separate evidence boundary

Reviewed 2026-10-19, source-only. SuSketch supplies a designer-facing loop: edit, inspect predicted spatial/temporal effects, compare alternatives, then explicitly apply a change. The author project page establishes this purpose. No tool, engine, model or game was run; no model binaries or participant records were fetched.

Inspectable workflow. The author-named GitHub profile pins the project, whose README links the publication. Source was inspected at 8962008e1340b32e6d5425a9ee5300dad2baed4f, committed 2022-04-30. This is an identified source snapshot, not an established paper-reproduction build.

  • Designer configuration consists of a 20×20 tile layout and two class selections. The inspected input adapter encodes architecture, pickups and stairs as seven channels; TFModel combines that representation with class parameters and invokes five saved networks; the kill-ratio and duration paths append an all-zero eighth cover channel. These are model estimates, not newly observed matches
  • Structural checks produce specific messages for failed traversal, inaccessible pickups, stairs and enclosed regions. They are distinct from predicted kill share, duration, death locations and combat progression
  • Display code renders player-share bars and temporal charts; the death display has 4×4 cells. Suggestion thumbnails show pickup-count differences and predicted balance change, with a separate apply operation. Class suggestions likewise require an apply action

Published evidence limits. The paper's 475,000 training/test traces are artificial-agent matches filtered to reach 20 kills within ten minutes. Thus the surrogate population excludes timeout matches. Reported mean-output test R² is 0.400 for death heatmaps and 0.438 for combat pacing. Its 16-person remote study uses the authors' contacts; it assesses tool use and questionnaires, not the enjoyment of people playing the resulting levels. Fifty-five valid design sessions remain after 19 exclusions. Designers could not play their levels inside the tool. Heatmaps were easier to understand than dramatic-arc feedback; activation-map and natural-language explanations were future work. Visual availability therefore should not be equated with causal explanation. Paper §§IV, VI–VII

Important version distinction. The paper describes 20 ordered different-class pairings and identifies Sniper/Soldier as its best different-class suggestions. Paper §V. Yet the pinned initializer adds 18 entries per invocation to a static list without clearing it, omitting both Sniper/Soldier directions from those additions; the inspected caller passes that list to the selector. This source-level discrepancy does not establish a runtime failure or invalidate the published study.

Availability and rights. ProjectVersion names Unity 2019.4.4f1. The complete tree lists C# source, five model-byte files, map files and analytics paths; only metadata was read for models/data. Neither a complete training-corpus release nor experiment reproduction was established. No root project license was observed; dependency-specific licenses do not settle whole-project reuse. V1.0.3, published 2024-08-30, points to an external executable, which was not fetched or validated.

Proposed GameMap adaptation, unimplemented. Preserve structural verdicts, predicted metrics and actual playtest observations separately. For each suggested change, retain the before/after layout, class configuration, model revision and predicted effect; let the designer accept it explicitly. Verify selected changes with independent simulations and representative human playtests, including stalled matches outside the cited training population. Freeze the predictor when comparing harness changes, retain all rejected candidates and reserve held-out layout families. These are design recommendations, not measured improvements.

Acceptance layers for the Planning Map

  1. Plan: define the core loop, inputs, win/loss conditions, restart behavior, and progress state. Limit scope to a slice that supports continuous playtesting.
  2. Code / Scene: have the agent write code while using the editor, CLI, or MCP to inspect real scenes, asset bindings, logs, and runtime state.
  3. 2D assets: standardize canvas, perspective, character scale, directions, anchors, transparency, frame order, loops, hit timing, atlases, and tile edges.
  4. 3D assets: record units, axes, origins, polygon counts, material slots, UVs, LOD, rigs, animation retargeting, collision, and navigation. A convincing generated image covers only part of this work.
  5. Test: check compilation, gameplay invariants, visual layout, input reachability, win/loss and restart behavior, long runs, and performance separately. Visual judges and state probes provide complementary evidence.
  6. Ship: validate on target devices or exported builds. Record engine versions, asset sources, build steps, and performance budgets.

These layers are GameMap's planning recommendations, synthesized from the resources and their engineering boundaries. They are not experimental findings from any single paper.
