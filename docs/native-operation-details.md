# Native operation details and lifecycle boundaries

Sources checked **2026-10-18** in the earlier research; this document curates those inspected records and subsequent audit corrections. No new engine, DCC, middleware, model, adapter or command was executed. These are **documented upstream surfaces, not implemented GameMap bindings**. Proposed gates are editorial acceptance requirements, not promises that the API supplies them.

This supplement restores operation-level detail omitted by concise directory cards. It complements the [engine-operation notes](engine-operation-contracts.md#animation-rendering-and-interchange) and nine production work orders rather than restating their end-to-end chains. Source commits and document versions identify evidence only, never installed compatibility.

## How to read lifecycle limits

Each row distinguishes known completion/persistence behavior from unknown cancellation, retry and recovery semantics. “Unknown” means the inspected source did not establish that contract; it does not claim the vendor lacks it. Unless a row explicitly states otherwise, idempotent retry, transactional rollback, safe concurrent writers, crash/power-loss durability and complete application reset remain **unknown**. A successful API call, callback, file write or process exit alone does not establish accepted production output.

Version scope: Epic sources vary across versioned experimental Python 5.4/5.5/5.6/5.8 and rolling pages displayed as 5.8. Unity sources include 6000.0, CLI 6000.3, Test Framework 1.4.6, AI Navigation 2.0 and Input System 1.9. FMOD sources are 2.04 (pages identified 2.04.00, 2026-09-29). Max references are 2024; Substance documentation is rolling. Use the exact per-row links and source scope index below rather than assuming one coherent installed stack.

## Distinguish FMOD event lifecycle from audible completion

**Source-only scope.** Reviewed 2026-10-18 against FMOD Engine/Studio 2.04 documentation, identified as **2.04.00 (2026-09-29)**. These are documentation contracts, not installed-version, runtime, license-entitlement or adapter results. Existing scheduling, sample-readiness and event-release coverage is not replaced.

**Documented boundary.** The [EventInstance reference](https://www.fmod.com/docs/2.04/api/studio-api-eventinstance.html#fmod_studio_event_callback_type) defines callback types separately from playback-state enums: `FMOD_STUDIO_EVENT_CALLBACK_STARTING` reports a start request on a previously nonplaying event; `STARTED` can be delayed by sample loading. `START_FAILED` reports polyphony refusal, in which case STARTING, STARTED and STOPPED callbacks are not issued. Separately, `getPlaybackState` writes the playback enum `FMOD_STUDIO_PLAYBACK_STOPPED` for an invalid instance. This output enum is separate from the `FMOD_RESULT`/`RESULT` return of the C/C++/C# call; retain both. Calling `start` on an already-playing instance restarts it.

[Studio state mapping](https://fmod.com/docs/2.04/studio/advanced-topics.html) documents that pause does not change `FMOD_STUDIO_PLAYBACK_STATE`; query pause separately.

[Studio stealing modes](https://www.fmod.com/docs/2.04/studio/event-macro-controls-reference.html#stealing) distinguish Oldest/Furthest/Quietest (stop the selected instance), Virtualize (quiet instances continue without output and can become real as relative audibility or capacity changes) and None (refuse new playback while at the limit). These are event max-instance policies, not Core software-channel limits. [Core resource management, Interaction with the Core API Virtual Voice System](https://www.fmod.com/docs/2.04/api/managing-resources-in-the-core-api.html) documents that `EventInstance::isVirtual == false` can coexist with some or all underlying Core Channels being virtual because of the software-channel limit. A real Studio event therefore does not prove audible Core voices.

**Proposed acceptance contract.** Record instance identity, API result, callback type, playback enum, pause state, event virtualization, applicable Core voice limits and stop intent separately. Join these observations to the existing captured-output evidence. Distinguish refusal, invalidated observation, normal native stop and verified audible completion. Neither STOPPED nor PLAYING nor event-level nonvirtual status is a standalone audible-success gate. Reconcile uncertain starts before retrying.

**Unimplemented fixtures:** polyphony refusal with no STOPPED callback; Studio-real/Core-virtual playback under a constrained software-channel limit; pause while PLAYING; handle invalidation before terminal polling; virtual-to-real restoration. Capture onset and intended tail separately. No fixture, adapter, engine/API/model execution or physical-device measurement was performed.

## Other native persistence and browser-engine boundaries

[Godot ResourceSaver](https://docs.godotengine.org/en/stable/classes/class_resourcesaver.html) returns an Error status when saving supported resources; generated resource UIDs are not persisted during runtime because the relevant code is editor-only. [Godot 4.4 RNG](https://docs.godotengine.org/en/4.4/classes/class_randomnumbergenerator.html) restores previously generated state; set seed before state when setting both, and do not assume algorithm stability across versions. [Blender 4.5 CLI](https://docs.blender.org/manual/nl/4.5/advanced/command_line/arguments.html) evaluates arguments in order, so loading a blend may override settings placed earlier; background operation is separate from CPU/GPU rendering choice. These source behaviors do not establish crash-safe persistence or whole-game replay.

Browser-engine observation and export also have separate completion surfaces: [Three.js asynchronous render-target readback](https://threejs.org/docs/pages/WebGLRenderer) resolves pixel data, while [GLTFExporter.parseAsync](https://threejs.org/docs/pages/GLTFExporter.html) resolves exported data and requires renderer-specific utilities for compressed textures. Neither promise alone saves an evidence file or proves downstream importer fidelity. [Babylon NullEngine](https://github.com/BabylonJS/Documentation/blob/master/content/setup/support/serverSide.md) requires no WebGL device but produces no rendering; server/test/import support under it cannot establish visual correctness. Cancellation, idempotent retry and output durability remain unverified.

[Houdini licensing](https://www.sidefx.com/docs/houdini/licensing/system.html) documents configurable product/mode selection hierarchies. Proposed deployment evidence should record the selected product, mode and actual license configuration; a working host UI or headless entry point does not establish entitlement. No price, free tier or universal license checkout order is asserted.

[Epic's Behavior Tree overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview), inspected as UE 5.8 documentation, describes observed Blackboard conditions aborting lower-priority branches and Simple Parallel/services organizing behavior. Conceptual parallelism does not establish OS-thread parallelism or a generic cancellation contract.
