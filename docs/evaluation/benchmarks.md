## Concrete evidence changes from the earlier discovery note

1. **JAMER release status is internally inconsistent.** Preserve both statements and label availability unverified; neither “released” nor “closed” is established by the examined paper alone. The paper's calibration exclusion is useful, but it does not answer all task-order or persistent-memory leakage questions.

## Fair pi-based recursive harness improvement

When adapting a harness, implement the controls below alongside the extension and optimizer surfaces in the [pi/GEPA reference](source-revisions.md).

For generated interaction regressions, [stateful discovery and failure reduction](gameplay-state.md#stateful-interaction-discovery-and-failure-reduction) separates adaptive shrinking, clean-state reproduction and fixed regression promotion. Count every reset, attempted step, shrink/replay and cleanup; reduced traces are not independent success-rate trials.

### Choose the unit of comparison first

- **Official reproduction:** preserve the publisher's exact tasks, evaluator, engine, allowed observations/actions, budgets and run policy. A new pi adapter must meet those conditions before its score is compared with published results.
- **Harness improvement study:** freeze one released task/evaluator revision, compare baseline and candidate on the same declared conditions, and identify results as a new study. Replacing engine checks with vision judging, adding privileged state, or extending the feedback budget changes the experiment.
- **Protocol-inspired fixture:** when evaluator/data are unreleased or rights unresolved, create original tasks and tests that exercise the documented idea. Name the protocol influence without claiming the source benchmark's score or task coverage.

### Keep the search space separate from protected evaluation

| Surface | Proposed mutable scope during improvement | Protected boundary and evidence |
| --- | --- | --- |
| Tool interface | Parameter schemas, error presentation and documented compositions over the same authorized native operations | Do not add hidden oracle state or broader filesystem/network authority to only one condition; record adapter and policy hashes |
| Visual observation | Frame selection, crop, compression and explicitly declared diagnostic views | Retain original frames, transforms, timestamps and actual model packets; compare pixel/token/latency budgets and never silently expose final answer images |
| Memory and retrieval | Candidate skills, task-local notes and permitted prior-development experience | Partition by originating project/tutorial family; separate development, selection and final-test memory stores; no test solution/rubric retrieval |
| Refinement feedback | Developer split failures and allowed play traces | Evaluator-owned final assertions and rubric stay outside the optimizer and its reflection context; log all feedback delivered |
| Termination and recovery | Bounded retries and error handling within the declared budget | Record all attempts, aborts, invalid measurements and late results; do not retain only successful reruns or treat timeout as verified failure of gameplay |

Public test material may already be present in a base model's training data. Isolation can reduce experiment-time leakage but cannot prove absence of prior contamination. A held-out partition should group related projects, tutorial derivatives and nearly identical tasks rather than merely randomizing filenames. If public task coverage is too small, report the limitation rather than call the result general self-improvement.

### Proposed evaluation record

Freeze task identifiers and origin groups; content/asset hashes; evaluator and engine versions; solver model and reasoning settings; candidate harness revision; allowed API/GUI/file surfaces; training/selection/test membership; memory provenance; model-token/tool-call/time budgets; seed and fresh-start policy; build and runtime logs; screenshots/video and authoritative checks; final judge configuration; raw terminal outcomes and resource costs. Preserve credential references only, never secrets. Do not configure any credential transmission merely to fill this record.

For each candidate, retain paired baseline/candidate outcomes on the same tasks and report the sampling unit. Separate valid task failures from harness/infrastructure failures and give denominator policy before viewing results. Repeat stochastic runs where justified; a single successful retry is not a robust capability. Run the final held-out evaluation only after selection, and archive the unsuccessful candidates too. None of these fixtures, statistical comparisons or execution permissions has been established by this source-only review.

## Harness selection: statistical independence and adaptive feedback

Checked 2026-10-18. Primary-source inspection only; no installation, benchmark execution or game-performance claim. The proposed protocol below extends the existing candidate-selection and reproducibility records.

### rliable: repeat whole tournaments, preserve the intended comparison

Agarwal et al. assume independent runs per task, each yielding a scalar normalized score. Appendix A.4 treats best-of-N as a distinct stochastic algorithm: one maximum over N candidates supplies only **one run of that selection algorithm**. It therefore needs independent repetition. Stratified bootstrap resamples runs within each task. The Atari coverage study shows nominal 95% CIs under-cover with three runs; percentile intervals perform well around ten for examined aggregate metrics. These empirical results do not establish a universal sample-size guarantee. [Paper v4, §2, §4.1, Fig. 6, Appendix A.4][RL-paper]

At inspected commit `3ccd9f4dea577a04d3d2b557f259aac08badbd81`, `get_interval_estimates` takes method-to-score mappings shaped `(runs, tasks, ...)` plus an aggregate function, returning point estimates and lower/upper CI arrays. Defaults are percentile, 50,000 bootstrap replications and 95% nominal coverage. The single-array route supports `task_bootstrap`: false resamples runs on fixed tasks; true additionally resamples task columns. Tuple/list-valued entries instead use `StratifiedIndependentBootstrap`, independently resampling arrays without `task_bootstrap`. That convenience route is **not a paired A/B effect interval**. For matched mean differences, a pair-aligned difference matrix can use the single-array route; nonlinear contrasts need a verified pair-preserving route. This is an API-path limitation, not a claim that the entire library cannot support paired analysis. [Pinned library][RL-library]

IQM trims 25% from each tail of pooled scores. Probability of improvement averages taskwise Mann–Whitney rank statistics; it is not a posterior probability of being the best system. [Metrics][RL-metrics]

The public code is Apache-2.0; setup declares 1.2.0 and `arch >= 5.3.1, < 8.0`. The repository is archived. Its older README dependency example is not a runtime lock. [Setup][RL-setup], [license][RL-license], [README][RL-readme], [repository][RL-repo]

### Adaptive holdout: an independent evaluator can still leak selection feedback

Dwork et al. distinguish independently fixed candidates from ones adapted using previous holdout feedback; ordinary static multiple-testing treatment does not automatically cover the latter. Thresholdout takes training/holdout datasets, threshold, noise scale and overfitting budget, answering bounded queries `phi: X -> [0,1]`. Below a noisy discrepancy threshold it returns the training mean; otherwise it returns a noisy holdout mean and spends budget. It stops when exhausted. Theorem 9 requires i.i.d. holdout samples, calibrated parameters/sample size and mediated access. This is not a guarantee for unrestricted visual critiques, correlated project variants or unlimited binary feedback. [NeurIPS 2015, §1, §3, Theorem 9][HO-paper]

The inspected release evidence establishes paper/pseudocode, not an official executable package or software license. The arXiv record is v2, September 25, 2015, with a non-exclusive distribution license. [Record][HO-record], [license][HO-license]

### Check the judge before optimizing its score

**Source finding.** MT-Bench v4 (§§3.3–3.4) tests text-answer judging, not game images. It documents order sensitivity and a repetitive-list verbosity probe; its conservative comparison requires the same winner after swapping answer positions. Increased consistency alone is not accuracy. Its self-enhancement investigation is explicitly inconclusive, so it does not establish a universal preference for a judge's own outputs. These historical-model findings motivate controls; their measured rates cannot be transferred to current visual judges. [Paper v4](https://arxiv.org/html/2306.05685v4)

**Inspected interface.** FastChat's pairwise path accepts a question, two answers, a judge and optional reference, calls the judge in both orders, and stores both mapped winners, prompts and judgments. Its loader labels disagreement `inconsistent`; malformed verdicts can remain `error`. This is a text interface, not a released screenshot/video evaluator. Single-answer grading is a separate path and should not be described as an order-swap test. [Pinned common.py](https://github.com/lm-sys/FastChat/blob/587d5cfa1609a43d192cedb8441cac3c17db105d/fastchat/llm_judge/common.py)

The inspected code is [Apache-2.0](https://github.com/lm-sys/FastChat/blob/587d5cfa1609a43d192cedb8441cac3c17db105d/LICENSE). Its [documented hosted-judge flow](https://github.com/lm-sys/FastChat/blob/587d5cfa1609a43d192cedb8441cac3c17db105d/fastchat/llm_judge/README.md) needs model/API access; code licensing does not grant that access or settle dataset/model terms. No call was made.

**Comparison template.** For visual candidate tournaments, freeze the task and exact evidence packets, remove candidate/model identity cues, and compare both presentation orders while retaining within-clip chronology. Record preference, tie, inconsistent judgment and invalid response separately, with their denominators. Audit a blinded human/reference subset for actual task correctness; agreement or order consistency cannot replace engine-state acceptance. Run a control with identical evidence and another with redundant views or verbose self-reports to detect presentation sensitivity before using the judge for selection. These visual probes are proposed experiments, not validated extensions of MT-Bench.

## GEPA execution controls: counts, caches and resumed evidence

Checked 2026-10-18. Read-only source inspection at `f1cfdee2856e9dc4b5b4dc5cc2e391d0aa20d819`, the revision already used for the adapter review. No external code, models or evaluations were run. These are code-level boundaries and proposed tests, not reproduced overspending or game-performance findings. The [MIT license][GEPA-license] does not supply model-service or asset rights.

### Count proposal tasks separately from iterations and retained candidates

The [sampling strategies][GEPA-sampling] can produce one, N or P×N parent/minibatch tasks per iteration. However, [MaxCandidateProposalsStopper][GEPA-stoppers] checks `state.i`, which the [main loop][GEPA-engine] increments once per iteration. Equal settings therefore do not guarantee equal actual proposal counts. `MaxTrackedCandidatesStopper` counts the retained candidate pool, not all failed, skipped or discarded proposals. This does not imply every sampled task produces a new candidate. Parent selection is called repeatedly without a distinct-parent constraint in these samplers; the strategy name alone does not establish unique parents.

**Proposed GameMap control:** retain separate iteration, proposal-task, generated-proposal, unique-candidate, admitted-candidate, actual-evaluation and cache-hit counts. Match actual search resources when comparing broader sampling against a better selector, and preserve costs for discarded branches.

### A stop condition is not hard admission control or remote cancellation

[MaxMetricCallsStopper][GEPA-stoppers] compares accumulated evaluation count. On a fresh run, [engine.run][GEPA-engine] evaluates the seed on the validation batch before reaching the main loop's stop check. This static path does not guarantee rejecting an over-budget initial batch before execution. The loop-boundary check does not itself cancel an in-flight model, renderer or evaluator. `TimeoutStopCondition` starts its clock at object construction, not automatically at remote-job submission.

There is a concrete cost-tracking caveat: [optimize][GEPA-api] wraps an ordinary `reflection_lm` callable lacking `total_cost` in [TrackingLM][GEPA-lm]. That wrapper estimates tokens but reports cost `0.0`; a positive `max_reflection_cost` alone cannot trip on that path. The separate custom `reflection_strategy` path has additional cost-capability checks and must not be conflated with it. Even supported reflection-cost accounting does not automatically include task-model, renderer, tool or human costs.

**Proposed GameMap control:** reserve a bounded batch budget before dispatch; independently enforce call, rendering and wall-time limits; record in-flight work and final reconciliation. Probe whether cost measurement is supported rather than interpreting zero as free. Verify executor/service cancellation separately. Use a no-external-call mock adapter for limit tests, not a live paid endpoint.

### Cache hits and resume are not independent repetitions

[EvaluationCache][GEPA-state] keys contain a candidate-text hash, train/val namespace and example ID. Distinct train/val loaders already have separate namespaces; the same loader deliberately shares one. [ListDataLoader][GEPA-loader] uses positions as IDs, not content hashes. The key has no independent model, engine, evaluator, asset, environment or trial identity fields; callers must encode or invalidate those changes themselves.

The [API contract][GEPA-api] and [engine][GEPA-engine] reuse the saved seed's validation evidence when `gepa_state.bin` exists; an identical supplied seed already in the pool causes no extra seed evaluation. A supplied seed absent from that pool is instead evaluated and added before the main stop check, also advancing `state.i`. Migration discards old unnamespaced cache entries but leaves previously recorded validation scores intact. Disabling evaluation caching does not itself erase those candidate scores or start a fresh experiment. Additionally, the engine's full-validation path bypasses cache when `write_agent_state` is enabled so it can capture trajectories: richer recording is not necessarily cost-neutral.

**Proposed GameMap control:** bind data contents/order, model/engine/adapter/evaluator versions, assets and reset policy into an experiment fingerprint. Use a fresh run directory for semantic changes rather than reusing saved scoring state. For independent stochastic trials, use fresh state or explicit trial-aware identities; returning the same cached observation does not add a sample. Record trace/cache settings and distinguish cumulative resumed results from newly executed work. GEPA's valset is used for selection and defaults to trainset when omitted; keep final assessment outside optimization rather than treating that parameter name as a protected test split.

**Unimplemented acceptance fixtures:** zero remaining budget with a larger initial validation batch; actual task/proposal counts under N and P×N sampling; a callable without real cost tracking; rejection of incompatible resume after dataset reordering or evaluator changes; actual evaluation counts with cache/trace settings toggled; and independent repeats of the same candidate. None was executed, and no general vulnerability or capability gain is asserted.

## Harness composition and evaluation accounting

Bind evaluation results to the complete candidate composition and the path that executed it. The GEPA and Meta-Harness references below describe their respective implementations; the Meta-Harness case concerns its classification harness.

### 1. GEPA: named components are not a typed execution graph

At **f1cfdee2856e9dc4b5b4dc5cc2e391d0aa20d819**, [adapter.py][HC-G-adapter] defines Candidate as dict[str,str]. evaluate(batch,candidate,capture_traces) must construct the system and return aligned outputs/scores and, when requested, trajectories; make_reflective_dataset returns per-component JSON-serializable records. ProposalFn explicitly permits coupled updates. [Component selection][HC-G-components] offers one component in round-robin order or all keys.

The [mutation implementation][HC-G-reflect] copies the parent and asserts each returned replacement key already exists (585–588); this assignment does not itself check membership in components_to_update or enforce semantic dependencies. [Merge][HC-G-merge] requires identical component-key sets and takes whole component texts from descendants sharing an ancestor. When both descendants changed a component, executable code chooses the higher aggregate-score descendant, randomly breaking ties (159–190), despite an adjacent comment describing proportional random selection. It does not synthesize or type-check their combined workflow.

[Candidate hashing][HC-G-state] is SHA-256 over JSON-serialized sorted candidate items (37–39). This identifies text, not the builder, tool implementation, operation authority or external runtime. Existing cache warnings remain correct.

**Proposed GameMap adaptation, unimplemented:** retain the GEPA map, e.g. tool_schema, workflow and evidence_policy, rather than claim GEPA supplies a graph language. Freeze a builder interface: validate_and_build(candidate, frozen_contract) returns either a plan or structured invalid_candidate reasons. Declare primitive operation IDs, argument/result schemas, dependency edges, sequential/parallel execution, bounded retries and error branches. Validate the mutation mask and coupled-schema compatibility before evaluation. Keep evaluator/permissions outside candidate text. Identify an executable candidate with component-text hash plus builder revision, primitive/schema manifest, dependency lock and fixed authority hash; keep experiment/trial identity separate. Store parent IDs and the chosen component provenance for merges.

### 2. GEPA: “metric calls” depend on the execution path

EvaluationBatch has optional num_metric_calls. [Reflective evaluation][HC-G-reflect] honors it for parents and children, falling back to batch length (372–376, 638–642). [Full validation][HC-G-engine] instead charges len(val_ids) with traces and len(uncached) otherwise (287–368). The [merge/cache evaluator][HC-G-state] likewise returns requested/cache-miss example counts. Therefore num_metric_calls is not a universal accounting override for nested model calls or retries.

Reflective batch counts are incremented after a batch returns. The default [batch adapter][HC-G-adapter] evaluates pairs sequentially; if a later call raises after earlier external work, that path does not provide a complete spent-resource count. Batched reflection failure also triggers per-task retries ([245–272][HC-G-reflect]); additional attempted work must be retained. These are static paths, not reproduced overspending.

**Proposed control:** maintain an append-only dispatch/settlement ledger outside optimizer scores: candidate/trial/task/operation IDs; phase; reserved budget; attempts; observed model tokens, tool/render calls and wall time; charged/estimated/unknown cost; terminal status. Reconcile cancellation and late results. Keep valid task failure, invalid candidate, infrastructure failure, timeout, abstention and unknown outcome distinct, even if a declared optimization metric assigns some the same failure score. A missing usage report is unknown, not zero. Budget admission and total-cost reconciliation remain adapter/executor responsibilities.

### 3. Meta-Harness: a concrete interface and incomplete-coverage boundary

At **8123ccabe2b19fa1123090b2e5f1bacc20963ce8**, the classification example’s [MemorySystem][HC-M-memory] requires predict(input) → (answer,metadata), learn_from_batch(results), get_state() → serialized string and set_state(state). Its [loader][HC-M-inner] imports a module and instantiates the first inspected MemorySystem subclass (479–504). The outer [validation][HC-M-loop] checks zero process exit status plus stdout containing OK when importing the candidate (192–215); that is narrower than validating the runtime interface and is already code execution, not safe static inspection.

[benchmark.py][HC-M-bench] requires complete configured seed groups per model/dataset/candidate (179–239), but aggregate-frontier construction averages accuracy over the dataset groups actually loaded, without requiring every configured dataset for each candidate (675–688). Its context-character axis instead averages only strictly positive context lengths and then truncates to an integer; these axes therefore use different inclusion rules. The [outer summary][HC-M-loop] similarly averages available datasets (529–540). Zero score is labeled “failed”; invalid imports disappear from the normal summary when other candidates are valid (232–244, 490–560). Preserve a complete manifest rather than treating those summaries as exhaustive failure denominators.

The Pareto axis is memory_context_chars, not total model cost. [MemorySystem][HC-M-memory] tracks the last prompt per thread and defines context length in characters. The actual classification evaluation uses the last tracked call_llm prompt length minus test-input length, clamped to zero and integer-averaged ([inner_loop.py 439–469][HC-M-inner]); this includes template text as well as memory, rather than serialized-state size or all prompts. Its evaluated metric does not call the default get_context_length path. [benchmark.py][HC-M-bench] separately sums available runtime, call and token fields, with missing fields defaulting to zero. Do not rename character efficiency as token or spending efficiency.

**Proposed control:** content-address candidate code plus dependencies/configuration; record the exact exported class instead of relying on module names. Require complete prespecified dataset/seed coverage for promotion, report coverage separately, and retain every proposal/import/evaluation attempt. Validate interfaces without importing untrusted candidates; later runtime validation requires a separately authorized isolated environment.

## Browser-game virtual time: stepping and suspension are different experiments

Sources checked **2026-10-19**. Read-only review of Microsoft Playwright **v1.64.1**, whose [tag](https://api.github.com/repos/microsoft/playwright/git/ref/tags/v1.64.1) resolves to `cfe490d941f992655948eee8fd4fd94e1c4234bf`. This selected release matches GameMap's declared development dependency, not a verified benchmark runtime. The repository [license](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/LICENSE) is Apache-2.0; it does not clear browser binaries, tested games or their assets. No upstream code, browser or game was executed.

### Source-backed temporal boundaries

- **Choose what time means.** The [Clock API](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/docs/src/api/class-clock.md) distinguishes `setFixedTime` (fixed Date values while timers continue), `setSystemTime` (change wall time without firing timers), `runFor` (advance through callbacks), and `fastForward`/`pauseAt` (jump, firing overdue timers at most once). Thus replacing a five-second gameplay interval with a five-second jump can change how many update callbacks run. That consequence is GameMap's application to game tests, not a measured game defect.
- **The animation cadence is synthetic.** [Injected source](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L355-L401) supplies animation callbacks with simulated ticks and schedules each new frame request for the next 16 ms boundary; the [unit tests](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/tests/library/unit/clock.spec.ts#L1283-L1359) assert this grid. A jump can instead deliver an already-overdue frame at its destination, because the [jump path](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L277-L291) reschedules overdue timers there. This is not measured display refresh, GPU throughput or evidence that the game uses a 60 Hz physics step. [Timer creation](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L294-L323) schedules a zero-delay timer created during a tick one millisecond later. [Tests](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/tests/library/page-clock.spec.ts#L473-L519) show that such a nested callback at the requested endpoint needs another advance, including when scheduled through a microtask.
- **Installation and isolation are explicit inputs.** The [guide](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/docs/src/clock.md#L24-L44) warns that installation must precede use of the replaced timer APIs. The API's scope is the entire browser context, including its pages and iframes, not one isolated page. [Server dispatch](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/src/server/clock.ts#L37-L110) applies clock operations to frames and preserves initialization instructions for later documents. Do not treat sibling pages as independent time-controlled trials or infer worker, Web Audio, network/server or whole-browser synchronization from that scope.
- **Manual advance is not an instantaneous, atomic step.** [`runFor` and its timer loop](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L169-L195) continue processing due timers after catching a synchronous callback Error, advance the clock, then rethrow the first Error. A [browser test](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/tests/library/page-clock.spec.ts#L98-L104) expects a later callback to run before rejection. The [callback invoker](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L355-L393) yields through a real timer after each callback and does not await a callback's returned promise. A rejected advance therefore does not imply unchanged state or safe retry; its completion is not a network/asset-readiness barrier.
- **Keep performance measurement outside this treatment.** The [performance replacement](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/injected/src/clock.ts#L754-L772) makes `performance.now()` follow simulated ticks. For the performance methods copied by this implementation, entry queries return empty arrays and mark/measure calls return synthetic entries. These readings cannot substantiate native frame-time or resource-timing claims. Separate real-clock performance runs from virtual-time functional runs.

### Proposed acceptance contract, not executed

Record game/build hash, Playwright and actual browser revision, context identity, initialization/readiness policy, clock mode, starting wall/monotonic values, ordered clock commands and input events, randomness/reset policy, application tick counters, callback/error trace and post-step state. The release's [browser inventory](https://github.com/microsoft/playwright/blob/cfe490d941f992655948eee8fd4fd94e1c4234bf/packages/playwright-core/browsers.json) is an expected dependency list, not proof of the installed executable.

Use an explicitly quiescent game-start boundary after bootstrap; a large `pauseAt` jump during active gameplay is itself a suspension treatment. Confirm the starting state before issuing player input. Keep real-clock play, fully stepped virtual time and suspend/resume probes as distinct conditions with separately declared oracles. Require an application-owned completion signal for asynchronous effects rather than adding arbitrary extra simulated time until a test passes.

**Unexecuted fixtures:**

1. In separate fresh contexts, start identical movement on positive 100 ms intervals and cooldown logic after the same paused baseline; compare `runFor(1000)` with `fastForward(1000)`. Record callback counts, elapsed-time calculations and final state. Different results can reflect the declared temporal treatment, not automatically a game bug.
2. Record the starting simulated-tick phase and advance a self-rescheduling animation loop just before and onto its next 16 ms-grid boundaries. From a timer callback firing at endpoint T, schedule a nested zero-delay follow-up: assert absence at T and presence after a predeclared advance to T+1, rather than waiting indefinitely at T or silently extending the budget.
3. Make one timer throw `new Error(...)` before another mutates score. Retain the rejection and resulting state, then discard that trial context rather than blindly repeating the advance.
4. Include a sibling page and a separately observed worker/audio or server deadline where used. Establish which clocks actually move; unsupported synchronization leaves that fixture outside the virtual-time claim.

These are original proposed harness checks. They do not establish deterministic simulation, synchronized external clocks, delivered rendered frames, reproducible benchmark scores or real-time performance.

## Online harness adaptation and change-level audit

Checked 2026-10-19. The following complementary studies extend the source-only methodology inventory. Neither establishes effectiveness in game production.

### Harness²: contrastive task-local edits and reusable improvement evidence

The [October 9 paper, v1](https://arxiv.org/html/2610.14224v1), studies frozen-model harness adaptation on professional-work benchmarks, not game production. It proposes invariant and domain-specific edits, probes them on the same task, then composes a successor from execution contrasts. Those contrasts do not certify correctness. The next task starts from a common base harness; adopted components and lessons inform subsequent proposals rather than automatically replacing that base. Parallel width and sequential depth are distinct budget choices. The paper reports three shuffled streams and discusses selection regressions, shared incorrect premises, extra inference cost and uncertain transfer. Its leave-one-out completed-library analysis can access later tasks and is explicitly an offline reuse analysis, not an online gain estimate. These distinctions make it a useful comparison for changing a visual harness between project tasks without treating selected output as verified improvement.

**Released surface.** The author-linked [repository snapshot](https://github.com/google-research/harness2/tree/1cfe254e8d25b15f37048c3730134686abe60335) contains orchestration code, benchmark bridges and a deterministic demo. Its [README](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/README.md) describes OpenCode/Codex executors and model-backed JobBench, LAB and WorkBuddy workflows. These need external dependencies and model access; none was installed or run here. Apache-2.0 covers the repository's own code, while third-party code/data retain their terms. Released code and paper results are separate evidence; this inspection does not establish that these exact bytes produced the paper's results.

**Operational boundaries from the same pin:**

- [Experiment guide](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md): task order is seeded, model sampling is not. `max-tasks` applies per domain. Generated task partitions are local artifacts, and JobBench download revision is recorded at setup rather than fixed by the repository. The release warns that unrestricted network access can expose public rubrics, and reports one such validation-run retrieval; neither this warning nor prompt instructions establish protected evaluation. No network/security configuration was changed here.
- [Library implementation](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/library.py): a retained entry includes the complete component tree and an experience record; admission checks require nonempty cue, lesson and evidence strings. Those structural checks do not establish the truth of a lesson.
- [Budget ledger](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/ledger.py): the nominal identity counts `4k` rollout entries and `3k` improvement-stage entries. Retry attempts, selection and reflection must be accounted for separately; cached entries are not new independent executions.
- [Report implementation](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/report.py): graded rows form the score denominator, and ungraded rows are separately counted. The module also warns about inherited-harness fallback, selected base/candidate outputs and mixed scoring units. Read these populations before comparing a headline average.
- [Completion marker](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/runmark.py): the API documents recording after normal runner return, storing a supplied-tree fingerprint or the shared `base` sentinel when no harness directory is supplied. It does not independently verify completion. This is reuse metadata, not evidence of valid game behavior, fresh model sampling or an independently successful task.

**Comparison template:** compare a fixed harness, task-local edits without a library, and the same edits with a project-separated library under equal total budgets. Bind any visual lesson to frame/build/artifact IDs; keep editor/run provenance and invalid verdict counts. Reserve protected project tests and audit the full candidate-to-selected-to-inherited chain. This is a proposed game-production experiment, not a demonstrated benefit or compatible pi integration.

### Audit promotion and inherited state

[Auditing Harness Tampering in Self-Improving Agents, v1](https://arxiv.org/html/2609.00069v1) adds a change-level perspective: obligations can fail during execution, evaluation, selection, recording or propagation. Its constructed dataset inserts matched faulty/benign edits into recorded changes; classification receives target lines, while localization must find them. Construction supplies labels and human inspection covers a subset. The reported natural-run analysis applies a model auditor to released trajectories. Its finding rates are not independently established defect prevalence, and seeded-control false-positive rates do not establish natural-run precision. An ancestor's flagged edit does not prove activation or a causal score gain in its descendants. The reviewed paper/deposited manuscript archive did not establish an author-linked auditor, labeled-data or full-output release; availability remains unverified. Paper licensing does not establish software/data rights. No auditor or alleged defect was executed here.

Extend existing candidate provenance through promotion and later reuse. Record full diff and relevant pre-state, the frozen allowed-mutation/obligation manifest, suspicious lines, supporting trace IDs and disposition. Keep static suspicion, human-adjudicated defect and reproduced effect separate. Use original paired fixtures to test:

- Missing required platform/playthrough results despite excellent remaining scores
- A previous build's screenshot or asset report substituted for current evidence
- A failed import or timeout omitted while its successful retry remains
- A reporting defect inherited through a merge, alongside a genuine repair control

Compare raw events with the protected acceptance manifest, and report detection and false alarms separately. A model flag should prompt investigation; a changed line number alone does not prove repair. This proposal complements protected evaluators and task splits without asserting that an audit model certifies safe harness evolution.

### GameCraft-Bench: the upstream replay-to-score contract

[GameCraft-Bench](https://arxiv.org/html/2606.17861v1) evaluates complete Godot projects and agent-supplied demonstrations. At upstream [`a4334753`](https://github.com/FreedomIntelligence/gamecraft-bench/tree/a43347534374df9a0c1a6c001aa9380862783f6d), shared by the later adapters, traces remain development-visible; “hidden” describes the evaluation rubric's role, not secret test trajectories. Named scenarios may initialize advanced states. Credit therefore concerns demonstrated requirements, not independently discovered playability or enjoyment. This source audit ran no games or judges.

**Evidence budget.** The [task contract](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/tasks/cardgame-autobattler/instruction.md#L98-L152) asks for 1–10 traces, capped at 600 frames at 30 FPS. With overridable defaults, the [scorer](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/score.py#L110-L184) keeps the first ten filenames before replay. Each [fresh launch](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/replay.py#L73-L218) defaults to a 1280×720 input viewport and resized 854×480 MP4. The [frame sampler](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/score.py#L342-L402) defaults to 0.5-second spacing and, for longer recordings, a contiguous 20-second window seeded by demo name; a short recording can have its final frame cloned. Replay separately defaults to a 90-second limit. These are distinct submission, replay and observation limits.

The [OpenAI judge](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/judges/openai_gpt.py#L59-L139), defaulting to GPT-5.5, sends at most 40 sampled PNGs, as do the released Claude/Kimi paths. The [Gemini path](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/judges/gemini.py#L39-L100) sends the full MP4 instead. The sampling window is not a universal video-duration cap; provider choice can change evidence modality as well as judgment.

**Aggregation and failures.** Each [rubric item](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/score.py#L298-L317) uses max (default) or mean across scored demos; different items can win on different playthroughs. The [inspected task rubric](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/tasks/cardgame-autobattler/tests/rubric.json#L1-L9) combines item averages with a build gate and mechanics/depth/visuals/art weights of 15/35/15/35. A caught replay failure is logged and skipped, shrinking a mean's demo denominator. By contrast, five failed judge attempts produce item zeros for that replayed demo. Missing, null or non-numeric answers, including “NA,” also become zero; there is no coverage-exclusion rule. No successful evidence leaves requirements at zero. Preserve failure counts alongside scores. [Failure handling](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/score.py#L142-L268), [response parser](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/gamecraft_bench/verifier/judges/_common.py#L68-L106)

**Release and transfer.** The pin contains 140 task packages plus an example, public rubrics, evaluator and reference-source material; some reference scripts are [placeholders](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/tasks/sports-archery-quest/solution/solve.sh). This is not an inspected all-task run archive. [Apache-2.0](https://github.com/FreedomIntelligence/gamecraft-bench/blob/a43347534374df9a0c1a6c001aa9380862783f6d/LICENSE) covers repository code; downloaded asset entries retain their own terms. For a proposed GameMap comparison, freeze project/trace hashes, filenames, scenarios, capture/sampling settings, backend/model and failure denominator. Keep upstream replay, RSIGame's patched/padded replay and Recursive Game Creator's native recordings separately labelled even when they share a rubric and formula.

### RSIGame: persistent evidence and retained game checkpoints

[RSIGame v1](https://arxiv.org/html/2609.39045v1) combines evidence-directed game editing, an evolving checklist and separate checkpoint selection; optional guidance starts another stage. Training-free rounds change game artifacts and working context, while separate experience internalization fine-tunes the generator. Neither demonstrates recursive harness-code optimization. The benchmark rubric is hidden, but submission demos remain visible during development. A small free-play check changes interaction paths on existing tasks; it does not establish unseen-game or human-enjoyment generalization.

**Source-inspected mechanism.** At [commit 1214b342](https://github.com/WenyiWU0111/RSIGame/tree/1214b342fce22e97fe19bfc56be189d06f44634b), [checklist state](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/src/rsigame/checklist/checklist_state.py) retains supported findings when a later replay does not observe an item, while tracking staleness and deferral separately. The [issue verifier](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/src/rsigame/controller/verify.py) combines observed persistence/disappearance/non-exercise with the editor's attempted-work report, preserving partial fixes and unknowns. These are model-assisted runtime observations, not authoritative behavioral assertions. Champion selection [compares criterion values on common observed coverage](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/src/rsigame/eval/estimator/aggregate.py); an unobserved criterion is excluded rather than scored zero.

**Stopping and scoring.** The [released default](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/src/rsigame/monitor/live.py#L14-L34) retrospectively selects checkpoints after all 30 development rounds, explicitly identified as the paper-run procedure. Retrospective stopping estimates should not be presented as prospectively avoided calls. Optional live monitoring ends at a round boundary and does not roll the working tree back. The [scoring wrapper](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/src/rsigame/eval/score_game.py) conditionally extends replay duration beyond the benchmark's original cap and records that deviation. Preserve the exact replay/padding configuration and selected build.

**Release and rights.** The [pinned HF release](https://huggingface.co/datasets/RSIGame/RSIGame-TableArtifacts/tree/2735939d5a75c95c6cb67130a9485fbc0e3881cc) lists base/scored game archives, judge records and 19 manifests; intermediate rounds and full recordings are excluded. Source-only arithmetic reproduces their 19 advertised rounded means using the full 140-task denominator, including missing-task zeros. This does not recompute gameplay scores. Five of the current paper's 24 main-result rows are absent from this inspected release. No dataset license is declared in the inspected card/root. [Code Apache-2.0](https://github.com/WenyiWU0111/RSIGame/blob/1214b342fce22e97fe19bfc56be189d06f44634b/LICENSE) does not establish rights to game assets, model weights or external services. The required repair fork and patched GameCraft dependency need separate pins; this code revision is not established as the experimental commit.

**Proposed transfer, unimplemented:** compare last-build return, fixed-budget champion selection and prospective live stopping on an owned fixture containing a regression, an unexercised feature and a failed judge. Keep game-edit search distinct from harness search. No model, engine, benchmark or released test was run here.

### Recursive Game Creator: source-assisted policies and conservative retention

**Source scope:** [paper v2](https://arxiv.org/html/2610.08621v2), with released implementation inspected at [`8284cae`](https://github.com/IMBALDY/RecursiveGameCreator/tree/8284caeac655e8c6c08354a759b97b1599d426fd). No agent, game or evaluator was run. The evolving object is the game project; normal operation does not modify model weights, role prompts or controller code.

The Player reads a source copy, writes `reset(seed, profile)` / `act(state)` policy code and executes real keyboard/pointer actions without per-action model calls. Policies inherit from the retained game, but new versions receive an adaptation call. Equal seeds therefore do not establish equal player skill. Policy completion is not independently verified victory, and three named profiles do not prove diverse human-like behavior. [Policy inheritance and authoring](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/src/game_agent_lite/policy.py#L297-L437)

Behavioral traces and sampled images feed a separate reviewer. The implementation retains a changed candidate only after valid checks/evidence and two opposite A/B presentation orders both prefer it; disagreement, ties or unavailable evidence preserve the incumbent. Citation/hash checks establish evidence identity, not the truth of the review. Ordinary 2 FPS capture cannot certify brief feedback, frame pacing or input latency. [Promotion gate](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/src/game_agent_lite/loop.py#L19-L28), [capture boundary](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/docs/player-policy.md#L196-L213)

**Reproduction boundary:** the released 45-task GameCraft path can score native Player captures through upstream judging/formulas when scoring is separately requested, separately labelled from official input replay. It records `recording_score` with `official_score=null`, and indexes each round's candidate, including rejected candidates. The GameASG adapter runs one round and explicitly leaves strict end-to-end success null when using the test-only evaluator. These are available adapter implementations, not receipts reproducing published headline results. [GameCraft preparation](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/scripts/run_gamecraft_batch.py#L122-L183), [candidate/score records](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/scripts/run_gamecraft_batch.py#L290-L378), [GameASG metrics](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/scripts/run_gameasg_batch.py#L223-L244)

Code is MIT; figures, screenshots and other non-code assets are explicitly excluded unless separately licensed. The inspected repository includes regression-test source and configurations, but `runs/` contains only a placeholder rather than complete paper-run outputs. Benchmark repositories, runtime images and judge/model access remain external dependencies. [Rights](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/README.md#L223-L225), [benchmark dependencies](https://github.com/IMBALDY/RecursiveGameCreator/blob/8284caeac655e8c6c08354a759b97b1599d426fd/docs/benchmarks.md#L1-L5)

**Proposed transfer, unimplemented:** preserve fixed-policy regression tests alongside adapted exploration, separate authoritative gameplay checks from visual preference, and record all attempts/capture modes/costs before testing whether the combined evidence improves retention.

### GameReplica: recover rules before implementing a replica

[GameReplica v1](https://arxiv.org/html/2609.22308v1) adds a distinct task: infer a running game's specification through screenshots, clicks, keys and resets, then deliver a self-contained HTML replica and an inferred rule checklist. Its 125 tasks cover 25 games at five difficulty levels. Sections 3.4–4 evaluate checklist agreement, implementation consistency and visual fidelity separately, using model judges; source-code assessment is not a deterministic behavioral-equivalence oracle. Visual `NA` items leave that score's denominator. Table 1 averages three replications, but its displayed sample standard deviation is across task instances. The “Faithful” failure-analysis category requires HTML, visual score ≥60 and mean implementation/rule score ≥50, not perfect rule recovery. Process-level failure attribution compares trajectories through another model judgment, rather than a controlled causal intervention.

**Inspected release.** The [paper-linked project site](https://qqqqqqby.github.io/GameReplica/) has a corresponding [public showcase repository pinned at `acddd12a`](https://github.com/QQQQQQBY/GameReplica/tree/acddd12a2e8a978cc785dae0ba32f84dd76f0701). Its complete tree contains 401 demo HTML files across eight games and 40 game-level combinations, including 40 originals; these are a showcase subset, not evidence that all 125 task packages or the evaluator were released. Other files include the page, display scripts and manifests, figures, framework illustration and hosting marker. No license file or evaluation runner appears in that inspected tree; repository metadata has no detected license. Public access alone does not settle reuse rights. [The page](https://github.com/QQQQQQBY/GameReplica/blob/acddd12a2e8a978cc785dae0ba32f84dd76f0701/index.html) explicitly averages token/time costs over completed instances. Its [display data](https://github.com/QQQQQQBY/GameReplica/blob/acddd12a2e8a978cc785dae0ba32f84dd76f0701/assets/data.js) and headline text contain different reported leaderboard values, so retain each artifact's revision rather than treating the page as a machine-verifiable reproduction of paper scores.

**GameMap proposed adaptation:** compare fixed screenshots, predetermined action traces and active boundary probes under the same explicit screenshot/action/reset budget and fixed model/runtime/time limits. Split by source game, not difficulty variant alone. Preserve the inferred rule checklist separately from implementation artifacts; require protected held-out interaction traces and explicit failure denominators before claiming mechanics recovery. These are unimplemented experiment controls, not reported GameReplica results.
