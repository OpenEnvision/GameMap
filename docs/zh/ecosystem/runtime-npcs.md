# 设计和评估运行时 NPC

守卫发现玩家，追到一扇关着的门前，然后原地顶着门跑。挑 AI 工具之前，先定这时候守卫该怎么办：等门开、换路，还是收队回岗？后面再看另一类 NPC，负责给玩家指路。

## 选择够用的最小系统

| 面向玩家的需求 | 起点 | 验证内容 |
| --- | --- | --- |
| 可预期的巡逻、清晰的攻击预兆或任务推进 | 手工编写的状态机、行为树或效用规则 | 状态可达、提示可读、切换可重复且能够恢复 |
| 自然措辞或有关世界设定的可选问答 | 手工定义任务状态，按已批准的事实生成回应 | 与当前状态一致、语言支持、延迟以及可用的手工回退 |
| 更长时间跨度的社交或战术决策 | 在限定范围内提出动作的规划器或学习策略 | 场景成功率、状态合法性、受干扰后的恢复和单次运行成本 |

先建立一个小型手工基线。Epic 的[行为树文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-trees-in-unreal-engine)给出了使用决策分支与黑板状态的引擎实现。Park 等人的 [Generative Agents](https://arxiv.org/abs/2304.03442)在社交沙盒中研究了记忆、规划和反思。论文中的可信度结果可以为相近研究问题的消融实验提供思路。任务完整性和上线预算需要另外收集证据。

给守卫先写四个状态：巡逻、追击、搜索、回岗。门关上以后，寻路失败或短时间没走动，就转到搜索或回岗。在同一个房间里试三次：追击时门关了、玩家重新进入视野、守卫最后回到岗位。如果设计只需要这些切换，手写规则就够了。要让玩家感受到守卫会在多条路线或多个目标之间做取舍，再考虑加规划器。

## 由游戏维护权威状态

在引导 NPC 练习中，引擎提供当前路线是否可通行、任务阶段和 NPC 可以透露的知识。策略返回已有提示的 ID、安全路点请求或不采取动作。先根据当前快照校验提议，提交时再确认一次。寻路、奖励、门的状态和保存的进度均由引擎负责。可选的生成措辞作为独立输出检查内容。

| 条件 | 预期行为 | 可观察的检查 |
| --- | --- | --- |
| 路线被挡 | 根据当前任务状态给出可达的替代路线 | 不把锁住的路线标为可通行 |
| 玩家在请求过程中离开或重新加载 | 丢弃过期回应，或针对新状态重新发起请求 | 新会话开始后不会出现旧提示或旧路点 |
| 动作无效或请求超时 | 显示预写提示，让玩家可以继续 | 在规定时限内出现回退，进度仍可继续 |
| 同一请求送达两次 | 使用请求标识，确保游戏效果只生效一次 | 事件日志只记录一次提交，存档与之相符 |
| 内容未经批准、偏离主题或使用不支持的语言 | 返回已本地化的预写回应，或提供受支持的交互方式 | 玩家看到的结果符合既定体验范围 |

存档、回放和事务的边界详见[游戏状态与持久化效果](../evaluation/gameplay-state.md)。使用远程策略时，给每次遭遇设定请求预算，明确数据留存、玩家遇到服务故障时的提示，以及谁能关闭实时功能。用同一构建测试离线或脚本方案。

## 在相同条件下比较行为

收集案例前先写出要检验的主张。例如，变化的措辞能帮助玩家辨认正确路线，又不会增加错误提示或在服务超时时阻断交互。比较预写提示和由生成器表达的同一组提示，保持关卡、任务逻辑和回退固定。若改动规划方法，另设基线独立测试。

保留首次到访、路线被挡、从存档恢复和请求被中断的测试状态。两种方案使用同样的场景 ID、时限和可观察信息。固定构建、内容快照、策略设置和评分规则。把用于调优的提示与留出的测试案例分开。保存有版本的输入和脱敏输出，供复查失败原因。

分别记录任务成功与状态违规，以及人对表达清晰度和角色一致性的评价。记录无协助完成率、超时率、回退率、响应延迟分位数、每次完成交互的成本和各指标的试验次数。评价者使用相同问题，可行时隐藏所用系统。样本很少时，将试玩观察作为定性证据。证据选择和限制报告详见[开发评估指南](../evaluation/development-evaluation.md)。
