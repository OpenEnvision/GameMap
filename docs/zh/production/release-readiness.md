# 验收游戏的候选发布构建

最后一次修复产生的也是新候选版本，哪怕文件名没变。团队要决定的是：旧验收结果还有哪些有效，哪些玩家路径必须重跑。小团队先抓一个支持平台和一条核心循环，让确切的可安装构建对应上检查记录，再逐个覆盖其他目标。

## 确认测试的是哪个构建

记录源码提交、引擎与导出模板版本、预设、目标系统和架构、依赖以及产物校验值。把安装说明和版本说明与构建产物放在一起。签名凭据和生产密钥应留在包与构建日志之外。

以 [Fuse Courier 练习](../guides/practical-guide.md)为例，从干净的源码副本导出，使用已安装的 Godot 版本及匹配的导出模板。记录预设名称，交付可执行文件及独立的数据包（如果有）。Godot 区分可玩的项目导出与只导出项目数据。实际的预设与平台操作参见 [Godot 导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html)。

## 走完玩家的安装和更新路径

| 检查项 | 在候选版本上验证 | 保留证据 |
| --- | --- | --- |
| 全新安装 | 在干净的用户配置下，通过实际分发入口安装。启动、玩完一轮、返回菜单、重新启动，再卸载。 | 产物哈希、目标设备与系统、日志、预期和实际结果 |
| 更新与存档 | 使用上一受支持版本的真实存档副本。更新后从预期状态继续，再用另一份副本验证恢复。 | 存档格式版本、原始样本、迁移结果和恢复步骤 |
| 输入与呈现 | 用承诺支持的每种设备操作菜单。检查焦点、已支持的按键重映射、字号、适用的字幕，以及是否存在只靠颜色或声音传达的关键信息。 | 平台、输入、语言、画面尺寸和失败界面或交互 |
| 性能 | 在目标设备上重复运行压力最大的代表性场景。记录预热、采集区间、帧时间分布与内存峰值。 | 场景或回放、设置、硬件、样本数和采集前确定的阈值 |
| 故障与恢复 | 中断一个受支持的在线依赖，或挂起并恢复游戏。离线游戏应在无法联网时验证核心循环。 | 实际错误、玩家可执行的恢复操作、效果是否重复或丢失、重新打开结果 |
| 打包与宣传 | 对照候选版本核查交付包、署名和商店素材。确认宣传中的功能和平台支持确实出现在构建里。 | 构建内容、来源与许可台账、从该候选构建取得的截图或片段标识 |

Fuse Courier 的首个候选版本可以检查一次全新启动、一次获胜、两种失败、暂停与继续、连续三次重试、退出及再次启动。游戏确实没有存档或联网功能时，再将对应项写为“不适用”。参考 [Xbox 无障碍指南](https://learn.microsoft.com/en-us/xbox/accessibility/guidelines)确定输入、字幕和视觉提示检查。较大的项目可另建设备、输入和语言矩阵。

## 补齐来源和分发记录

每项随游戏交付的资产或服务都应记录来源、版本或生成记录、允许的用途、必要的署名和负责人。分别跟踪源码、模型、贴图、字体、配音、音乐和运行时服务。记录各提供方实际适用的条款，在送审前处理未决事项。参见[资产 API 条款](../assets/api-terms.md)和[资产验证](../assets/validation.md)。

如果发到 Steam，针对准备提交的构建核对当前[构建与商店审核](https://partner.steamgames.com/doc/store/review_process)及[内容调查表](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)。Steam 区分制作期间为玩家生成并随产品交付的 AI 内容，以及游戏运行中实时生成的 AI 内容。按当前调查表记录实际交付内容和适用的运行时控制。团队内部验收与商店审核分别回答不同的问题。

提交前，让构建者以外的人按安装说明，从真实发行渠道装一遍。Steam 的[审阅指南](https://partner.steamgames.com/doc/store/review_process)明确要求通过 Steam 全新安装，并检查商店宣称支持的功能；它也区分非语言音频的无障碍字幕和对白字幕。给审阅人一条简短路线，说明每项承诺的功能从哪里进入；菜单复选框或商店截图不能证明包内功能可用。

临时修复到来时，把改动文件及受影响依赖附在候选决策上。字体或布局改动，交回界面 QA 核对相关语言、字号和菜单焦点路径；碰撞或场景改动，交回玩法负责人重走受影响路线；存档模式变化，重新打开支持的旧存档迁移和恢复检查；打包变化，则重做渠道安装与干净启动。未受影响的旧结果仍保留原构建身份，并记录为什么可以沿用，不要改个标签就当成新产物上跑过。负责人无法界定影响范围时，先扩大相关检查，再签收。

## 明确发布决策

为每项检查指定负责人，记录通过、失败或未测，并附证据。事先约定哪些问题阻止发布。对小型游戏，全新安装后无法启动、存档不可恢复、必需的输入方式走不通，以及随包资产权限未解决，都适合作为阻断项。在新候选构建上复测修复，并关联原失败记录。发布更新前应指出上一个已知可用版本，用实际存档和服务端版本验证恢复方案。

把构建 ID、源码提交、产物哈希、测试矩阵、阻断项及负责人、送审清单和恢复说明放在一起。截图可以说明候选版本的画面，明确的构建和测试步骤能让别人验证实际行为。打包、部署或补丁操作需要单独证据时，参见[生产任务单](work-orders.md)。
