# 编码智能体与游戏工具集成：来源审阅笔记

分别选择模型、执行框架、领域技能和引擎接口。下列组合提供了实现来源和设置说明的链接。

## 必须区分的概念

- **模型 ≠ 执行框架 ≠ 技能 ≠ MCP。** 模型产生决策；执行框架管理工具循环、上下文和执行环境。技能封装领域流程，而 MCP 为客户端调用工具提供接口。游戏开发成果取决于全部四层以及真实的引擎反馈。不能根据模型名称就把资源视为可互换。
- **将 DeepSeek 作为后端。** [官方 Anthropic API 兼容指南](https://api-docs.deepseek.com/guides/anthropic_api/)确认了兼容端点和 Claude Code 集成，并列出被忽略、被映射或部分支持的字段。本条目涵盖的是提供商集成文档。2026-10-19 的一次定向检查确认，另行发布的 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/README.md#L1-L15)是官方通用开发者预览版；它的存在并不能证明具有游戏专用引擎支持，也不会让本条文档条目变成执行框架条目。该文档中的模型映射可能变化；本目录不固定当前别名。
- **代码测试 ≠ 试玩测试。** 构建和单元测试检查软件行为。视觉、输入、碰撞、胜负状态、游戏手感和持续运行需要来自运行中游戏的反馈。通用 SWE-bench 分数无法直接对游戏开发能力进行排名。
- **编辑器桥接 ≠ 引擎厂商官方支持。** 所列 Unity、Godot、Blender 和 UE 桥接均为独立项目。应分别检查其功能、维护情况、许可证和引擎兼容性。

## 规划游戏开发工作流

1. **先选择可观察的反馈循环。** 浏览器游戏提供截图、输入、控制台输出、网络检查和测试反馈。对于原生引擎，应先建立可用的无头、编辑器或 MCP 工作流，再让智能体扩展功能。
2. **将编辑器状态视为数据。** 修改前先读取场景对象 ID、组件、材质、资产引用和编译状态。对象名称不是稳定标识；提示词不应猜测当前场景。
3. **为每一步定义证据。** 代码变更记录构建和测试；场景变更记录截图、层级和属性差异；玩法记录输入轨迹和预期状态；导出则记录在目标运行时中的成功启动。
4. **保留可重复的流程。** 把成功的精灵、GLB、场景和测试工作流整理为包含脚本和示例的技能。将项目约束记录在 AGENTS.md 中，而不是不断扩充一个庞大的提示词。
5. **比较智能体时控制变量。** 记录模型、执行框架、引擎和工具版本、预算、随机种子、任务及验收标准。更换模型时保持任务和验证环境不变，使差异能够得到有意义的归因。
