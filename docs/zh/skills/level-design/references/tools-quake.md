## 1. 选择工作流程，而非时髦标志

询问：

- 游戏是否已经提供练习所需机制？
- 工具能否表达所需空间与实体？
- 设计者能多快地搭建、运行、观察与修改？
- 是否有可用的导入／构建／打包流水线？
- 有哪些平台、许可与社区支持？

原书推荐通过 Doom／Quake 模组学习，因为规则、资源、敌人与调校已经存在。通用引擎提供更广可能性，却可能先需要大量系统工作。

对于 2D，内置工具可能已足够；Tiled 和 LDtk 等独立编辑器支持许多自定义流水线。对于 3D，应区分关卡搭建工具与资源建模工具。Blender 适合资源和某些搭建流程，但建模流程并不自动提供可玩迭代、实体、碰撞或脚本。

应将定价、维护、插件兼容性和“最佳工具”主张视为特定快照中的信息。安装或承诺支持之前，核实当前文档。

## 2. TrenchBroom 的适用性

TrenchBroom 是跨平台、基于笔刷的编辑器，具有以 3D 为中心的工作流程，以及凸笔刷验证、裁切、缩放和纹理工具。

对于非 Quake 项目，分别验证三项集成：

1. **几何：** 目标能否导入 MAP、编译 BSP 或使用导出内容？
2. **资源：** 纹理、材质与模型引用能否正确解析？
3. **实体：** 摆放的物件与键／值属性能否变成实际游戏对象？

OBJ 导出可能保留几何却丢失实体数据。网格导入成功，并不能证明玩法流水线有效。

快照列出了 Godot 的 FuncGodot、数个 Unity 导入器，以及 Unreal 的 HammUEr 等集成。这些是线索，不是兼容性保证。检查目标版本、维护、许可、碰撞、材质、实体与重新导入行为。

若搭建与标注是 TrenchBroom 的优势，就用于这些工作；复杂编排可能更适合在目标引擎中原生制作。

## 3. 验证最小端到端流水线

搭建大地图之前：

1. 配置目标游戏、路径、地图格式与实体定义。
2. 制作带起点和简单灯光的封闭测试房间。
3. 添加一种纹理和一个有代表性的实体／交互。
4. 构建或导入。
5. 用真实控制器运行。
6. 修改某项内容，验证重新导入／重新构建。
7. 打包，并从单独位置运行。

不要仅因原书提供链接就自动安装可执行文件或插件。遵守项目审批与依赖安全规则。

## 4. Quake 制图流水线

典型经典流水线使用：

- 可编辑的 MAP 源文件。
- 合适的游戏／模组 FGD 定义与纹理来源。
- 编译器工具链。
- 兼容引擎／源码移植版。
- 合法取得的必需基础游戏数据。

来源为 Quake 推荐 EricW 工具：

- **qbsp：** 构建编译后的几何，并报告泄漏等相关错误。
- **vis：** 计算用于可见性管理的潜在可见集合。
- **light：** 构建照明信息。

标志参数与限制应查阅实际工具版本的文档。快速迭代设置与最终质量设置可能不同；记录所用配置。

### 按阶段诊断

| 症状               | 首先检查                                   |
| ------------------ | ------------------------------------------ |
| 地图无法编译       | 格式、无效几何、路径、错误日志             |
| 泄漏报告           | 密封、实体位置、点文件／调试输出           |
| 缺失纹理           | 来源 WAD／材质引用与编译／导入配置         |
| 实体缺失或不活动   | FGD／运行时不匹配、classname、键、目标连接 |
| 意外黑暗           | 灯光、编译阶段、受支持设置、引擎兼容性     |
| 仅在作者环境中有效 | 缺失依赖、资源路径、包布局                 |

Quake 纹理 WAD 不是 Doom WAD。在经典 Quake 流程中，所用纹理通常嵌入编译后的 BSP；应核实自定义流水线与外部资源要求，而不是凭扩展名推断打包方式。

### 用一个房间检查整条链

这项 GameMap 实践补充采用维护者的 [TrenchBroom 参考手册](https://trenchbroom.github.io/manual/latest/)，以及 ericw-tools 的 [QBSP](https://ericwa.github.io/ericw-tools/doc/qbsp.html)、[VIS](https://ericwa.github.io/ericw-tools/doc/vis.html) 和 [LIGHT](https://ericwa.github.io/ericw-tools/doc/light.html) 参考文档。它提供测试步骤，不声称某个具体安装环境已经通过。

写下已安装的编辑器与编译器发布版本、源码移植引擎版本、所选游戏／模组、MAP 格式、纹理 WAD 路径和运行时 maps 目录。三个编译器可执行文件应来自同一工具发布版本。编辑器能找到纹理，并不自动证明编译器也能解析其 WAD。

1. 将一个小型封闭房间保存为 `practice_room.map`。使用所选游戏的定义，将 `info_player_start` 放在不与实心笔刷相交的位置，添加一个 `light`，并为原版 Quake 测试放置可接近的 `weapon_nailgun`。使用已配置 WAD 中一种已知纹理。实体类别不同的模组应选择自己的代表性拾取物。
2. 在地图工作目录中依次运行下列命令，只有前一个成功后才继续。若工具不在命令搜索路径中，使用已记录的可执行文件路径。

```sh
qbsp -leaktest practice_room.map
vis practice_room.bsp
light practice_room.bsp
```

QBSP 构建 BSP；VIS 读取对应的 PRT 门户文件，更新 BSP 中的可见性；LIGHT 更新其照明。保留命令输出。如果 QBSP 报告泄漏，在 TrenchBroom 中加载其点文件，沿着从内部通向虚空的线寻找开口。修复密封，而不是添加 `-nofill` 来掩盖失败的测试。

3. 将新构建的 `practice_room.bsp` 及任何必需的照明附属文件复制到已记录的运行时目录。通过引擎配置启动这张地图。检查起始位置、墙面碰撞、纹理、可见的光影响应，以及拾取物对物品栏或 HUD 的影响。编辑器截图不能确立这些运行时结果。
4. 移动拾取物，并改变一处易于识别的墙面特征。重新执行三个构建阶段，在引擎中确认两项变化。若仍是旧位置，先检查源文件、输出时间戳、复制目标和实际启动的游戏目录，再考虑修改玩法代码。

可在副本中做一次有用的反向检查：在外围结构墙上打开一个洞，确认 `-leaktest` 失败。恢复墙面、重新构建后再打包。最后按下文的简单地图包步骤制作压缩包，并安装到单独环境中；商业基础游戏数据不应进入压缩包。

## 5. Quake 模组与资源

来源描述了：

- **Arcane Dimensions：** 扩展的单人工具包。
- **Alkaline：** 偏科幻／基地风格的内容与系统。
- **Copper：** 对原版 Quake 相对克制的改良。
- **progs_dump：** 面向制图者的功能，同时总体保留熟悉的武器与敌人。
- **2021 再发行版 Horde：** 特定模式的实体配置与管理器。

对于任何模组：

1. 明确确切版本与支持引擎。
2. 使用匹配的 FGD 和制图文档。
3. 研究随附示例／测试地图。
4. 确定发布形式是带依赖的独立包，还是附加包。
5. 保留所需许可，避免意外覆盖上级模组。

不要假定原书提到的 2022 年 1 月版本仍是最新版。

来源描述了一些社区中宽松的资源共享习惯。 **社区礼仪不是法律许可。** 在要求署名时，署名是必要的，但不能替代授权。优先使用权利明确的官方资源发布。

## 6. Quake 打包：选择一种连贯结构

使用不带空格的小写名称。优先使用广泛支持的 ZIP。

### 简单地图包

对于仅含地图相关文件的包，来源接受将文件置于 ZIP 根目录：

- mymap.bsp
- mymap.lit，如需要
- mymap_readme.txt
- 可选的、获准提供的源文件

说明应解压到哪个 maps 目录，以及如何启动。

### 完整模组包

将模组目录放入 ZIP 内：

- mymod/maps/mymap.bsp
- mymod/maps/mymap.lit
- mymod/gfx/env/skybox-face.tga
- mymod/sound/mymod/soundname.wav
- mymod/progs/modelname.mdl
- mymod/progs.dat，如需要自定义游戏代码
- mymod/readme.txt

文件夹是 **sound** ，不是“sounds”。将地图文件直接放在 maps 中，而非额外嵌套的地图目录。这些名称仅作示例；实际天空盒后缀必须与引擎匹配。

PAK 文件可以保留预期内部结构，但需要自身的打包流程。

### 部分附加包

部分包可在根目录包含 maps、gfx、sound 及相关子目录，用于解压到已有模组。明确说明依赖与目标位置。

没有有意、已记录且获授权的理由时，不要覆盖上级模组的代码或资源。不要对部分文件使用完整模组结构，对其他文件却使用散装地图文件。

### 测试

仅依据 readme，将 ZIP 安装到干净／单独环境中。启动、完成、重试并检查缺失文件。切勿仅因商业基础游戏数据存在于本地，就将其打包。

## 7. 理解文件格式的职责

### FGD：面向编辑器的实体定义

FGD 描述实体、字段、选项、标志、默认值和编辑器呈现。它帮助编辑器提供运行时游戏的词汇。

它 **不** 实现实体的运行时行为。在 FGD 中添加 classname 或复选框，不会在游戏中创建支撑代码。

让定义与实际模组保持同步。开放大量属性之前，先使用小型测试实体。

### MAP：可编辑的文本几何与实体

Quake 家族 MAP 文件通常组合：

- 通过键／值属性表达的实体。
- worldspawn 中的世界几何。
- 由平面定义的凸笔刷。
- 面纹理信息。

格式变体各不相同，包括纹理投影惯例。解析或导出之前，确认实际变体。编译后的 BSP 是另一种产物；不要把可编辑源文件与可玩输出视为可互换。

实现解析器时，验证语法、笔刷朝向、纹理轴、属性与有代表性的往返转换。查阅规格，而不是从一个示例立方体猜测。

### MDL：Quake 1 模型数据

链接的 MDL 文章是 David Henry 的存档技术规格，标为 **GNU 自由文档许可证** ，示例代码另有许可。

独立措辞的入门说明：

- 二进制头与计数描述皮肤、纹理坐标、三角形和动画帧。
- 顶点数据经过量化，通过缩放／平移重建。
- 纹理数据使用调色板。
- 纹理接缝与正／背面三角形关系需要特殊处理。
- 动画混合帧数据，并使用存储的法线引用。

本技能不转载其代码或表格。若实现加载器，请阅读原文、保留适用声明，并在分配或索引之前验证标识符、版本、字节序、计数、偏移、截断和算术边界。存档示例并不是经过安全审查的解析器。

MDL 扩展名并不代表跨游戏通用、可互换的模型格式。

## 8. 按需使用资源列表

- **资源：** 来源指向 Kenney、OpenGameArt、Quaternius、Poly Haven 和 ambientCG 等资源库。检查每项实际资源的权利与技术适用性。
- **演讲：** 分为一般设计、战斗和非线性／沙盒设计。先读说明，再检查原演讲，之后才能把它作为证据。
- **书籍：** 区分通才理论、行业类型专门建议、美术／参考书和建筑。宽泛理论书与狭义遭遇指南解决不同问题。
- **社区：** 特定游戏群体通常最适合工具排障与实际试玩测试；美术社区适合视觉评议；评论平台支持其他类型分析。

不要声称已看完这些目录链接的所有内容。参考书目是发现工具，不是继承而来的证据。

## 交付物

推荐最简工具链并说明其假设，提供已验证的测试地图流水线、已知兼容性缺口、资源来源和可复现的包。区分当前验证与从快照复制的建议。
