# 脚本、导航与门

来源：[脚本](https://book.leveldesignbook.com/process/scripting)、[（占位）导航](https://book.leveldesignbook.com/process/scripting/nav)、[门](https://book.leveldesignbook.com/process/scripting/doors)。依据 CC BY-NC-SA 4.0 改编与重组。导航来源为占位页；下列实现检查明确属于实用扩展，而非原书已完成的导航章节。

## 1. 选择语法之前先描述行为

**关卡脚本** 协调局部事件、交互、目标、敌人与世界变化。它可以使用代码、可视化图、实体连接、时间轴或编辑器属性。

从可读的行为描述开始：

- **条件：** 什么使某事具备发生资格？
- **事件：** 什么引发一次尝试？
- **动作：** 什么发生变化？
- **反馈：** 玩家能察觉什么？
- **持久化：** 之后哪些事实保持成立？
- **恢复：** 中断、失败或重新进入后会发生什么？

例如：“玩家进入庭院后，关闭闸门一次，提示伏击，并在所有必需敌人被击败后解锁出口。”这仍留下关键问题：如果敌人无法到达玩家、玩家在关闭前离开，或中途加载存档，会怎样？

不要把缺失的设计决策藏进庞大的可视化图中。

## 2. 使用项目现有工具制作原型

添加新抽象之前，先检查可用触发器类型、交互事件、实体定向、状态存储、调试与重置方法。

- 为不确定行为保留小型测试地图或场景。
- 使用清晰名称与可检查的连接。
- 让时序和依赖足够可见，便于调试。
- 对一次性问题，优先使用简单的局部机制，而非项目级系统。
- 反过来，重复行为在需求明确后，可能值得提取为共享组件。

“可视化脚本”不意味着不涉及编程概念。状态、顺序、条件、依赖和归属仍然重要。

## 3. 实用状态规格

下表是为稳健实现而作的改编：

| 状态    | 进入条件     | 行为        | 退出条件   | 重新进入／存档行为  |
| ----- | -------- | --------- | ------ | ---------- |
| 可用    | 前置条件满足   | 提示可交互     | 玩家激活   | 恢复可用性      |
| 活跃    | 接受激活     | 运行遭遇／事件   | 完成或失败  | 恢复，或有意重新开始 |
| 已完成   | 必需条件成立   | 开放路线／授予结果 | 通常持久保留 | 不重复奖励／事件   |
| 失败／中断 | 已定义的异常条件 | 恢复、重置或报告  | 恢复规则   | 避免进度丢失或软锁  |

只使用行为所需的状态。装饰性灯光开关不需要遭遇框架。

区分：

- 触发器触发与动作完成。
- 事件发生一次与状态持续成立。
- 延迟与可能永远不成立的条件。
- 局部实体状态与全局任务状态。
- 动画播放到结尾与玩家获得可用路线。

## 4. 触发器与遭遇时序

测试：

- 进入、离开与重新进入。
- 高速穿过或从意外方向穿过。
- 激活两次，包括在过渡期间激活。
- 敌人死亡、消失或掉出关卡。
- 玩家死亡、读档、重启与放弃。
- 可选路线绕过触发器。
- 在支持的情况下，多于一个相关角色进入。

若推进依赖敌人完成条件，应定义哪些敌人计数，以及某个敌人不可达时如何处理。不要让隐形计数器悄然变成永久锁。

用反馈解释有意义的状态变化。声音、移动、光、目标更新与可见几何能传达不同方面；避免要求玩家推断看不见的标志位。

## 5. 导航：区分层次

- **寻路引导：** 玩家对去哪里的理解。
- **可通行性：** 几何与移动规则允许什么。
- **AI 导航：** 智能体如何表示并沿路线行动。
- **脚本：** 路径、目标或行为何时变得可用。

可见路线可能在机制上受阻。有效的导航网格仍可能导致糟糕的遭遇行为。

由于原书导航页面未完成，实际 API、智能体设置、动态更新、连接和调试应查阅目标引擎文档。

实用检查：

- 正确的智能体尺寸与净空。
- 楼梯、坡道、窄缝、落差与特殊移动。
- 门的过渡与动态封锁路线。
- 追击、撤退、拥挤与不可达目标。
- 运行时变化是否按预期更新导航。

除非确实观察到，否则不要声称已重建导航网格或 AI 路线已成功。

## 6. 门是系统问题

一扇门涉及几何、碰撞、动画、音频、输入、AI、导航、故事、持久化，可能还涉及联网。静态网格只是其中一部分。

### 门的简报

**目的**

- 限制推进、分隔可见性、支撑潜行、点缀节奏，还是提供普通流线？
- 是否必须有一扇可运作的门，还是开口更合适？

**交互**

- 自动、靠近、按钮、使用动作、钥匙，还是脚本控制？
- 两侧都可操作吗？
- 什么告诉玩家它可用、已锁，或永久只是装饰？
- 运动期间重复交互会怎样？

**移动与碰撞**

- 摆动、滑动、旋转、破裂，还是消失？
- 向哪个方向开启？
- 它能否推动、夹住、阻挡或伤害角色？
- 每种状态下，玩家能否透过它射击、看见或听见？
- 镜头或携带物是否会发生碰撞？

**其他角色**

- 敌人能否开门、关门、堵门、破门或跟随穿过？
- 门运动时，他们的导航会怎样？
- 同伴是否可能被困在另一侧？

**状态**

- 将锁定／解锁与开启／关闭、运动／停止分开。
- 只有在支持时才定义被毁、卡住或禁用状态。
- 明确重生、存档／读档与全局任务变化。
- 应用全局事件时，保留各扇门有意设置的独立状态。

### 具体故障追溯

一个任务锁住所有门，完成后又将它们全部解锁。原本锁住的门现在也被意外打开，因为脚本恢复了统一条件，而非每扇门之前的状态。

来源用 Witcher 3 的一个事件说明这种依赖。一般教训是区分临时覆盖与底层状态，并测试恢复，而不是想当然。

## 7. 验证矩阵

对任何有实质影响的脚本物件，覆盖相关组合：

- 初始状态与完成之后。
- 正常交互与重复交互。
- 从每个允许的侧面接近。
- 玩家死亡、读档与重启。
- 绕过路线与返回。
- AI 或同伴参与。
- 运动或事件被中断。
- 若游戏支持，多人权限归属与重新连接。

这是针对实现任务的实用扩展。不要要求无关系统，也不要悄然给单人项目添加多人功能。
