# 白盒、体块、地景、构图与度量

## 1. 让空间假设易于修改

**白盒** 、 **块面模型** 或 **灰盒** 是用低成本形状构成的可玩草稿。其目的是在细节使修改变得昂贵之前，测试基础关系。

它必须包含问题所依赖的内容：

- 有代表性的玩家移动、镜头、碰撞与交互。
- 重要高差、视野、路线连接与边界。
- 必要的敌人行为、目标和临时脚本事件。
- 足以理解预期信息的照明与区分标识。

它不必通体灰色。临时颜色、标签、道具或声音，只要传达了测试必需的信息，就是合适的。反过来，精致资源也不能证明白盒有效。

### 有用的迭代循环

1. 选定一个不确定点：“玩家能否在投入行动之前发现下方的侧袭路线？”
2. 构建包含它的最小连通情境。
3. 用实际控制器游玩，而不只是用编辑器镜头查看。
4. 观察行为，区分空间失效与规则或信息缺失。
5. 修改并重复；在关系可信之前保持低成本可编辑性。

不要在验证反复使用的空间语法之前，就搭建整套战役。

## 2. 体块：组织实体与空体积

**体块** 关注大型形体的排列、尺度和关系。对体块之间空间的设计，应与对体块本身同样用心。

从以下内容着手：

- 主要地面高度与大体积。
- 重要开口、门限与连接。
- 视线遮挡物、俯瞰点与鲜明轮廓。
- 只有在大关系成立后，才添加较小的辅助形体。

询问玩家能否区分前景、可进入的中景、远处目的地与不可玩的背景。大型装饰形体可能无意间暗示一条不可进入的路线。

**示例：** 庭院视觉上令人震撼，却玩起来平淡。添加道具前，先测试抬高的入口、被遮挡的侧路，以及能改变玩家所知与所能的俯瞰点。

## 3. 地景是可玩的组织，而非地形噪声

从地貌与关系思考：山脊、山谷、坡地、高台、盆地、水体、植被、路径和人工边缘。

用地形来：

- 显露和隐藏目的地。
- 引导移动，而不必处处围墙。
- 提供不同进路和暴露程度的变化。
- 分隔区域，建立令人难忘的过渡。

检查：

- 控制器实际处理坡度与台阶的能力。
- 可通行地面与装饰地面的区分。
- 坠落恢复与意外攀爬路线。
- AI 导航、碰撞接缝与植被可读性。
- 在写实性重要之处，水体和排水是否在空间上合理。
- 远距离可见性、流式加载与性能。

依据拓扑和工具选择高度场、网格、笔刷或混合方法。高度场适合广阔地形，但无法单独表达所有悬挑或叠层空间。

景观建筑有助于研究序列、围合、路径、种植、使用与维护，而不只是收集风景图片。

## 4. 在镜头可自由离开的空间中构图

构图组织视觉关系。精心布置的视图与可通行的 3D 构图有关联，却不等同。

- 评估入口、接近过程、移动视野、反向视野和战斗视野。
- 用地标和鲜明的大形体作为定向参照。
- 借助尺度、轮廓、纵深、明度、框景、运动与对比建立层级。
- 赋予远景游玩或解读上的目的，而不是把它做成强制观看的明信片。

来源质疑关于 **引导线** 的简单化说法。截图中的一条线并不保证自由移动的玩家会沿着它看。应把这类假设当作可测试的可能性，而非眼动追踪事实。

避免只优化一个宣传镜头，而让正常游玩产生遮挡、平淡感或误导路线。

## 5. 瞭望与庇护

**瞭望** 关乎观察全局的能力； **庇护** 关乎保护或隐蔽。二者的关系可以帮助设计整备区、门限、俯瞰点与进入危险的过渡。

区分：

- 感知到的安全。
- 实际机制上的保护。
- 从该位置能够获得的信息。
- 留在那里或继续前进的成本。

受保护的俯瞰点可以让玩家在进入暴露空间前规划行动。它是否令人感到安全，取决于镜头、威胁、文化与过往经验。不要将该理论说成人类偏好的普适解释，或优秀设计的保证。

## 6. 度量是与机制经过测试的约定

**度量** 是有用的尺寸与游玩量值：净空、高度、移动距离、范围、时间及相关数值。

不要将现实尺寸或另一款游戏的数值直接当作权威默认值。镜头视野、碰撞体积、动画、移动加速度、跳跃规则和输入容错都会改变结果。

### 搭建度量测试场

| 测试    | 记录                      |
| ----- | ----------------------- |
| 门洞与走廊 | 最小通行尺寸、舒适通行尺寸、转向与镜头净空   |
| 楼梯与坡道 | 台阶极限、坡度极限、碰撞行为、移动平顺性    |
| 跳跃与下落 | 可重复达到的距离、极限距离、落地容错、坠落后果 |
| 掩体    | 站立／蹲伏视线、开火起点、边缘暴露、镜头偏差  |
| 交互    | 可及距离、朝向要求、可用空间、受阻行为     |
| 敌人移动  | 智能体尺寸、转向、连接、追击与拥挤       |
| 行进    | 正常、冲刺、谨慎和战斗移动下的时间       |

区分理论最大值、专家可重复的极限与可靠的普通动作。应围绕目标受众的条件构建关卡，而不是作者的一次完美尝试。

记录单位、控制器／配置版本、测试条件和证据。改变移动或镜头设置可能使早先测量失效。

## 7. 网格与模块化套件

网格支持对齐、可重复搭建与协作。它是工具，不是强迫所有关系塞进同一模块的理由。

制作大型套件之前：

1. 确定尺度、轴心约定、吸附步长与连接规则。
2. 制作一个小型套件，覆盖真实测试房间及其过渡。
3. 测试转角、门洞、楼梯、地面变化、端部与特殊接合处。
4. 检查碰撞、接缝、材质尺度、照明与导航。
5. 只有在试点揭示缺失部件后才扩展。

模块化以部分独特控制力换取复用与一致性。当套件无法经济地表达有意义的关系时，应使用定制部件。

不要围绕尚未经受控制器测试的尺寸定稿美术套件。

## 8. Doom 与 Quake 数据：作为特定游戏参考使用

来源页面包含尺寸、武器、伤害、怪物、移动及相关制图数据。这些是参考表，而非通用调校标准。

- 明确游戏、引擎／源码移植版、模组、难度设置及变更的机制。
- 区分地图单位与物理单位。
- 在战斗中验证表面上的数值优势：瞄准、闪避、敌人内斗、掩体、垂直分隔与敌人组合都会影响实际结果。
- 衍生自 Doom 和 Quake 的引擎具有不同的几何与移动假设。源码移植版的扩展又可能改变这些假设。
- 查阅相关版本的链接表格；不要悄然将数值移植到另一引擎。

## 白盒阶段结束前的问题

以下是建议的决策检查，不是原作规定的普适里程碑：

- 预期活动是否能够从进入一直玩到完成？
- 正常游玩时，重要空间关系是否可以理解？
- 度量与核心机制假设是否已有记录？
- 风险最高的路径、重试与替代进路是否已经实际测试？
- 是否有足够证据支持投入成本更高的美术与脚本？

如果没有，应指出不确定性，而不是宣布关卡“只差打磨就完成了”。
