# 优化、文档、打包与发布

来源：[优化](https://book.leveldesignbook.com/process/env-art/optimization)、[发布](https://book.leveldesignbook.com/process/release)。依据 CC BY-NC-SA 4.0 改编与重组。来源中的引擎命令、平台示例和数值预算取决于版本；请针对实际项目核实。

## 1. 尽早规划可行性；依据证据优化

优化诊断性能问题并改善资源使用，涉及设计、编程、美术、技术美术、音频与制作管理。

**问题：** 高成本关卡可能超出项目能力，而过早优化可能在打磨后来会被删除的内容。

**示例：** 一场战斗要求大量寻路敌人在可见范围很大的城市中活动。问题可能出在遭遇范围、AI 实现、渲染、内存，或多项叠加。

**应对：** 尽早确定目标平台和可行范围，为高成本关系制作原型，并在选择干预前进行性能剖析。

记录：

- 目标硬件、分辨率、质量设置与帧时间目标。
- 关卡大小、密度、开放程度、镜头及流式加载假设。
- 有代表性的最坏情况视野与活动。
- 测量所用构建版本与测试条件。

## 2. 区分预算

- **内存：** 资源、运行时数据、重复、驻留与加载。
- **CPU：** 模拟、脚本、AI、物理、音频、提交及相关工作。
- **GPU：** 几何、着色、照明、阴影、透明与图像处理。
- **加载／流式加载：** 所需数据能否及时可用，且不造成破坏体验的停顿。

低帧率并不能指出哪项预算超标。平均 FPS 可能掩盖严重尖峰；应检查帧时间与代表性事件。

## 3. 性能剖析流程

1. 在已知构建版本中复现具体卡顿。
2. 在相关硬件上采集代表性数据。
3. 找出主要开销与合理原因。
4. 作针对性修改。
5. 在相同条件下比较。
6. 检查视觉、玩法、内存与加载退化。
7. 记录剩余不确定性。

使用引擎当前的性能剖析工具。原书提供 Unity 与 Unreal 示例，但未经核查已安装版本，不要照抄旧命令或界面路径。

不要伪造性能采样，也不要声称未经测量的编辑带来了提升。

### 针对一次疑似卡顿的采样卡

进行 GameMap 实践对照时，选择一条短路线，例如起点 → 进入遭遇 → 转向出口 → 重试。在路线上标出出问题的事件。比较构建之前先确定预热与采样时长；小型练习可从预热 10 秒、采样 60 秒开始调整，这并非性能标准。冷启动加载应与预热后的通行分开测试。

| 记录项                                           | 基线版本            | 候选修改              |
| ------------------------------------------------ | ------------------- | --------------------- |
| 构建、引擎版本、采样文件                         | ___                 | ___                   |
| 硬件、电源模式、分辨率、质量、帧率上限／VSync    | ___                 | 保持相同，或说明：___ |
| 初始状态、路线、输入序列、支持时使用的种子       | ___                 | 保持相同，或说明：___ |
| 预热、采样时长、重复次数                         | ___                 | ___                   |
| 帧时间：中位数、第 95 百分位、最大尖峰及对应事件 | ___ ms／___ ms／___ | ___ ms／___ ms／___   |
| 可获取时记录主要 CPU／GPU 工作与峰值内存         | ___                 | ___                   |
| 已检查的玩法、画面及加载退化                     | ___                 | ___                   |

第 95 百分位指 95% 的采样帧不超过的帧时间。仍需同时查看事件记录：即使多数帧很快，单次长停顿也可能很重要。保留各次采样，不要只汇报最好的一次。缺少测量值时留空，不填写为零。

如果暂停 NPC 更新后遭遇尖峰消失，应借助采样定位高成本工作。候选方案可能是在保留敌人的同时，减少不必要的路径重算。修改后重新检查追逐、攻击时机和路线完成情况；空竞技场并不是等价但更快的遭遇。若代码智能体提出修改，将其改动与实测结果分开保留，不要与其预测混为一谈。

## 4. 让干预匹配瓶颈

### CPU 候选问题

- 活跃实体过多，或更新频率不必要地过高。
- 高成本或重复的脚本工作。
- AI／寻路的密度与复杂度。
- 物理与碰撞工作量。
- 实体创建／销毁或加载行为。

可能的应对包括仅激活相关内容、简化工作、重设计遭遇范围和修复代码。禁用敌人可能证明一个假设，却不自动成为可接受的最终设计。

### GPU 候选问题

- 可见几何成本高，或提交过多。
- 材质／着色器复杂度。
- 动态照明与阴影。
- 透明与叠加效果。
- 可见性管理不足。

可能的应对：

- 对兼容几何进行批处理。
- 对重复网格／材质组合进行实例化。
- 适当降低远处对象的细节。
- 视锥或遮挡剔除。
- 更简单的着色器、照明、阴影或效果。
- 改善资源／材质组织。

**批处理** 合并兼容提交； **实例化** 高效重复兼容几何。具体细节与取舍取决于引擎。

纹理图集或合并网格可能降低某些成本，却恶化灵活性、内存驻留或剔除。更多优化机制并不自动意味着更快。

### 内存与流式加载候选问题

- 过大或过多的独有资源。
- 不必要的同时驻留。
- 重复数据或分组不佳的内容。
- 过晚请求数据的大规模过渡。

当流式加载是基础需求时，应共同设计路线、可见性与加载边界。不要仅因“走廊能优化游戏”就任意添加走廊。

## 5. 避免沿袭性能迷思

- 来源中的粗略绘制调用表，不是当今通用的硬件约定。
- 多边形更少不保证一帧更快。
- 更多光源在不同渲染器中并不具有相同成本。
- 前向／延迟标签不能完整描述现代引擎的混合流水线。
- 透明与透明度测试材质在不同硬件上的表现不同。
- 隐藏物体仍可能消耗资源，取决于系统。

使用实际性能剖析工具与引擎文档。除非已验证，否则应将旧示例数值视为历史背景。

## 6. 打包可用的成品

关卡可以以 alpha、beta、演示版、模组或完成项目的形式发布。诚实标注其状态，而不是等待未定义的完美状态。

打包之前：

- 明确支持的游戏／引擎版本与依赖。
- 包含必需文件与目录结构。
- 包含安装、启动、操作方式、署名、许可与已知问题。
- 排除不需要的缓存、私密数据和未经许可的资源。
- 使用目标社区接受的格式与惯例。
- 优先采用方便获取的分发方式，例如在适当时使用 ZIP，而非不必要的安装程序。

Quake 特定结构见[工具与 Quake](tools-quake.md)。

### 全新安装测试

从干净或单独准备的位置测试：

1. 只遵循随附说明。
2. 确认依赖确实可获得。
3. 启动并完成相关路径。
4. 在支持时测试重试、存档／读档与变化状态。
5. 检查缺失资源、区分大小写的路径与默认设置。
6. 记录测试配置。

不要把在作者资源丰富的开发环境中成功运行，当作包内容完整的证明。

随包保留简短的安装记录：压缩包名称与校验和、所需游戏／模组及版本、目标目录、准确启动说明、测试系统，以及启动、完成和重试的结果。请他人在没有编辑器或你的开发目录的条件下照做。若缺少纹理，记录失败路径，补齐获准提供的依赖或修正路径后重新打包。不要悄悄修好测试机器，却将原压缩包标为通过。

## 7. 展示关卡，而不只是最漂亮的墙

有用的发布页面包括：

- 简洁的名称，以及类型、机制、范围和预期体验的说明。
- 主要空间与关系的游戏内截图。
- 简短且有代表性的游玩视频。
- 可用的下载或平台链接。
- 清晰的署名、依赖、安装与已知问题。

来源建议提供数张截图和简短游玩录像。应将其中具体的分辨率、时长、平台假设与社交媒体建议视为可调整示例，而非永久要求。

记录玩法时，应展示普通游玩与关卡的实际行为。避免片头画面、无关音乐和掩盖被评估活动的剪辑。

## 8. 作品集证据

只添加能说明作者贡献和推理过程的材料：

- 带标注的总览，展示路线、目标、生成点、遭遇或谜题依赖。
- 少量清晰的过程图。
- 简短复盘：预期目标、主要改动、测试证据、优点与弱点。
- 准确的个人职责及团队／资源署名。

不要暗示整个团队项目归自己所有，也不要将最终截图当作关卡设计决策的证据。

原书包含关于雇主如何看待专业工具的具体意见。应将其视为有情境的行业评论，而不是对 Minecraft、Fortnite、Roblox 或其他用户生成内容作品的永恒禁令。让证据匹配实际岗位与受众。

## 9. 发布也是反馈循环

准备应对错误报告、补丁、兼容性问题与玩家解读。区分缺陷与偏好，并让版本信息清晰可见。

受众规模不是直接的质量指标。来源明确重视小型社区、未完成实验、非商业作品，以及为制作本身而制作关卡。

## 交付物

适用时提供实测性能报告、可复现的包、全新安装结果，以及准确呈现项目的发布页面。若未获授权发布，应准备包与说明，但不要公开发布任何内容。
