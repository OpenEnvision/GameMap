# 关卡设计：从预期体验到经过测试的空间

这是对 [The Level Design Book](https://book.leveldesignbook.com/) 的非官方英文改编与重组；原书由 Robert Yang 创立并主要撰写／编辑，贡献者包括 Andrew Yoder。这是一项可执行的技能，而非原书的完整复刻。改编材料采用 **CC BY-NC-SA 4.0** 许可；署名、第三方例外及改动均记录于 [LICENSE.md](LICENSE.md)。

## 范围与限制

- 主要面向 3D 游戏。用于 2D、开放世界、零输入关卡或实体空间时，应说明发生变化的假设。
- 关卡设计组织空间、活动、规则与信息。它不等同于摆放资源、绘制漂亮的平面图、编写背景设定或添加敌人。
- 以迭代方式工作。布局、白盒搭建、脚本、测试与美术可以相互影响；这不是强制的瀑布式流水线。
- 来源尚未完成。[来源映射](references/source-map.md)列出了全部 94 个索引页面，包括占位页。对于链接指向的视频、外部文章和游戏，不视为已经观看、阅读或游玩。
- 下文的检查清单、模板、建议验收标准和任务分流均属改编，并非引文、普适法则或实测结果。

## 串起同一轮迭代

第一次接任务时，复用已有控制器，只做一条从起点到目标的路线。在简报中明确构建版本、玩家目标、改变推进状态的规则、重置状态，以及一个要测试的问题。只有当第二条路线或遭遇有助于回答这个问题时，再将它加入。

三个模板跟随同一个关卡版本。使用相同的构建标识；关卡修改后，保留之前的记录：

| 记录                                         | 填写什么                                         | 返回路线关卡中的例子                                     |
| -------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------- |
| [简报](templates/level-brief.md)             | 意图、固定规则、假设及计划的测试                 | 陌生玩家查看空插座后，能够找到电池并返回。               |
| [试玩测试报告](templates/playtest-report.md) | 每次测试实际发生的情况，包括协助、超时和技术故障 | 记录玩家到过插座后，在岔路口首先选择哪条路线。           |
| [评审](templates/review.md)                  | 与证据对应的问题、建议改动及回归检查             | 如果玩家错过廊道入口，先测试地面连续性，再考虑路线箭头。 |

这是 GameMap 的工作示例。建议的路线与检查不代表已游玩关卡中的观察结果。模板提供了规划示例和明确标注为假设的问题，帮助团队理解三份记录如何衔接。

AI 工具参与时，写清它承担什么工作。开发代理可以修改关卡，游玩代理可以尝试通关，人可以判断提示是否易于理解。这些结果分别记录。自动游玩时，记录观察／动作接口、模型和客户端版本、重置／种子，以及动作或时间预算。游玩代理抵达目标，并不能证明陌生的人类玩家理解了路线。

## 操作流程

### 1. 明确实际任务

重新表述： **针对哪类玩家，在什么规则与约束下，应当发生什么体验，又有什么证据能够支持这一点？**

只询问会改变下一步决策的缺失信息：

- 类型、镜头、移动、战斗、交互及现有项目状态。
- 受众、单人或多人规则、预期时长或对局长度。
- 引擎、平台、资源、团队、截止时间及所需交付物。

只要能够推进，就应说明暂定假设并提出一个小的后续步骤，而不是停留在冗长问卷上。执行实现任务时，先检查项目；不要凭空编造引擎 API、单位、玩家能力或资源。

### 2. 编写最简简报

使用[关卡简报模板](templates/level-brief.md)。确定：

- 一句话的体验目标，以及少量可执行的设计支柱。
- 核心活动；引入、考验、组合或改变哪些内容。
- 开始、完成、失败、重试及持久化条件。
- 必需范围、排除项、依赖及风险最高的未知因素。
- 第一个可证伪的试玩测试问题。

“黑暗而恢宏”还不够。应将其转化为可执行表述：“玩家可以在安全处观察危险，但必须离开安全处才能前进。”

### 3. 用成本最低且有用的表达方式探索结构

选择节拍表、节点图、平面图、剖面图或粗略白盒，不要要求全部具备。

- 标出起点、目标、必经流程、分支、门槛、捷径与地标。
- 区分可见与可达；标注高度与重要视线。
- 先估算，再测量移动、战斗、等待和折返时间。仅凭面积无法预测时长。
- 添加每条分支、每道门槛、每场遭遇和每项独特资源之前，先问清它的作用。

### 4. 尽早让风险部分可玩

针对风险最高的关联，构建一个规模小、可从头玩到尾的片段：

- 使用有代表性的镜头、移动、碰撞、交互和敌人能力。
- 在度量测试场中测试通行净空、跳跃、楼梯、掩体、镜头行为和重试。
- 只添加回答问题所需的脚本、照明、声音与临时标识。
- 不要用“美术完成后就会好用”来解释未经测试的空间问题。

如果无法实际运行，应交付明确标注为 **未运行** 的规格说明和测试步骤。

### 5. 观察，而不是替玩家完成体验

使用[试玩测试指南](references/wayfinding-playtesting.md)和[试玩测试报告](templates/playtest-report.md)。

- 招募测试者之前，定义问题和预期可观察到的行为。
- 除非约定的测试方法有此要求，否则不要在游玩过程中指导、解释或辩护。
- 区分观察到的行为、玩家陈述和设计者解读。
- 将“难”“迷路”或“无聊”定位到具体空间、时间、状态和行动。
- 对改动重新测试，并检查替代路线、重试、持久化、多人模式和性能。
- 小规模便利样本无法证明总体层面的成功率。

### 6. 根据证据选择下一项干预

| 症状         | 添加内容之前先调查                                         |
| ------------ | ---------------------------------------------------------- |
| 路线令人困惑 | 地面连续性、决策点、地标、目标显露与实际连接——不要先加箭头 |
| 战斗平淡     | 敌人职责、可读信息、空间、资源与替代选择——不要先加生命值   |
| 尺度别扭     | 镜头与控制器的实测数据——不要只看现实尺寸                   |
| 单调         | 活动变化、强度、缓冲时间、重复与重试成本——不要一味增加长度 |
| 美术破坏游玩 | 视线、碰撞、交互可读性与导航——不要再堆细节                 |
| 性能差       | 代表性硬件上的实测瓶颈——不要仅凭截图或平均 FPS             |

### 7. 交付可评审的版本

提供任务所需内容，而非所有可能的文档：

1. 意图、约束及明确标记的假设。
2. 带图例和有效注释的节拍／路线／布局。
3. 可玩的白盒或可实现的规格说明。
4. 相关度量和脚本状态。
5. 测试问题、证据、限制与结论。
6. 按优先级排列的下一轮迭代改动。
7. 若要发布：依赖、安装、操作方式、署名、性能与已知问题。

评议时使用 **问题 → 具体位置／复现步骤 → 最小有效改动 → 验证** 。参见[评审模板](templates/review.md)。

## 判断规则

- 对称不等于平衡；单人难度不等于竞技公平。
- 不要将戏剧曲线、教学—考验—变奏，或唯一关键路径强加给每款游戏。
- 并非所有迷失方向都意味着失败。应区分有意设计的探索与难以理解的系统。
- 构图精美的截图不能证明空间可顺利导航。玩家会转身、低头、跳跃，也会从其他方向接近。
- 不要把色彩、形状或建筑联想说成普适心理规律。
- 不要编造试玩观察、完成时间、玩家行为或性能剖析结果。
- 避免过早打磨资源，但不要以“这只是白盒”为由，开脱测试必需信息的缺失。
- 不要把来源中的 STUB/TODO 扩写成方法，再归于原作者名下。
- 编辑代码、安装工具、运行游戏或发布之前，遵守项目与工具的安全规则。

## 任务处理示例

- **“设计一个十分钟的第一人称潜行关卡。”** 从简报、有意义的路线、可读的威胁和一个可测试片段开始，而不是先写冗长的虚构历史。
- **“这张地图总是同一队获胜。”** 提出镜像布局前，先检查规则、起点、行进时间、视线、资源和对局证据。
- **“场景很好看，但玩家总迷路。”** 从玩家镜头出发走过各个决策点；测试最小的空间或信息修正。
- **“教我这本书。”** 使用短小而完整的迭代循环与评议，而不是只背术语。
